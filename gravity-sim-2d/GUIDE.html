gravity-sim-2d · rust + wgpu

Gravity Sim, Explained

You asked to be taught like an idiot. Deal. This page walks through every file of the codebase assuming you know nothing about GPUs and only a little Rust — and by the end you'll know exactly what happens between "I move my mouse" and "pixels change".

fig. 0 — the entire output of this codebase. seriously.

How to read this: the numbered chapters tell one story in order. Inside each chapter, ▸ deep dive panels unfold the actual code line by line — open them when you want the gory details, skip them when you don't. Gold boxes teach you Rust. Blue boxes teach you GPU. Teal boxes answer "ok but why".

01

What you're looking at

When you run cargo run, this program does exactly four things:

  1. Opens a window — a normal, resizable OS window titled "Gravity Sim 2D".
  2. Finds your graphics card — it prints Using GPU: NVIDIA GeForce RTX 4080 SUPER (Vulkan) because it genuinely goes and gets your RTX 4080.
  3. Draws, forever — it repaints the window from scratch, in lockstep with your monitor's refresh rate. Every repaint is: fill everything with black, draw one white square.
  4. Listens to you — scroll wheel zooms, left-drag pans, Esc quits. Resizing the window does not scale the scene — it just shows you more or less of the world.

That's it. It's deliberately tiny — it's the chassis for a gravity simulation that doesn't exist yet. But this chassis already contains every fundamental concept of GPU programming, which is why it's worth understanding completely.

The parts we didn't write

Rust programs pull in libraries ("crates") declared in Cargo.toml. Ours uses five, and it's worth knowing what job each one has, because the whole codebase is basically us gluing two big ones together:

crateversionwhat it actually does for us
winit CPU0.30 Windowing. Talks to the operating system: "make me a window", "tell me when the mouse moves", "tell me when the user resizes". It knows nothing about drawing.
wgpu GPU30.0 Graphics. Talks to the graphics card. On your machine it speaks Vulkan to the NVIDIA driver; on a Mac it would speak Metal, on the web WebGPU. Same Rust code either way.
pollster1.0 A 50-line utility: lets us call wgpu's async functions and just wait for the answer (chapter 10 explains why that's needed).
bytemuck1.25 Safely converts a Rust struct into raw bytes. The GPU doesn't take structs, it takes bytes (chapter 11).
env_logger0.11 Prints wgpu's warnings/errors to the terminal. Without it, problems are silent. Run with RUST_LOG=warn cargo run to see more.
why though?

Why two separate big libraries? Because the OS and the GPU are genuinely separate machines with separate rules. winit's job ends where the inside of the window begins; wgpu's job is only the inside. The single point where they meet is called a surface — wgpu's name for "the drawable part of a window".

02

Two computers in your computer

Everything in this codebase makes sense once you accept one fact: your PC contains two very different computers, and this program runs on both at once.

The CPU is a few extremely clever cores. It runs your operating system, your Rust code, everything. It's great at complicated, branching, one-thing-after-another logic.

The GPU is thousands of dumb cores. Each one is slow and simple, but they all run the same tiny program at the same time on different data. Drawing graphics is exactly that shape of problem: "for each of these 160,000 pixels, decide a color" — so give each core a pixel and let them all go at once.

That tiny program the GPU cores run is called a shader. Ours lives in src/gpu/shader.wgsl, written in a language called WGSL. Chapter 12 dissects it character by character.

GPU concept

Why can't the CPU just draw? It can! Old software did. But "set 160,000 pixels, 165 times a second, while also running physics" is a lot of repetitive work, and the CPU does it one pixel at a time. The GPU does thousands at a time. For the future gravity sim — "compute forces for 100,000 particles" — the same parallelism applies, which is why this project is GPU-first from day one.

check yourself
The white square shows up at 400×400 pixels. Roughly how many times does the fragment part of our shader run per frame?

About 160,000 times — once per covered pixel (400 × 400 = 160,000). And the GPU shrugs; that's a rounding error for it. Chapter 12 explains fragments properly.

Can the Rust code read a variable that lives in the shader, like pixels?

No. They're separate programs on separate processors with separate memory. The only communication is explicit: the CPU sends bytes (buffers, commands), the GPU produces an image. That's why chapter 11 makes such a fuss about copying a struct into a buffer.

03

What a "frame" is

The window is not a painting; it's a flipbook. The program produces a complete new image — a frame — over and over, and your monitor shows each one for ~6 milliseconds (at 165 Hz). Nothing on screen "stays"; if it's visible, it's because we redrew it this frame, from scratch, again.

Who keeps the loop spinning?

winit is event-driven: it sleeps until something happens. So how do we redraw continuously? At the end of every draw, src/app.rs calls request_redraw() — "wake me up to draw again". That would spin at 100% CPU, except for one elegant brake: the surface is configured in Fifo mode (chapter 10), which means "presenting a finished image waits for the monitor's next refresh". That wait is vsync. Free, perfectly-paced throttling — and later it's the natural heartbeat for simulation ticks.

why though?

Why redraw at all when nothing changed? Right now we technically could redraw only on input. But a gravity simulation changes every frame by itself, so the architecture assumes continuous motion from day one. It also makes resize/zoom/pan feel instant — there's always a fresh frame at most ~6ms away.

check yourself
You drag the square to the right, then let go and don't touch anything. Is the program still drawing?

Yes — same loop, same rate, drawing the same image over and over. The square stays put because the camera numbers stopped changing, not because drawing stopped.

What stops the redraw loop from using 100% of a CPU core?

Vsync. Presenting in Fifo mode blocks until the monitor is ready for a new image, so the loop naturally runs at the refresh rate and sleeps the rest of the time.

06

main.rs — the ignition

The shortest file, and the only one the program starts in. Its whole job: turn on logging, build the event loop, hand control to App — then it never returns until you quit.

deep dive: every line

mod app; and friends — these four lines are the project structure. Each one tells the compiler "compile that file too, as a module of this program" (see the Rust box in chapter 4). Order doesn't matter.

use winit::event_loop::EventLoop; — a use is just an abbreviation. Without it you'd write the full path winit::event_loop::EventLoop::new() every time. Nothing is "imported" in a runtime sense; it's naming convenience only.

env_logger::init(); — installs the logger. wgpu almost never panics on mistakes; it reports them through Rust's standard log system. No logger installed = errors go nowhere. This line is one of those things you set up once and it saves you a day of confusion six months later. You control it with an environment variable: RUST_LOG=warn cargo run.

EventLoop::new().unwrap() — asks the OS for an event loop.

Rust — unwrap and Result

Rust functions that can fail return a Result — a value that is either Ok(the thing) or Err(what went wrong). The compiler forces you to decide what to do about the Err case. .unwrap() is the bluntest decision: "give me the thing; if it failed, crash the program right here." Perfectly reasonable at startup — if you can't even get an event loop, there's nothing sensible to do but die loudly.

let mut app = App::default(); — builds our application object with every field at its default (no GPU yet, camera at start position).

Rust — mut

Variables are immutable unless you say mut. The event loop will be changing app's insides constantly (camera moves, GPU state appears), so it must be declared mutable — and &mut app on the next line lends the loop mutable access to it.

event_loop.run_app(&mut app) — the point of no return. From here on, winit owns the thread: it sleeps until the OS reports something (mouse moved, redraw needed), calls the matching method on app, and sleeps again. Forever, until something calls event_loop.exit() — which app.rs does on Esc or the window's ✕.

07

app.rs — the switchboard

src/app.rs is the operator at the old telephone exchange: every event the OS sends arrives here, gets identified, and gets plugged through to the one module that handles it. It contains almost no logic of its own — deliberately.

The deal winit offers

winit says: "implement my ApplicationHandler interface — a resumed method and a window_event method — and I'll call them at the right times." Our whole file is filling in that form.

Rust — traits

A trait is a named list of methods — a contract. impl ApplicationHandler for App { … } means "my App type fulfills that contract; here are the method bodies." It's how one library (winit) can call into code it has never seen (ours). If you know interfaces from other languages: same idea.

event from the OSwhat app.rs does with it
resumedFirst call after startup → create the window, boot the GPU (once).
CloseRequested / Escevent_loop.exit() — end of program.
Resized→ ctx.resize() (chapter 10). Camera untouched — that's the no-scaling rule.
RedrawRequested→ acquire a frame, → renderer.render(), then immediately request the next redraw.
CursorMoved / MouseInput / MouseWheel→ the CameraController (chapter 9).
Occluded(false)Window just became visible again → kick the redraw loop awake.
everything elseIgnored (_ => {}). The OS sends dozens of event kinds we don't care about.
deep dive: the state, and why it's an Option
Rust — Option

Rust has no null. When a value can legitimately not-exist-yet, you say so in the type: Option<Gpu> is either Some(gpu) or None, and the compiler refuses to let you use it without checking which. Here it encodes a real-world awkwardness: App is created in main(), but winit forbids creating windows before the event loop runs — so for a brief moment the app exists without its window/GPU half. The Option makes that moment impossible to mishandle.

Rust — derive

#[derive(Default)] is a derive macro: the compiler writes the boring Default implementation for you (each field gets its own default: None, default camera, default controller). Anything in #[…] is an attribute — metadata attached to the next item. You'll meet more powerful ones in chapter 11.

deep dive: resumed — booting the world

Three things worth pausing on:

1. The 1280×720 is logical pixels. On a monitor with 125% scaling, winit multiplies by 1.25 and makes a 1600×900 physical window. Everything after this line works in physical pixels.

2. Arc::new(…).

Rust — Arc, or shared ownership

Rust's core rule: every value has exactly one owner, so the compiler always knows when to free it. But the window genuinely needs two owners: our App (to ask for redraws) and the GPU surface (which draws into it and must never outlive it). Arc — Atomically Reference Counted — is the escape hatch: a counter travels with the value; .clone() makes a new handle and bumps the counter; the value is freed when the counter hits zero. Cheap, safe, everywhere in Rust code that shares things.

3. pollster::block_on(…).

Rust — async, in one paragraph

An async fn doesn't run when called — it returns a plan (a "future") that must be driven to completion by an executor. wgpu makes GPU setup async because on some platforms (the web) you're not allowed to wait blocking-style. On desktop, we're happy to just wait — and that's the entire job of pollster::block_on: "run this future right here, right now, and give me the result." One line of ceremony, then async never bothers us again.

deep dive: window_event — the actual switchboard
Rust — match and patterns

match is a switch statement with superpowers. Each arm is a pattern that can simultaneously test the shape of a value and pull data out of it. Look at the Escape arm: it matches "a KeyboardInput event, whose inner key is specifically Escape, in the Pressed state" — and the .. means "and I don't care about the other fields". WindowEvent::Resized(new_size) both matches the variant and captures the new size into a variable. The | combines two patterns into one arm ("close request OR escape key"). The compiler checks you handled every possible variant — that's what the final _ => {} ("anything else: do nothing") satisfies.

Rust — let … else

let Some(gpu) = &mut self.gpu else { return; } reads as: "if self.gpu contains a value, name it gpu and continue; otherwise leave the function." It's the standard early-exit for Options.

Note the shape of the RedrawRequested arm — it's the frame loop from chapter 3, in the flesh: try to get this frame's canvas; if that works, draw into it; either way, ask for another go. If acquire_frame returned None, the surface was mid-repair (chapter 10) and we simply skip one frame — at 165 fps, nobody will ever notice.

check yourself
Why is request_redraw() called inside the redraw handler itself?

That's what makes rendering continuous: each frame schedules the next one. Vsync (chapter 3) keeps this from spinning wildly — presenting blocks until the monitor wants a new image.

The user mashes keys on the keyboard. Which match arm runs?

For Escape: the exit arm. For every other key: _ => {} — the catch-all that does nothing. The events still arrive; we just decline to care.

08

camera.rs — where am I looking

This file is pure math — no winit, no wgpu, no windows. Which means it's fully understandable on its own. The entire camera is three numbers:

And the entire world→screen mapping — the one formula this whole codebase revolves around — is:

screen_px = world × zoom + pan

The square's corners live at world ±0.5. With the starting zoom = 400 (pixels per world unit) and pan = [0, 0], the corner (+0.5, +0.5) lands at screen (+200, +200): two hundred pixels right of and above the window center. Hence: a 400×400 px square, dead center, in any window.

why though? — the no-scaling trick

You asked for "resizing must not scale or move the scene". Look at the formula: the window's size appears nowhere in it. World units become pixels using only zoom and pan. So when the window changes, nothing about the scene's pixel size or its position relative to the window center can change — the resize only changes how many pixels exist around the center for the world to show through. The invariant isn't enforced by careful code; it's baked into the choice of coordinate system.

Panning: embarrassingly simple

The mouse moved 30 px right → add 30 to pan[0] → every world point lands 30 px further right. The scene sticks to your cursor 1:1, at any zoom, because pan is applied after the zoom multiply.

Zooming: exponential, and anchored under your cursor

deep dive: why multiply, and where that pan formula comes from

Why ZOOM_STEP.powf(lines) instead of adding? One wheel notch multiplies zoom by 1.1 (10% bigger). Multiplying feels identical at every scale: +10% is a visible step whether you're at zoom 4 or zoom 4000. If we added, say, 50 per notch, zooming would crawl when far out and explode when close in. .clamp(MIN_ZOOM, MAX_ZOOM) just stops you at 0.1 and 10,000 px/unit so you can't scroll into oblivion.

The anchor formula, derived with actual numbers. Rule we want: the world point currently under your cursor stays under your cursor while everything grows around it (how every map app behaves). Say zoom = 400, pan = [0,0], and your cursor sits at anchor = 100 px right of center. The world point under it is w = (100 − 0) / 400 = 0.25. Now scroll one notch in: new_zoom = 440, so k = 1.1.

If we changed only zoom, that world point would land at 0.25 × 440 = 110 px — it slid 10 px away from your cursor. To pin it, pan must absorb the slide: we need 0.25 × 440 + pan = 100, so pan = −10. The formula produces exactly that: pan' = 100 − (100 − 0) × 1.1 = −10. ✓

In general: pan' = a − (a − pan) · k is just "solve w·zoom' + pan' = a for pan'", i.e. the world origin slides away from the anchor by the same factor everything else grew by. Zoom out and k < 1 — same formula pulls the scene back toward your cursor.

Rust — struct + impl

Rust separates data from behavior: struct Camera { … } declares the fields; a separate impl Camera { … } block holds its functions. Methods taking &self may only read; &mut self (like both methods here) may modify. The impl Default for Camera block is the same idea aimed at a trait: it teaches Camera how to construct its starting value (pan [0,0], zoom 400), which is what App::default() ends up calling.

Rust — const

pub const INITIAL_ZOOM: f32 = 400.0; — a named compile-time constant. The file keeps all its magic numbers (MIN_ZOOM, MAX_ZOOM, ZOOM_STEP) at the top with doc comments, so tuning the feel later is a one-line edit, not a treasure hunt.

check yourself
Zoom is 800 (px per world unit). How wide is the square on screen?

800 pixels. The square is exactly 1 world unit wide (corners at ±0.5), and zoom is the world-unit→pixel exchange rate.

You make the window twice as wide. What happens to pan and zoom?

Nothing. Literally nothing in camera.rs runs on resize. That's the entire no-scaling guarantee.

Why does zooming in at the top-right corner make the scene drift down-left?

Because the anchor formula pushes the world origin away from the anchor by factor k: everything grows around your cursor, so the parts between cursor and center get pushed toward (and past) the center. It's the same motion Google Maps makes.

09

input.rs — your mouse, translated

src/input.rs owns two jobs: remember what the mouse is doing (where it is, whether the left button is down), and translate raw window events into the camera operations from chapter 8. It also handles a subtle, bug-breeding detail: the two halves of this program disagree about which way is up.

deep dive: the controller, line by line

Why Option again? Because "where was the cursor last frame" genuinely has no answer before the cursor has ever entered the window — and panning needs a previous position to compute a delta from. Encoding "no answer yet" in the type means the first-ever mouse event can't produce a garbage jump.

Read it as a story: convert to centered coordinates; if we know where the cursor was and the left button is held, pan by the difference; either way, remember where it is now. Releasing the button doesn't need special handling — on_mouse_button just flips left_down, and this function stops calling pan_by.

Rust — enums that carry data

MouseScrollDelta is an enum whose variants hold values: a mouse wheel sends LineDelta(x, y) in whole notches, a touchpad sends PixelDelta(position) in pixels. The match unpacks whichever arrived and normalizes both into "notches" (dividing pixels by 60, a conventional notch-height). This is the Rust enum superpower: variants aren't just names, they're alternative shapes of data, and the compiler makes you handle each shape.

self.cursor.unwrap_or([0.0, 0.0]) — "the cursor position, or the window center if we've never seen the cursor" (possible if you scroll before ever moving the mouse over the window). A graceful default instead of a crash.

check yourself
You move the mouse straight up while dragging. What sign does winit report for the y change, and what sign reaches pan_by?

winit's y decreases (its +y is down). centered() flips it, so the delta reaching pan_by is positive y — matching the camera's +y-up world, and the scene follows your hand upward.

Why does the controller store the cursor position at all, instead of using the deltas winit could give?

Window events report absolute positions, so a delta must be computed from the remembered previous position. (winit does offer raw deltas via a separate "device event" stream, but absolute positions are also exactly what zoom-anchoring needs — one mechanism, two uses.)

10

gpu/context.rs — the negotiation

This file performs the creation chain from chapter 5 (fig. 4), once, at startup — and then spends the rest of its life doing two humbler jobs: resizing the surface, and handing out one frame at a time. It's the file that will barely ever change as the simulation grows.

deep dive: the startup chain, in code

Line by line, in plain words:

  • Instance — boot wgpu. The mouthful of a constructor does two mundane things: lets an environment variable (WGPU_BACKEND) override which API to use, and hands over a display handle, which helps GPU enumeration on some Linux setups.
  • Surface — wrap our window's drawable area. Note window.clone(): that's the Arc from chapter 7 sharing ownership, so the surface can guarantee the window outlives it. (That guarantee is what the odd type Surface<'static> in the struct declaration is about.)
  • Adapter — "give me a physical GPU that (a) is the high-performance one and (b) can actually present to this surface." On your machine: the RTX 4080 SUPER, speaking Vulkan. The println! is why you see that line in the terminal.
  • Device + Queue — open the connection. We request zero optional features and default limits: maximum portability, and the validator holds us to the strictest rules. When the gravity sim needs something fancy later, this is where it gets requested.
  • Configure the surface — the default config means: the window's size, the screen's preferred pixel format, and Fifo presentation — vsync, the frame-loop brake from chapter 3.
Rust — .await and expect

The .awaits mark the two genuinely slow steps (driver initialization); they're what makes this function async, and chapter 7's pollster::block_on is what waits for them. .expect("msg") is .unwrap() with a custom parting message — same "crash if this failed" policy, better crash report.

Resize: five honest lines

The surface's textures must exactly match the window's size, so every resize rebuilds them. Notice what's absent: no camera, no scale factors, no layout math. That absence is the "resizing doesn't touch the scene" guarantee, enforced by having nothing to enforce.

acquire_frame: the paranoid doorman

Once per frame, someone must ask the surface for "this frame's canvas" (the surface texture). The OS can refuse in several ways, because the surface is the one GPU object the outside world can break — a resize mid-frame, a driver reset, a lock screen. acquire_frame() translates all of them into a simple contract for the caller: Some(frame) = draw, None = skip this frame, I've already fixed things.

check yourself
Why is startup allowed to just crash (expect) while frame acquisition carefully recovers?

At startup, failure means "this machine can't run the program" — crash loudly, nothing better exists. At frame time, failure is a routine, transient hiccup (a resize!) — recover and carry on. Same philosophy as a car: refuse to start with no engine, but don't explode at every pothole.

What single call makes vsync happen?

surface.get_default_config(…) — the default present mode is Fifo. There's no separate "enable vsync" switch; it's a property of how the surface presents.

11

gpu/renderer.rs — the drawing machine

Everything chapter 10 built is plumbing; this file finally draws. It does two things: at startup, it bakes the pipeline (the "how to draw" recipe); every frame, it ships the camera to the GPU and replays the recipe. The interesting story is how a Rust struct becomes GPU bytes — the one place the two computers from chapter 2 must agree perfectly.

One struct, two languages

These are two declarations, in two languages, compiled by two different compilers, describing the same 24 bytes. Nothing checks they match — if they drift apart, the shader just reads garbage from the wrong offsets. Hence the paranoia below:

byte 0–34–78–11 12–1516–1920–23
holds resolution.xresolution.ypan.x pan.yzoom_pad
e.g. 1280.0720.00.0 0.0400.00.0

The 24 bytes as they sit in the uniform buffer. Each cell is one f32 = 4 bytes.

deep dive: the three magic attributes on that struct
Rust — #[repr(C)]

By default, Rust may reorder your struct fields in memory for efficiency — the source order is a suggestion. #[repr(C)] switches to C's rules: fields in declared order, predictable layout. Mandatory for any struct whose raw bytes another system will read.

Rust — bytemuck's Pod and Zeroable

Turning a struct into bytes is trivially easy to do wrong (padding bytes, pointers, types with invalid bit patterns). The bytemuck crate makes it safe: deriving Pod ("plain old data") makes the compiler prove the struct is nothing but plain numbers with no gaps — the derive literally fails to compile if there's hidden padding. That proof is what makes bytemuck::bytes_of(&globals) (used below) a safe, zero-cost "give me these 24 bytes" instead of an unsafe hack.

And why _pad? WGSL's layout rules round a struct's size up to a multiple of its largest member's alignment — this struct contains vec2s (8-byte aligned), so WGSL insists the struct is 24 bytes, not 20. The explicit _pad: f32 makes both sides agree on 24 honestly, and doubles as a free slot for the next field (elapsed time, probably). This kind of invisible-rule mismatch is a top-3 GPU beginner bug; the comments in both files cross-reference each other for exactly that reason.

deep dive: startup — buffer, sockets, pipeline

A buffer is just GPU memory with a size and a permission list. labels appear in error messages — always set them.

GPU concept — why two objects for one buffer?

The layout (socket shape) is part of the pipeline's compiled interface — the shader is compiled against "binding 0 is a uniform buffer". The group (the plug) is swappable per draw without recompiling anything. With one buffer it feels like bureaucracy; with a particle sim double-buffering positions every frame, swapping plugs into a fixed socket is exactly what you want. The socket number here — group 0, binding 0 — is the same address the shader declares with @group(0) @binding(0). That pair of numbers is the entire connection between the two languages.

include_wgsl! pastes the shader file into the executable at Rust compile time (no file loading at runtime), and the GPU driver compiles it here, at pipeline creation — a typo in the WGSL panics on this line with a pointer into the shader source. The descriptor is long but every field answers a dumb question: which program? ("vertex_shader_main"/"fragment_shader_main" — one file can hold many entry points) · drawing into what format? · triangles or lines? · depth sorting? (no). Baked once; every frame just says "use that recipe".

deep dive: render() — the every-frame path
GPU concept — record, then submit

GPU work isn't issued call-by-call — that would mean thousands of tiny CPU↔GPU round-trips. Instead you record everything into a command encoder (a shopping list), then submit the finished list to the queue in one go. Until submit, nothing has happened on the GPU at all.

The famous clear: LoadOp::Clear(BLACK) means "when this pass begins, wipe the canvas to black". That's your black background — one enum value. And draw(0..6, 0..1) is the entire drawing command: "run the vertex shader for indices 0,1,2,3,4,5, once" (the 0..1 is the instance range — the slot that becomes 0..100_000 when particles arrive). Finally present(frame) hands the finished canvas to the OS — the moment the square actually reaches glass.

check yourself
Which single line paints the background black?

load: wgpu::LoadOp::Clear(wgpu::Color::BLACK) in the render pass. Not a draw call — a "how to start the pass" setting.

You add a time: f32 field after zoom in the Rust struct but forget the WGSL side. What happens?

It compiles fine on both sides — and the shader silently reads the wrong bytes (your new field where it expects padding, sizes now disagreeing: 28 vs 24 — wgpu's validator would actually catch that size mismatch at draw time and log an error… courtesy of the layout declaring a uniform binding. Subtler drifts, like swapped field order, really do just render garbage). Moral: edit these two structs as a pair, always.

Why is it fine that write_buffer rewrites all 24 bytes every frame even when the camera didn't change?

24 bytes is nothing (the GPU moves gigabytes per second), and unconditional upload means zero "did it change?" bookkeeping. When the sim ticks every frame anyway, per-frame upload is the normal pattern, not a waste.

shader.wgsl — the program inside the GPU

Everything so far was arrangements. This file is the only code that runs on the GPU — GPU territory at last. It's ~40 real lines of WGSL, and it defines two tiny functions that between them put the square on screen.

The two stages, and the machine between them

The decorators (WGSL calls them attributes)

Those @word markers are not decoration — each one is a contract with the hardware, answering "where does this value come from / go to?". Here is every one used in our shader:

attributeonmeaning
@vertexa function"This is a vertex-stage entry point." The Rust side selects it by name: entry_point: Some("vertex_shader_main").
@fragmenta function"This is a fragment-stage entry point." Same file, second entry point — one WGSL file can hold many.
@builtin(vertex_index)an input"Hardware, please fill this parameter with which vertex number this run is" — 0,1,2,3,4,5 across our six runs. Free counter, no buffer needed.
@builtin(position)an output"My return value is the clip-space position" — the one output the rasterizer requires from every vertex shader.
@location(0)an output"My return value goes to output wire #0" — wired to the first (only) color target the pipeline declared: the surface texture. Wire numbers, not names, connect the stages.
@group(0) @binding(0)a global"This variable is plugged in from outside, at socket group 0, binding 0" — the exact address the Rust side plugs the camera buffer into with set_bind_group(0, …). This pair of numbers is the whole CPU↔GPU wiring.
deep dive: the vertex shader, line by line

var<uniform> globals — a global variable living in the uniform address space: read-only, same value for all 6 runs, supplied from outside via that @group/@binding socket. This is chapter 11's 24 bytes, arriving.

The no-vertex-buffer trick. Normally vertex positions stream in from a buffer. For 6 fixed corners that's overkill — instead we exploit @builtin(vertex_index): the hardware tells us "you are run #3", and we look up corner #3 in a little array written right in the code. That's why the pipeline said buffers: &[].

The three-line coordinate journey — with real numbers for corner (+0.5, +0.5) at startup (window 1280×720, zoom 400, pan [0,0]):

linespacevaluewhat happened
corners[i] * 0.5world(0.5, 0.5)±1 template corners → the 1×1-unit square.
* zoom + panscreen px(200, 200)The camera formula from chapter 8 — the only line the camera touches.
* 2 / resolutionclip(0.3125, 0.5556)Pixels → the GPU's mandatory −1…+1 space: ±640px maps to ±1 horizontally, ±360px to ±1 vertically.

And there's the no-scaling rule one final time, from the GPU's side: the window size enters only in that last division, which cancels out exactly — a 200px offset is 0.3125 of a half-window when the window is 1280 wide, and 0.25 when it's 1600 wide, but both land on the pixel 200 px from center. Same pixels, any window.

The returned vec4 packs (x, y, z, w): z = 0 (flat 2D, no depth), w = 1 (a perspective-divide term — leave it at 1 until you do 3D).

WGSL — var vs let

In WGSL, let is an immutable value; var is actual addressable storage. The corner array is a var because indexing with a runtime value (vertex_index) requires the array to exist in real memory, not as a compile-time value. If you write let there, the compiler rejects it — now you know why.

deep dive: the fragment shader (all four lines of it)

For every pixel the rasterizer found inside our two triangles, this runs once and answers: (red, green, blue, alpha) = (1, 1, 1, 1) — fully white, fully opaque. Colors are 0.0–1.0 per channel, not 0–255. All ~160,000 runs return the same constant; a gravity sim will make this stage earn its keep (soft glowing particles are fragment-shader work). Pixels outside the triangles never run it — their black comes from chapter 11's clear, not from any shader.

check yourself
What would you change to make the square red?

The one line of fragment_shader_main: return vec4<f32>(1.0, 0.0, 0.0, 1.0);. Nothing on the CPU side changes at all.

@group(0) @binding(0) — where do those two numbers appear on the Rust side? (Two places.)

In renderer.rs: the bind group layout entry declares binding: 0, and at draw time set_bind_group(0, …) supplies group 0. Numbers matching across the language boundary is the entire wiring mechanism.

Why does the vertex shader run 6 times but the fragment shader ~160,000 times?

Vertex runs are one per corner (6). The rasterizer then fills the area between corners — a 400×400 px square is ~160,000 covered pixels, each needing a color. Area beats corners.

14

Where the gravity goes

Nothing in this codebase simulates anything yet — and that's the point. Here's how the pieces you now understand are waiting to be used:

  • Particles will be a buffer. Just like Globals, but big: a buffer with, say, 100,000 entries of position + velocity + mass, created by the Device in renderer.rs.
  • Physics will be a compute shader. A third kind of shader (no vertices, no pixels — just "run this function 100,000 times on this buffer"). It will read particle positions, compute gravity, and write new positions — entirely on the GPU, no CPU round-trip.
  • Drawing particles will be instancing. That second argument in draw(0..6, 0..1) becomes 0..100_000: "draw the same 6-vertex square once per particle", with the vertex shader offsetting each copy by its particle's position.
  • The camera is done. Pan/zoom/resize behavior applies unchanged to a million particles — that's why it was built as pure math in its own file.
  • The frame loop is the simulation clock. Each vsync tick: run compute pass, then render pass. Both recorded into the same command encoder you met in chapter 11.

When you're ready to build it, the only files that change meaningfully are gpu/renderer.rs (new buffers, new pipelines, one extra pass) and gpu/shader.wgsl (a @compute entry point next to the existing two). Everything else already does its job.

Glossary

Plain-language definitions. Dotted terms all over this page jump here; use your browser's Back button (or Alt+←) to return.

adapter
wgpu's word for one physical GPU in your machine (or a software fallback). You don't draw with it — you inspect it and request a device from it. Created in gpu/context.rs.
bind group
The object that says which actual buffer is plugged into which numbered socket a shader declared. The socket numbering is @group(g) @binding(b) in WGSL; the Rust side matches it with set_bind_group(g, …). Its sibling, the bind group layout, describes only the socket's shape (a uniform buffer, visible to the vertex stage) — the layout is part of the pipeline; the group carries the real data.
buffer
A plain block of GPU memory with a size in bytes and a list of allowed uses (UNIFORM, COPY_DST, …). No structure, no types — bytes. Both sides just have to agree on the layout (see chapter 11's byte table).
clip space / NDC
The coordinate system a vertex shader must output: x and y from −1 to +1 across the viewport (left→right, bottom→top), regardless of window size. Anything outside is clipped off. Also called normalized device coordinates.
command encoder
A recorder for GPU work. You "record" passes and copies into it; nothing executes until the finished recording is submitted to the queue. Like writing a full shopping list instead of driving to the store per item.
device
Your open, validated connection to a GPU. Creates every resource (buffers, pipelines, shader modules, bind groups) and checks your work. If you break the rules, the device reports errors through the logger — that's why env_logger exists in this project.
fragment
A candidate pixel produced by the rasterizer. The fragment shader runs once per fragment and returns its color. In this project: "return white", ~160,000 times a frame.
frame
One complete image of the window. Programs like this one produce a fresh frame continuously (here: at the monitor's refresh rate). Also used for the surface texture you draw the image into.
instance (wgpu)
The initialized wgpu library — the root object everything else comes from. Not to be confused with drawing "instances" (copies of geometry; see chapter 11's draw call).
physical vs logical pixels
Physical: actual screen dots. Logical: physical divided by the OS scale factor (125% scaling → 1 logical = 1.25 physical). We request the window in logical (1280×720) so it looks right on any monitor, but do all rendering math in physical.
pipeline (render pipeline)
The compiled, immutable bundle of "how to draw": vertex shader + fragment shader + output format + primitive type + blend/depth settings. Expensive to create, so it's built once at startup and reused every frame. Different look = different pipeline.
queue
Where command buffers are submitted for the GPU to execute, in order. Also provides write_buffer (small uploads) and, in wgpu 30, present.
rasterizer
Fixed hardware between the two shader stages: takes each triangle's three clip-space corners and works out exactly which pixels it covers, emitting a fragment for each. Not programmable, extremely fast, entirely invisible in the code — but it's the reason the two shaders exist.
shader
A small program that runs on the GPU, thousands of instances in parallel. Kinds used here: vertex (per corner: "where does this go on screen?") and fragment (per pixel: "what color?"). The future physics will add compute (per anything: "just calculate").
surface
The bridge object between the window and the GPU: the drawable area, owning a small rotating set of images (swapchain). Must be configured (size, format, present mode) before use, and re-configured on every resize.
surface texture
"This frame's canvas": the texture the surface hands you to draw into, which is then handed back with present. Acquiring it can fail in recoverable ways (window resized, GPU reset…) — gpu/context.rs handles all of them.
swapchain
The rotating set of 2–3 images behind a surface: while the monitor shows image A, you draw into image B, then swap. The word comes from Vulkan; wgpu hides it inside the surface, but you'll meet it constantly in graphics writing.
texture
GPU memory organized as an image (width × height × pixel format) rather than raw bytes. What render passes draw into; also what images/sprites are stored as.
uniform
Small, read-only data that is the same ("uniform") for every shader invocation in a draw — settings, not per-item data. Ours: window resolution + camera pan + zoom, 24 bytes, updated every frame.
vertex
One corner of a shape. GPUs draw everything as triangles between vertices. Our square = 2 triangles = 6 vertex-shader runs (two corners are visited twice).
vsync / Fifo
Synchronizing presentation to the monitor's refresh. In wgpu it's the Fifo present mode (the default, and the only one guaranteed everywhere): finished frames queue up and are shown one per refresh; when the queue is full, your program waits. Gives smooth, tear-free output and free CPU throttling.
Vulkan
One of the low-level "languages" GPUs' drivers speak (others: DirectX 12, Metal). wgpu translates our calls into whichever one your platform has — on your Windows + NVIDIA box it chose Vulkan. You never write Vulkan yourself here.
WGSL
WebGPU Shading Language — the language shaders are written in for wgpu. Rust-ish syntax, but a separate, much smaller language compiled by the GPU driver. Chapter 12 is a full tour.
winit
The Rust crate for windows and input: creates the window, delivers every OS event (mouse, keyboard, resize) to our App. Cross-platform; knows nothing about drawing.
world space / screen space
World space: the simulation's own coordinate system, in "world units" — the square is 1×1 world units at the origin, forever, regardless of any window. Screen space (in this codebase): physical pixels measured from the window's center, +y up. The camera converts world → screen; the shader converts screen → clip.
