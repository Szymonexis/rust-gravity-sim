Gravity Sim, Explained

You asked to be taught like an idiot. Deal. This page walks through every file of the codebase assuming you know nothing about GPUs and only a little Rust — and by the end you'll know exactly what happens between "a particle gains mass" and "pixels change".

fig. 0 — the entire output of this codebase right now. one particle, breathing.

How to read this: the numbered chapters tell one story in order. Inside each chapter, ▸ deep dive panels unfold the actual code line by line — open them when you want the gory details, skip them when you don't. Gold boxes teach you Rust. Blue boxes teach you GPU. Teal boxes answer "ok but why".

01

What you're looking at

When you run cargo run, this program does five things:

  1. Reads a config file — app-config.json, sitting next to Cargo.toml. Window size, zoom limits, how many particles to make and where, how fast the simulation ticks. Anything missing or broken falls back to a default on its own, so one bad line never costs you the rest of the file.
  2. Builds a cloud of particles — sampled into a shape you choose (disc, ring, clusters, sunflower spiral…), given masses and velocities, and then pushed apart until no two of them overlap.
  3. Starts a simulation on its own thread — ticking at a rate you set (60 per second by default), completely independent of your monitor.
  4. Finds your graphics card — it prints Using GPU: NVIDIA GeForce RTX 4080 SUPER (Vulkan) because it genuinely goes and gets your RTX 4080.
  5. Draws, forever — it repaints the window from scratch in lockstep with your monitor's refresh, showing whatever the simulation last published. Resizing shows you more or less of the world; it never scales the scene.
  6. Draws an overlay on top — two panels of text in the top corners, telling you what the simulation is doing and which keys do what. Rendered from a font file the program loads off your disk, by code we wrote ourselves (chapter 15).

what it does today

There is no gravity yet. The simulation's tick is a placeholder: it swings every particle's mass between 1 and 1000 and back on a 4-second cosine. That's deliberately dull physics doing a very useful job — it proves the thread, the tick rate, the hand-off to the renderer, the mass→size rule and the mass→colour ramp are all wired up and visibly alive. It also gives the playback controls something to visibly do: pause it and the disc freezes mid-breath, run it backwards and the disc breathes in. Chapter 17 is where the real forces go, and it's a small hole to fill.

why though?

Why two separate big libraries? Because the OS and the GPU are genuinely separate machines with separate rules. winit's job ends where the inside of the window begins; wgpu's job is only the inside. The single point where they meet is called a surface — wgpu's name for "the drawable part of a window".

02

Two computers in your computer

Everything in this codebase makes sense once you accept one fact: your PC contains two very different computers, and this program runs on both at once.

The CPU is a few extremely clever cores. It runs your operating system, your Rust code, everything. It's great at complicated, branching, one-thing-after-another logic. We use two of its cores at once: one thread ticks the simulation, one runs the window — chapter 3.

The GPU is thousands of dumb cores. Each one is slow and simple, but they all run the same tiny program at the same time on different data. Drawing is exactly that shape of problem: "for each of these 160,000 pixels, decide a color" — so give each core a pixel and let them all go at once.

That tiny program the GPU cores run is called a shader. Ours lives in src/gpu/shader.wgsl, written in a language called WGSL. Chapter 14 dissects it character by character. There is a second one — src/ui/ui.wgsl, for the text overlay — and chapter 15 explains why it is a separate file rather than two more functions in the first.

GPU concept

Why can't the CPU just draw? It can! Old software did. But "set 160,000 pixels, 165 times a second, while also running physics" is a lot of repetitive work, and the CPU does it one pixel at a time. The GPU does thousands at a time. For the future gravity sim — "compute forces for 100,000 particles" — the same parallelism applies, which is why this project is GPU-first from day one.

check yourself
You bump amount from 1 to 50,000. Which of the two computers has to work harder?

Both, but differently. The CPU now ticks 50,000 particles per tick and copies 50,000 structs per published snapshot — that's the simulation thread. The GPU draws 50,000 instances instead of 1, which it barely notices. The startup cost of packing them without overlap is CPU too (chapter 9).

Can the Rust code read a variable that lives in the shader?

No. Separate programs, separate processors, separate memory. The only communication is explicit: the CPU sends bytes (buffers, commands), the GPU produces an image. That's why chapter 13 makes such a fuss about copying structs into buffers.

03

Two clocks, not one

The window is not a painting; it's a flipbook. The program produces a complete new image — a frame — over and over, and your monitor shows each one for ~6 ms (at 165 Hz). Nothing on screen "stays"; if it's visible, it's because we redrew it this frame, from scratch, again.

The simulation is also a flipbook, but a different one. It advances in ticks of a fixed size — 1/60th of a second by default — on a thread that has never heard of your monitor. These two rates have nothing to do with each other, and that is a design decision, not an accident.

Why not just tick once per frame?

Because then your physics would depend on your monitor. A 165 Hz screen would run the universe 2.75× faster than a 60 Hz one; alt-tabbing would freeze time; a dropped frame would be a dropped second of gravity. And integrating with a variable step is numerically worse: orbits that are stable at a constant 1/60 s drift and blow up when the step keeps changing size.

So src/simulation/runner.rs gives the world its own thread and its own fixed-timestep clock, and the window becomes a viewer: at each vsync it asks "anything new?", takes it if so, and draws.

why though? — the alternative

There is a single-threaded version of this: keep an accumulator in the redraw handler, add the frame time to it, and run while accumulator >= TICK { tick(); accumulator -= TICK; }. It's simpler, and for many games it's the right answer. It also means a tick can never run while a frame is being drawn — the two share a core, so a slow tick is a dropped frame. This project chose the thread because the endgame is 100,000-body physics, where that coupling is exactly what you don't want.

A third dial: how fast that clock runs

The tick size is fixed — that's the whole point above, and nothing you press changes it. What the arrow keys change is how much wall-clock time passes between ticks. At speed +2x the thread aims for a deadline every 8.3 ms instead of every 16.7 ms; each tick still integrates exactly 1/60 s of simulated time. The physics resolution is untouched; only the pace is.

That distinction is the reason reverse is even possible. Running the world backwards means feeding tick() a negative delta — a step of −1/60 s — not running the loop backwards in time. Chapter 8 has the whole mechanism.

why though? — three numbers that all sound like "speed"

Keep these apart or nothing later makes sense:

fps is how often the window is redrawn. Your monitor decides it. Pausing does not change it — a paused sim still redraws at 144 fps, it just keeps drawing the same thing.

tickRate (config) is the size of one step of simulated time, and the base rate ticks are aimed at. Changing it changes the physics.

speed (arrow keys) is a multiplier on that base rate, and a sign. It changes nothing about the physics — only how often, and in which direction, steps happen. tps, the second number in the title bar, is what you actually get: roughly tickRate × speed, and negative when you're in reverse.

Who keeps the drawing loop spinning?

winit is event-driven: it sleeps until something happens. So how do we redraw continuously? At the end of every draw, src/app.rs calls request_redraw() — "wake me up to draw again". That would spin at 100% CPU, except for one elegant brake: the surface is configured in Fifo mode (chapter 12), which means "presenting a finished image waits for the monitor's next refresh". That wait is vsync. Free, perfectly-paced throttling — for the drawing only.

check yourself
You minimise the window. What happens to the simulation?

Nothing. It keeps ticking at 60 tps on its thread. Redraws stop (no RedrawRequested), so snapshots pile up in the slot and get overwritten — each new one simply replaces the last. Restore the window and you see the present, not a backlog.

Your monitor is 144 Hz and tickRate is 60. Roughly what fraction of frames get a fresh snapshot?

About 60/144 ≈ 42%. The other ~58% call try_recv(), get None, and redraw the shapes already sitting in the GPU buffer. That's not a waste — it's how the camera stays responsive at full refresh rate even when the world is slow.

You hit Space. What does the fps number do, and what does the tps number do?

fps doesn't move — the window is still redrawing at your refresh rate, still panning and zooming normally, just drawing an unchanging world. tps falls to 0, because tick() stops being called. If the two rates were coupled, pausing the world would freeze the camera too, and you could no longer look around a frozen scene — which is most of what pausing is for.

What stops the redraw loop from using 100% of a CPU core?

Vsync. Presenting in Fifo mode blocks until the monitor is ready, so the loop naturally runs at the refresh rate. (The simulation thread throttles itself differently — chapter 8.)

check yourself
Which object would you ask: "make me a bigger buffer, the particle count grew"?

The Device — it creates all resources. renderer.rs does exactly that in update_shapes, and then has to rebuild the bind group too, because the old one still points at the buffer that just went away.

Why do Surface and Adapter both come straight from the Instance?

They're independent facts about your machine: the Surface is about the window, the Adapter is about the GPU. They only meet later, when we ask "which adapters can draw to this surface" and then configure the surface using the chosen device.

06

main.rs + config/ — starting up

The shortest file in the project, and the only one the program starts in. Its whole job: turn on logging, read the config, build the event loop, hand control to App — then it never returns until you quit.

deep dive: every line

mod app; and friends — these eight lines are the project structure. Each one tells the compiler "compile that module too" (see the Rust box in chapter 4). Order doesn't matter.

env_logger::init(); — installs the logger. wgpu almost never panics on mistakes; it reports them through Rust's standard log system. No logger installed = errors go nowhere. You control it with an environment variable: RUST_LOG=warn cargo run.

let config = config::load(); — reads and parses the JSON. Note it can't fail: the worst case returns AppConfig::default() and prints why.

App::new(&config) — borrows the config for the app's whole life. This is the line that builds the particle cloud and starts the simulation thread; by the time run_app is called the world is already ticking.

Rust — the lifetime in App<'a>

App holds config: &'a AppConfig — a borrow, not a copy. The 'a is a lifetime parameter: it's the compiler's way of writing down "this App may not outlive the config it points at". Since config is a local in main and app is created after it and dropped before it, the rule holds and the compiler proves it. No reference counting, no copying, no risk of a dangling pointer.

event_loop.run_app(&mut app) — the point of no return. From here on winit owns this thread: it sleeps until the OS reports something, calls the matching method on app, and sleeps again. Forever, until something calls event_loop.exit() — which app.rs does on Esc or the window's ✕.

The config file

Here it is in full — every knob the program has:

The "ui" block is chapter 15's, and only fontPath needs a word here. It is an absolute path to a font file on your disk — the program does not search, does not ask the OS for "the system font", and ships no font of its own. Forward slashes are fine on Windows and save you escaping every backslash as \. Set it to null, delete it, or point it at a file that doesn't exist, and the loader falls through to a short list of fonts that ship with your OS — the details, and why that list looks the way it does, are in chapter 15.

Two more things to notice. "$schema" points at app-config.schema.json, which is what makes your editor autocomplete "Sunflower" and underline "Sunflowr". And the strategy values — "Uniform", { "Circle": { "radius": 20.0 } } — are Rust enums in disguise: serde's default encoding for an enum is either the bare variant name (if it carries no data) or a one-key object whose key is the variant name.

why though? — one bad key shouldn't cost you the file

The obvious way to read this file is serde_json::from_str::<AppConfig>(&text)? — one call, done. But then a single typo anywhere means nothing loads and you get one error message about one line. config/partial.rs takes the tedious road instead: walk the JSON object key by key, and when a key is missing or unparseable, print exactly which dotted path was bad and substitute that field's own default. You always get a running program, and the terminal tells you precisely what it ignored.

deep dive: how a section wires itself up

Every config struct implements one small trait, and the implementation is always the same three moves: warn about keys you don't recognise, take your own defaults, then read each key with leaf.

warn_unknown_keys exists because a typo'd key would otherwise be indistinguishable from a key you never set — both are silently absent. Now "initail": 40 prints config: ignoring unknown key `zoom.initail`.

The path string threaded through everything is just for those messages: it accumulates "zoom", then "zoom.initial", so an error names the exact line you need to fix.

One section does more than fetch values — config/simulation.rs guards a number the rest of the program divides by:

tick_period() computes 1.0 / tick_rate and hands it to Duration::from_secs_f32, which panics on a negative or NaN input. Catching it here means the simulation thread can treat its period as always sane.

Rust — traits as a shape, not a hierarchy

FromJsonObject is a trait: a named list of methods a type can promise to provide. section::<ZoomConfig>(…) works because ZoomConfig implements it. Note the declaration is pub trait FromJsonObject: Default — the : Default means "anything implementing this must also implement Default", which is what lets section fall back to T::default() without knowing anything else about T.

check yourself
You write "tickRate": "60" (a string, not a number). What happens?

leaf tries to deserialize a f32 from a JSON string, fails, prints config: `simulation.tickRate` is invalid (…); using default, and returns 60.0. The rest of the file — window, zoom, generation — loads completely normally.

You delete the whole "generation" block. What do you get?

section sees the key is missing and returns GenerationConfig::default(): 100 particles, uniform in a radius-1000 disc, random masses from 1 to 2000, random velocities, overlaps separated. No warning — an absent optional section is not an error.

app.rs — the switchboard

src/app.rs is the operator at the old telephone exchange: every event the OS sends arrives here, gets identified, and gets plugged through to the one module that handles it. It contains almost no logic of its own — deliberately.

The deal winit offers

winit says: "implement my ApplicationHandler interface — a resumed method and a window_event method — and I'll call them at the right times." Our whole file is filling in that form.

Construction: the world starts before the window does

Read the order carefully, because it's the one place the whole architecture is visible in four lines. Generation makes a Vec<Particle>. Scene::init borrows it to build the initial shape list (the renderer needs to know how big a buffer to allocate). Then the Vec is moved into a World, which is moved onto the simulation thread — and from that moment the main thread cannot touch a particle again except through try_recv.

Rust — move, and why that's the whole safety story here

World::new(particles) takes the Vec by value, so ownership moves into it; then spawn moves the World into a closure that runs on another thread. After those lines the name particles is unusable — the compiler will reject any attempt to read it. That's not a style rule, it's the data race being made impossible to write. Two threads can't accidentally share the particle list, because after the move only one of them has it.

The last field is the odd one out. FontFace::load reads a file off your disk and parses it — neither of which needs a window or a GPU, so it happens here, at startup, where a bad path prints its complaint before anything else has happened. It returns an Option: if no font could be read anywhere, the program does not stop, it just runs without an overlay. The font sits in that field doing nothing until resumed comes along with a GPU to turn it into a texture.

deep dive: resumed — booting the window

Five things worth pausing on:

1. The size is in logical pixels. On a monitor with 125% scaling, winit multiplies by 1.25 and makes a 1600×900 physical window. Everything after this line works in physical pixels.

2. The guard at the top. resumed can fire more than once on mobile platforms; the early return makes a second call harmless.

3. Arc::new(…).

Rust — Arc, or shared ownership

Rust's core rule: every value has exactly one owner, so the compiler always knows when to free it. But the window genuinely needs two owners: our App (to ask for redraws) and the GPU surface (which draws into it and must never outlive it). Arc — Atomically Reference Counted — is the escape hatch: a counter travels with the value, .clone() makes a new handle and bumps it, and the value is freed when it hits zero. You'll meet Arc again in chapter 8, doing the same job across a thread boundary.

4. Renderer::new(&ctx, &self.scene.shapes). The renderer is handed the initial shape list so it can size its storage buffer. That's the only reason Scene::init ran before the particles were moved away.

5. self.font.take().map(…). Two Options meeting. .take() pulls the FontFace out of the field and leaves None behind (the same move-out-of-a-borrow trick Drop uses in chapter 8). .map() then says "if there was one, build a Ui from it; if there wasn't, stay None". So gpu.ui ends up Option<Ui>, and every later use is an if let Some(ui) — the "no font" case is handled by the type system rather than by a flag someone has to remember to check.

The scale line is read from the window before the window is handed to the GPU context, because GpuContext::new takes the Arc by value. It's the OS scale factor — 1.0 on a plain monitor, 1.5 on a 150%-scaled one — and chapter 15 multiplies the configured font size by it so text is the same physical size on any screen.

Rust — async, in one paragraph

An async fn doesn't run when called — it returns a plan (a "future") that must be driven by an executor. wgpu makes GPU setup async because on some platforms (the web) you're not allowed to block. On desktop we're happy to wait, and that's the entire job of pollster::block_on.

deep dive: window_event — the actual switchboard

This used to be one long match with the whole redraw inlined into one arm. It got split into three because of a Rust borrowing rule, and the rule is worth understanding — you will hit it.

Rust — why the handler had to be split up

The old version opened with let Some(gpu) = &mut self.gpu else { return }; and then used gpu, self.simulation and self.scene in the same arm. That compiles, because the borrow checker tracks borrows per field inside a single function body: three different fields, three independent borrows, no conflict.

The moment you want to call a method — self.status(), say — that stops working. A method takes &self or &mut self, which borrows the whole struct, and the compiler can no longer see that it only touches fields you aren't already holding. So the redraw path moves wholesale into fn redraw(&mut self), which re-borrows self.gpu on its own terms, and the leftover mouse/resize arms move into on_window_event for the same reason. Same code, same behaviour; the split exists purely so each borrow of self.gpu lives and dies inside one function.

Rust — match and patterns

match is a switch statement with superpowers. Each arm is a pattern that can simultaneously test the shape of a value and pull data out of it. The keyboard arm matches "a KeyboardInput event whose physical key is some known code, in the Pressed state" — and binds that code and the repeat flag to names in one go. .. means "I don't care about the other fields". The compiler checks you handled every variant, which is what the final catch-all satisfies.

Two details in that pattern do real work:

state: ElementState::Pressed filters out key releases. Without it every key would fire twice — once down, once up — and Space would pause and instantly unpause.

physical_key: PhysicalKey::Code(code) asks for the key's position on the keyboard, not the character it would type. winit offers both: logical_key is what the layout says (on a French AZERTY keyboard the key where QWERTY has Q produces "a"), while physical_key is derived from the hardware scancode and always calls that key KeyA. For controls you want physical, so Space and the arrows work identically on every layout on earth.

a trap, found the hard way

Because physical_key comes from the scancode, an arrow key must carry its E0 prefix to be recognised as an arrow. This matters if you ever script the program: injecting VK_RIGHT with the Windows keybd_event API without the extended-key flag delivers scancode 0x4D, which is the numpad 6 key sharing that code — and winit faithfully reports KeyCode::Numpad6. The app looks broken; it isn't. Real keyboards send E0 4D and arrive as ArrowRight.

on_key — four keys, and one of them means two things

Every branch is one call into SimulationHandle. app.rs decides which question to ask and knows nothing about how it's answered — no speed value, no tick counter, no atomics live in this file. Chapter 8 has all of that.

if !repeat is the whole design of the space bar. Hold a key down and the OS sends a stream of Pressed events, the first genuine and the rest auto-repeats; KeyEvent flags which is which. For the arrows that stream is a feature — hold → and the speed winds up smoothly, one rung per repeat. For a toggle it's a disaster: holding Space for a second would flip pause about thirty times and land wherever the timing left it. So the space arm carries a match guard.

Rust — match guards

KeyCode::Space if !repeat => is an arm with an extra condition bolted on. The pattern must match and the guard must be true, otherwise the arm is skipped and matching continues downward. Here that means a repeated space falls all the way through to _ => {} and is silently discarded — exactly what you want. Note that guards are invisible to the compiler's exhaustiveness check: a match made only of guarded arms still needs a catch-all, because the compiler cannot prove your conditions ever hold.

The arrows are modal, and that is a deliberate piece of interface design rather than an accident. Running, "left and right" is a natural way to say slower and faster. Paused, speed is meaningless — there's nothing to be fast about — and the obvious thing to want is to nudge the frozen world back and forth a bit. Same keys, and the overlay's controls panel rewrites its own description of them every frame, so you're never guessing which mode you're in (chapter 15).

redraw — the whole frame in one function

Five steps, and every one of them is optional except the last:

  • The snapshot is optional. if let Some(particles) = … — when the simulation hasn't ticked since the last frame we skip the sync and the upload entirely. The GPU still holds the previous shapes, so drawing them again costs nothing extra. While paused, this is every frame.
  • The rate sample is optional. sample returns true only once a second, which is when the title bar gets rewritten. Setting a window title is a call into the OS; you don't want it 144 times a second.
  • The overlay is optional twice over — once because there might be no font at all, and again because prepare itself may produce nothing if you switched both panels off in the config.
  • The frame is optional too. If acquire_frame returned None, the surface was mid-repair (chapter 12) and we skip one frame — at 144 fps nobody notices.
  • The redraw request is unconditional. It's the last line no matter what happened above, because if it were ever skipped the loop would simply stop and the window would freeze.

The block in the middle is the part that changed when the overlay arrived. The scene renderer used to own the whole frame: it created the encoder, recorded its pass, submitted, and presented. Now it records into an encoder handed to it, and this function owns the frame instead:

GPU concept — why two passes and not one

You cannot draw both in one pass, because a pass is compiled against exactly one pipeline configuration at a time and these two disagree about almost everything: different shaders, different vertex maths, different bind group layouts, different blending. Switching pipelines mid-pass is legal but you'd still be issuing two draws with two set_pipeline calls, so you have gained nothing over two passes and lost the ability to give each one its own load/store behaviour.

Two passes in one encoder is also nearly free. A pass boundary on a desktop GPU costs a state flush, not a round-trip; the whole encoder is still one submission. On a mobile tile-based GPU the calculus differs, which is why this pattern is worth knowing rather than assuming.

Rust — the Status struct, and why it's a copy

ui.prepare could have taken &self.simulation and &self.camera and read what it needed. Instead it takes a flat Status built on the spot: eight plain numbers, no references, no lifetimes. That costs a struct copy of about 40 bytes per frame and buys two things. First, the ui/ module never has to use crate::view::Camera, so it stays a module about text rather than a module about this particular program. Second, it dodges the borrow problem from the box above: gpu.ui is mutably borrowed while self.camera and self.simulation are read, and disjoint field borrows only work when the compiler can see the individual fields — which it can here, and could not through a method call.

The title bar is a measurement instrument

Frames are counted here; ticks are read from the simulation handle. Once a second the difference becomes two numbers. It's twenty lines of debug output, and it's the fastest way to confirm that the two clocks really are independent: set tickRate to 15, or to 240, and watch the second number move while the first one doesn't.

Two small changes arrived with the playback controls, and both are load-bearing.

It now keeps the last values instead of only returning them. The old version returned Option<(f32, f32)> — fine when the only consumer was a title bar that also only wanted updating once a second. But the overlay redraws every frame and needs an fps number on all of them, so the meter stores fps and tps as fields and sample returns a plain bool meaning "these are new". The numbers you read on screen are therefore up to one second old, which is the point: an instantaneous frame rate is an unreadable flicker.

ticks became i64. This one is not cosmetic. Run the world backwards and the tick counter decreases, so ticks - self.ticks is negative. As u64 that subtraction underflows — in a release build it wraps silently to something around 18 quintillion, and the title bar would report a tick rate with nineteen digits in it. Signed arithmetic simply gives you -80 tps, which is both correct and genuinely useful information.

Rust — the two faces of integer overflow

5u64 - 10u64 is not "-5" and it is not undefined behaviour. In a debug build Rust checks every arithmetic operation and panics with "attempt to subtract with overflow". In a release build those checks are compiled out for speed and the value wraps around to u64::MAX - 4. So this exact bug would have crashed loudly under cargo run and produced silent nonsense under cargo run --release — which is the worst possible way to find out. Choosing the signed type is how you stop having the conversation.

check yourself
Why is request_redraw() called inside the redraw handler itself?

That's what makes rendering continuous: each frame schedules the next one. Vsync keeps this from spinning wildly — presenting blocks until the monitor wants a new image. Note it sits outside the acquire_frame block: a frame we failed to acquire must still schedule the next attempt, or one hiccup would freeze the window forever.

You swap the two draw calls in redraw so the ui records first. What do you see?

Nothing but particles. The ui pass would draw its panels, and then the scene pass would begin with LoadOp::Clear(BLACK) and wipe the entire target before drawing the world over the top. The overlay would be computed, uploaded and rasterised every frame, and then thrown away microseconds later. A perfect example of why "the order in the encoder is the order on screen" is worth saying out loud.

Holding → winds the speed up smoothly. Why doesn't holding Space do anything after the first press?

The match guard if !repeat. The OS auto-repeat stream is flagged, and only the first, genuine press gets past the guard; the rest fall through to the catch-all arm. Without it, a one-second hold would toggle pause roughly thirty times.

The simulation thread panics. What does the window do?

It keeps running and keeps drawing the last snapshot forever. try_recv locks a poisoned mutex and recovers with PoisonError::into_inner, sees fresh == false and returns None; tick() stops advancing, so the title bar reads … / 0 tps. Frozen physics, live camera — and the panic message is already on stderr.

08

simulation/ — the world, on its own clock

Three files. particle.rs is the atom, world.rs is the state and the one function that changes it, and runner.rs is the thread plus the hand-off. None of them import winit or wgpu — the simulation could run headless tomorrow.

The atom

Twenty bytes: two floats of position, one of mass, two of velocity. new is a validating constructor — it takes a Particle and returns one with the mass clamped non-negative, so a bad config value can't produce a NaN radius later.

why though? — radius = √mass / 2

Mass is treated as area, not diameter. Four times the mass draws twice as wide, which is what your eye expects from a 2D disc of uniform density, and it keeps a 2000-unit particle from swallowing the screen next to a 1-unit one. The important part is that this rule lives in one function: the renderer sizes discs with it (chapter 13) and the overlap pass decides how much room each particle needs with it (chapter 9). Put the formula in both places and they will eventually disagree, and you'll get particles that visually overlap while the packer insists they don't.

The world, and its one tick

tick is the placeholder from chapter 1, and the shape of it is the part to keep. Note what it does not do: it never calls Instant::now(). Time in this world is ticks × delta and nothing else, which is why the same config always produces the same run.

The cosine turns a linear elapsed into a value that eases 0→1→0 every 4 seconds — smooth at the turning points instead of a hard corner. Mass 1 at t=0, 500 at t=1s, 1000 at t=2s, back to 1 at t=4s. Chapter 10 turns those numbers into colours.

Three details in there are entirely about running the world backwards, and none of them cost anything when you aren't:

  • delta is allowed to be negative. Nothing in the function assumes otherwise: adding a negative number to elapsed walks time back, and cos is perfectly happy with a negative argument (it's an even function — cos(-x) == cos(x)).
  • ticks is i64, not u64, and moves by ±1 rather than always up. It is a position in the world's history, not a count of work done, so it has to be able to go down. Tick −30 is a perfectly legal place to be: it means you stepped thirty ticks back past the start.
  • A delta of exactly zero returns early. Otherwise the sign test would have to invent an answer for "which way did we just go?", and the tick counter would drift upward every time the world was told to stand still.
why though? — reverse is honest here, and won't stay that way

This particular tick is exactly reversible, and it's worth knowing why, because it's a property you are about to lose. The entire state of the world is a pure function of elapsed — mass is just oscillating_mass(elapsed), recomputed from scratch every tick. Step back 10 ticks and elapsed returns to a number it genuinely held before, so the state is bit-for-bit the state you were in. Nothing is being undone; it is being recomputed.

Real gravity is not like that. Once tick accumulates — velocity += acceleration × delta, position += velocity × delta — running it with a negative delta is only approximately an inverse. A symplectic integrator like leapfrog is time-reversible in exact arithmetic, so you'd get close, but floating-point rounding is not reversible and the error compounds every step. Add anything dissipative (collisions, drag, merging particles) and reverse stops being meaningful at all — you cannot un-merge two bodies by negating dt. The honest long-term answer for scrubbing backwards is to record snapshots and replay them, not to re-integrate. Chapter 17's hole is bigger than it looks.

The thread

runner.rs is the interesting file. It has two jobs that pull in opposite directions: hit the tick rate accurately and hand results to another thread without ever making it wait.

Job one: hitting the rate

Ignore the two elided branches for now — they're the playback controls and they get their own section below. What matters here is the pacing, and the two lines that carry the speed dial into it.

base_period is what tickRate asked for: 16.67 ms at 60 tps. period is that divided by the magnitude of the speed — at 2x the thread aims for a deadline every 8.3 ms, at 10x every 1.67 ms. signed_delta is the untouched delta carrying the speed's sign. Between them they say the thing worth memorising: speed changes how often ticks happen and which way they point, never how big they are. Wind the speed to 10x and you have not changed the physics by one bit; you have asked for the same steps, sooner.

The line that matters most is next_tick += period. The naive version — next_tick = Instant::now() + period — would let every microsecond of lateness accumulate, and after a minute you'd be running measurably slow. Adding a fixed period to the previous deadline means a tick that runs 3 ms long simply leaves 3 ms less sleep before the next one; the average stays exact.

Rust — dividing a Duration

Duration is not a number, it's a struct of whole seconds plus nanoseconds, so you can't write base_period / speed. div_f32 is the provided method for exactly this, and it does the right thing at the extremes: 16.67 ms divided by 10 is 1.667 ms, no truncation to whole milliseconds. Dividing by zero would produce an infinite or NaN duration and panic — which is precisely why the branch above returns early when the speed is exactly zero, before this line can run.

max_catch_up is the escape hatch for when that isn't possible. If the machine genuinely can't tick fast enough, running the backlog would make each pass longer, which makes the backlog bigger — the classic spiral. So after at most five back-to-back ticks the loop gives up on the debt and re-bases the clock. The simulation runs slower than real time, deliberately and visibly (the title bar's tps number drops), instead of locking up.

Job two: sleeping accurately

the thing that bites everyone on Windows

thread::sleep(16.6ms) does not wake you up in 16.6 ms. It wakes you up in at least that, rounded up to whatever the OS timer granularity is — historically 15.6 ms on Windows, which would make 60 Hz pacing a coin flip. Modern Rust uses high-resolution waitable timers there, so it's now closer to half a millisecond, but "close to" isn't "exactly". Sleeping to 500 µs short of the deadline and burning the rest in a spin_loop costs about 3% of one core and makes the pacing boringly reliable.

The MAX_SLEEP cap is unrelated: it keeps each individual sleep under 50 ms so that a slow tick rate (say tickRate: 0.5) doesn't make quitting the program take two seconds. The loop re-checks the running flag after every chunk — and, since the playback controls arrived, the paused flag too. Same reasoning, different button: at tickRate: 0.5 the thread is asleep for up to two seconds at a stretch, and Space that only takes effect when the nap happens to end feels broken. Checking one extra atomic per 50 ms chunk is free, and it makes pausing feel instantaneous at any tick rate.

Job three: the hand-off

Now the interesting bit. The main thread needs to read particles; the simulation thread needs to write them. The obvious answer — wrap the Vec in a Mutex and let the renderer lock it — is wrong: the renderer would hold that lock for the whole duration of a GPU upload, and the simulation would stall behind it (or vice versa). What we want is for neither side to ever wait for the other.

Rust — mem::swap, and why it's free

A Vec is three machine words on the stack — a pointer to the heap, a length, a capacity — and the actual elements live somewhere else. mem::swap(&mut a, &mut b) exchanges those three words. The million particles behind the pointer don't move an inch; they just belong to a different variable now. This is why "swap instead of copy" is such a common Rust pattern for hand-offs, and why holding a lock across one is harmless.

The fresh flag is what makes it drop-oldest rather than a queue. The writer sets it on every publish; the reader clears it on every receive. Publish twice between two frames and the first snapshot is simply overwritten — it was never wanted. Read twice between two ticks and the second read returns None.

Rust — a poisoned Mutex

slot.lock() returns a Result, not the guard directly. If a thread ever panicked while holding this lock, Rust marks it "poisoned" and every later lock() returns Err — the standard library assuming the protected data might be half-updated. unwrap_or_else(PoisonError::into_inner) says "give me the data anyway". That's the right call here, and only because of what's inside: a Vec, a counter and a bool, all fully written before the guard is dropped. There is no half-state to observe.

Shutting down

Nothing in app.rs calls this. It happens because App is a local variable in main, and when run_app returns, App is dropped, which drops its SimulationHandle field, which flips the atomic flag and waits for the thread. Option<JoinHandle> rather than a plain JoinHandle because join consumes the handle by value and drop only has a &mut — .take() is how you move a value out of a struct you're only borrowing.

Playback: pause, speed, and running time backwards

Everything above describes a thread that starts, ticks forever at one rate, and stops. The playback controls add three questions the window thread needs to be able to ask it, at any moment, without ever waiting:

  1. "Stop ticking." / "Start again."
  2. "Tick this much faster, or this much slower, or backwards."
  3. "You're paused — take exactly ten steps that way."

Three questions crossing a thread boundary. The obvious tool is a channel, and the second-most obvious is another Mutex. Both are wrong here for the same reason: the window thread is on a 6 ms budget and must never block waiting for a tick that's halfway through 100,000 particles. So all three are atomics — single machine words that can be read and written from either side, with no lock, no waiting, and no way to observe a half-written value.

This struct is also a tidying-up. Before, the handle carried an Arc<AtomicBool> and an Arc<Mutex<Slot>> as separate fields, and the thread closure captured a clone of each. Wrapping the lot in one Shared means one Arc, one clone, and one place to look when you want to know what the two threads can see of each other. That list is now five items long, and it is the complete list.

Rust — there is no AtomicF32

The standard library gives you atomic integers and AtomicBool, and that's it — no atomic floats, because hardware atomics are defined over integer words. The standard workaround is what speed does: store the float's bit pattern in an AtomicU32 with f32::to_bits(), and reconstitute it with f32::from_bits() on the way out. That is not a conversion and loses nothing: a Rust f32 is already exactly 32 bits (IEEE-754 single precision), and those two functions just reinterpret the same bits with a different type. It's the same trick as bytemuck in chapter 13, at the scale of one number.

Rust — Ordering::Relaxed, and why it's enough

Every atomic operation makes you name an Ordering, and the honest short answer is "this is the hardest topic in concurrent programming, and you almost always want Relaxed or SeqCst". Relaxed guarantees the one variable is never torn — you always read a value somebody actually wrote, never a mix of two — and guarantees nothing about the order of other memory around it.

That is exactly the right level here, because none of these five atomics is being used to publish other data. They are self-contained facts: a bool that means paused, a bit pattern that means speed. The one place where ordering genuinely matters — "the particle buffer I just swapped in is fully written before you read it" — is handled by the Mutex, which provides that guarantee as part of locking. Reach for a stronger ordering the moment an atomic starts meaning "the thing over there is ready now".

The speed ladder, and the reason it has a zero in the middle

The requirement sounds simple: each press changes the speed by a factor of 1.1, it must be able to run backwards, and it clamps at ±10. Try to build that with a plain multiplier and you walk straight into a wall.

Press "slower" from 1.0 and you get 0.909. Again: 0.826. Again: 0.751. Keep going and the sequence gets closer and closer to zero and never arrives, because a positive number divided by 1.1 is still positive, always. Multiplication cannot change a sign. There is no number of presses that gets you from +1.0 to −1.0, and no number of presses that gets you to a full stop either.

So the rungs are numbered with an integer, and the number zero is given a meaning of its own:

Read value carefully, because it's four lines doing three things.

self.index.signum() collapses the index to −1, 0 or +1 — "which side of the bridge are we on". Zero gets its own arm and returns a literal 0.0; nothing else in the function has to think about it again.

self.index.abs() - 1 is the off-by-one that makes index 1 mean "normal speed": rung 1 is FACTOR to the power zero, which is 1.0. Without the minus one, +1x would be unreachable and the slowest forward speed would be 1.1x.

.min(LIMIT) clamps the magnitude before the sign is applied, which is why one expression handles both ends of the ladder. Clamping after multiplying by the sign would need .clamp(-LIMIT, LIMIT), which is fine too — but this way the sign is applied exactly once, at the end, and the reverse half of the ladder is guaranteed to be a mirror image of the forward half rather than a second set of arithmetic that might not agree.

Rust — a const block that runs a loop

MAX_INDEX is not a number someone worked out on a calculator and typed in; it's a while loop that the compiler runs at compile time and bakes into the binary as a literal. Rust's const evaluator handles loops, conditionals and — since 1.82 — floating-point arithmetic, so this is ordinary code that simply happens never to execute at runtime.

Why bother? Because it keeps FACTOR and LIMIT the only two knobs. Change FACTOR to 1.5 and the ladder re-derives its own length; write 26 by hand and you have planted a bug that only appears the day someone edits a constant fifteen lines up. The generated answer with today's numbers: 1.124 = 9.85, still under the limit, so the loop keeps going; 1.125 = 10.83, which trips it, giving MAX_INDEX = 26. That last rung is clamped down to exactly 10.0, so ±10 is genuinely reachable rather than something the ladder merely approaches. 53 rungs in total: 26 each way, plus the stop.

why though? — where the ladder doesn't go

There is no slow motion. The slowest non-zero speed on this ladder is 1.0x in either direction, because every rung away from the stop multiplies the magnitude. If you wanted 0.5x or 0.1x you'd extend the ladder downward — give index 1 a magnitude of FACTOR to the power of some negative offset, or simply let the exponent go below zero — and then LIMIT would need a companion minimum so the ladder still terminates at the bottom. It isn't there because for this program "slower than real time" is what tickRate is for, and stepping while paused covers the "I want to look at one moment" case more precisely than any slow-motion setting would.

The two branches at the top of the loop

Two ways of not ticking, kept separate on purpose. Paused is a mode you entered with Space and which enables stepping. Speed zero is just a rung of the ladder you happened to land on while walking through it toward reverse. They look identical on screen for a moment — nothing moves — but only the first one lets the arrows step, and the overlay labels them differently (PAUSED versus a speed reading of halted), so you always know which one you're in.

next_tick = Instant::now() + base_period is the important line in both branches, and it is easy to leave out. Remember from Job one that next_tick is a deadline that marches forward by a fixed period, and that the loop runs ticks while now is past it. Pause for ten seconds without re-basing it and you come back to a deadline six hundred ticks in the past — so the instant you unpause, the catch-up loop fires its entire budget, the world jumps five ticks forward, and it keeps doing that every pass until the debt is paid. Re-basing on every idle pass states the policy plainly: time you spent paused is not time the simulation owes you.

why though? — a 2 ms poll instead of a proper wait

IDLE_POLL is Duration::from_millis(2), so a paused thread wakes 500 times a second, checks two atomics, finds nothing to do and goes back to sleep. The textbook answer is a Condvar: the thread blocks properly and the window thread wakes it exactly when something changes, burning zero cycles in between.

The polling version is here because it's honest about its cost and keeps the loop one shape. 500 wake-ups a second is well under a tenth of a percent of one core — substantially less than the spin_loop in sleep_until is burning while the thread is running. A Condvar would mean a second synchronisation primitive, a predicate to re-check on every spurious wake-up, and a careful story about what happens if the flag flips between the check and the wait. That's the right trade at a thousand paused threads; at one, it's ceremony.

Stepping: draining, not reading

Those two functions are a tiny, complete lesson in atomics, so let's take it slowly.

fetch_add, not store. The window thread doesn't say "the pending step count is now 10", it says "add 10 to whatever is there". Press → three times inside one 2 ms nap and the counter holds 30 and the world moves 30 ticks. With store the first two presses would be silently overwritten — you'd press three times and the world would move ten. And because the value is signed, a left press and a right press in the same window cancel out to zero, which is precisely the right answer.

swap(0), not load then store(0). This is the same bug wearing a different hat. swap reads the old value and writes the new one as a single indivisible operation; nothing can happen in between because there is no "in between". Split it into a load and a store and you open a window — a few nanoseconds, but a real one — in which a key press can land after the read and be wiped out by the write. Every arrow press that ever went missing in a program like this went missing exactly there.

Rust — signum, unsigned_abs, and the i32::MIN trap

steps.signum() gives −1, 0 or +1; multiplying delta by it as an f32 is how one loop serves both directions. steps.unsigned_abs() then gives the magnitude as a u32 for the loop count.

That last method looks like needless pedantry over .abs(), and isn't. i32 spans −2147483648 to +2147483647 — one more negative value than positive — so i32::MIN.abs() has no representable answer and panics in debug, wraps in release. unsigned_abs returns u32, which has room for it, and cannot fail for any input. You get there by holding an arrow key for about four years, so this is not a bug anyone would hit — but it costs exactly the same to write the version that has no edge case at all.

Why stepping only works while paused. Nothing technically prevents draining steps in the running branch too. It's left out because the running branch's whole job is honouring a deadline, and injecting ten unscheduled ticks into it means either those ticks are counted against the budget (so your step gets swallowed by the pacing) or they aren't (so the rate you asked for is now a lie). Pausing first makes the question disappear: there is no clock to fight, and each press is exactly ten ticks and nothing else. That is also why app.rs asks is_paused() before deciding what an arrow means.

Who owns the ladder

Notice where Speed lives: on the handle, which is a main-thread object, not in Shared. The simulation thread never sees an index and has never heard of a ladder — it reads one f32 and multiplies. The rung you're standing on is interface state, in the same category as which panel the overlay is drawing; the number is the only part that is physics.

That split is worth copying. It means you can redesign the ladder entirely — add slow motion, change the factor, make it linear, replace it with a list of presets — by editing one small file, and the thread that runs the world does not change by a character.

toggle_pause takes &self, not &mut self, which looks wrong for something that obviously mutates. It's correct: the thing being changed lives behind an atomic, and atomics provide interior mutability — they're built to be modified through a shared reference, because being modified from several places at once is their entire purpose. faster does need &mut self, because it also moves the plain Speed field, which is an ordinary value with ordinary rules.

the read-modify-write in toggle_pause

toggle_pause loads the flag, inverts it, and stores it back — three steps, not one, so two threads calling it simultaneously could both read false and both write true, losing a toggle. The airtight version is fetch_xor(true, Ordering::Relaxed), which flips it indivisibly.

It's safe as written because exactly one thread ever calls it: the window thread, from inside a keyboard event, and winit delivers those one at a time. Worth knowing anyway — the day this gets called from a second place (a config hot-reload, a network command, a scripting hook) the bug appears, and it'll be the kind that happens once an hour and never in a debugger.

check yourself
Why does the copy in publish happen before the lock is taken, not after?

Because that copy is the only expensive thing in the whole hand-off — O(number of particles). Doing it inside the lock would make the main thread wait for it at exactly the wrong moment. Outside the lock, the main thread's worst case is "wait for three word-sized writes".

You set maxCatchUpTicks to 1000. What have you built?

A death spiral, if the machine ever falls behind. With no cap, a slow patch produces a backlog, running the backlog takes longer than real time, which produces a bigger backlog. The cap converts "hang forever" into "run in slow motion and show it in the title bar".

Why can't the speed just be a float you multiply and divide by 1.1?

Because it could never reach reverse, or a stop. Dividing a positive number by 1.1 gives a smaller positive number, forever — the sequence converges on zero and never touches it, and multiplication can't flip a sign. Numbering the rungs with an integer and defining index 0 as "stopped" gives you a value that is the crossing point, so the ladder walks continuously from +10x to −10x.

You replace steps.swap(0) with steps.load() followed by steps.store(0). What breaks, and how often?

Arrow presses go missing, rarely and unreproducibly. Between the load and the store there's a gap of a few nanoseconds; a key press landing in it is added to a value that is about to be overwritten with zero. You'd hit it perhaps once in a very long session, conclude your keyboard is flaky, and never find it. swap has no gap because it is one instruction.

You delete the next_tick = Instant::now() + base_period line from the paused branch. What does unpausing feel like?

Like a jump. next_tick is still the deadline from the moment you paused, so after a ten-second pause it's six hundred ticks in the past. The instant you resume, the catch-up loop runs its full budget of five ticks, publishes, finds itself still behind, runs five more — and the world sprints forward until the debt is paid or the re-basing safety net at the bottom of the loop catches it. Pausing would cost you simulated time.

Where would gravity actually go?

Inside World::tick, replacing the mass oscillation: compute pairwise forces, update velocity, then position += velocity * delta. Nothing else in this chapter changes — the thread, the pacing and the hand-off don't care what the tick does.

generation/ — building the cloud

This module runs exactly once, before the window exists, and produces the Vec<Particle> the simulation will own forever. It's the only place in the codebase with randomness in it, and the only place with a real algorithm rather than plumbing.

Three phases, and the order is load-bearing. Positions and masses first, because the overlap pass needs to know how much room each particle takes up — and that comes from mass. Separation second. Velocities last, because two of the velocity strategies are functions of position: Orbital gives each particle a velocity perpendicular to its radius, Radial gives it one pointing straight out. Sample those before separation and every particle that got nudged would be orbiting a point it no longer sits on.

Phase 1: sampling

Every position strategy produces points on the unit disc — a circle of radius 1 at the origin — and Area::from_unit_disc then stretches that disc into whatever shape the config asked for. One sampler, any ellipse.

deep dive: the sqrt that stops the clump

The obvious version is let r = rng.random::<f32>(); — pick a random angle, pick a random radius. It looks right and it is wrong: it puts far too many points near the centre.

Here's why. The area of a thin ring at radius r grows with r — the ring at r=0.9 has nine times the area of the ring at r=0.1, so it deserves nine times the points. Picking r uniformly gives every ring the same number regardless of size, so the small inner rings end up dense. Taking the square root of a uniform value biases it outward by exactly the right amount: the fraction of points landing inside radius r becomes r², which is exactly the fraction of the area inside radius r.

The same reasoning is why Sunflower uses ((i + 0.5) / amount).sqrt() for its radii, and why Ring interpolates between squared fractions: (inner² + u × (1 − inner²)).sqrt().

Rust — &mut impl Rng

Every sampler takes rng: &mut impl Rng rather than reaching for a global. impl Rng in argument position means "any type that implements the Rng trait, decided at compile time" — no vtable, no indirection, fully inlined. The &mut is because generating a number advances the generator's internal state; two functions sharing one &mut can't accidentally produce the same stream. Passing the generator explicitly is also what would make this whole module seedable and reproducible in one line.

Phase 2: making them not overlap

Sample 300 particles into a disc and a good number of them will be sitting on top of each other — overlapping by up to ten world units in the measurements below. Two families of fix exist:

  • Rejection sampling — draw a candidate, check it against everything placed so far, throw it away and redraw if it collides. Statistically pure, but it distorts Ring and Clusters (rejections concentrate where there's space), it can't be applied to the deterministic Sunflower at all, and it degrades badly as the space fills up.
  • Relaxation — sample everything wherever the strategy wants, then repeatedly push intersecting pairs apart until nobody intersects. Works with every strategy, always terminates, and preserves the shape of whatever was sampled because it only ever nudges.

This project does relaxation.

The inner loop, and the two decisions in it

Decision one: measure everything, then move everything. The alternative — move each particle the moment you find an overlap — is faster to converge but makes the result depend on array order, which means the same config produces subtly different clouds depending on nothing meaningful.

Decision two: divide by the contact count. A particle wedged inside a clump might be intersecting eight neighbours. Each one contributes a "get away from me" vector; adding all eight and applying the sum would fire it across the map, and then the clump would collapse back and do it again next pass. Averaging asks it to satisfy its neighbours on balance, which converges instead of oscillating. RELAXATION = 1.4 then pushes slightly beyond the average, because pure averaging undershoots.

Three details worth naming:

  • distance_sq >= wanted * wanted — comparing squared distances avoids a square root for every pair that isn't touching, which is most of them.
  • Two particles at exactly the same point have no direction to separate along; dividing by zero would give NaN and poison the whole cloud. They get fanned out along a per-index golden angle instead, so a pile of coincident particles opens into a rosette rather than all shooting the same way.
  • The correction is split by mass, so a 2000-unit particle barely budges while a 1-unit one does the travelling. Physically arbitrary, visually right — big things look like they hold their ground.

Not comparing everything to everything

Checking every pair is O(n²): fine for 100 particles, 2.5 billion comparisons for 50,000—per pass, and there are up to 128 passes. So neighbours come from a uniform grid.

Two constraints, and the larger wins. Cells must be at least contact wide — the largest distance at which any two particles could possibly touch — because that is exactly what guarantees an overlapping pair lands in the 3×3 block of cells around either of them. Make cells smaller and the search silently misses pairs. Beyond that floor, cells are sized so there's roughly one per particle: on a thinly-spread cloud that stops the grid from being a million mostly-empty buckets.

Rust — float to integer casts

cell_of does (x.max(0.0) as usize).min(self.columns - 1) on a computed float. Two hazards are handled by the language rather than by us: f32::max returns the other operand when one is NaN, so a NaN position folds to cell 0 instead of a garbage index; and since Rust 1.45 a float→integer as cast saturates rather than wrapping, so an absurd coordinate clamps to usize::MAX and then gets .min()'d into range. No panic, no out-of-bounds.

Knowing when to stop

accumulate_pushes returns the depth of the worst intersection it found, and the loop breaks as soon as that's under a tolerance of one-thousandth of the biggest particle's radius. Because the measurement happens before anything moves, that's a real guarantee about the result, not a hope. In practice the uniform case converges in well under 128 passes and the loop exits early; a dense cluster case needs a few hundred.

color/ — mass, in colour

Three small files that know nothing about particles, physics or GPUs. They answer one question — "given a number and a list of colour stops, what colour is it?" — and the answer is more interesting than it sounds.

A colour is four floats from 0 to 1 — red, green, blue, alpha — because that is exactly what the shader wants and what WGSL's vec4<f32> is. Not 0–255, not a struct.

Why blending in RGB looks wrong

The naive way to blend two colours is to average each channel. Try it with yellow [1, 1, 0] and red [1, 0, 0] and you get [1, 0.5, 0], which is orange — fine. Now try blue [0,0,1] and yellow [1,1,0]: you get [0.5, 0.5, 0.5], a dead grey. Halfway between two vivid colours should not be mud.

So mix converts both ends into HSL — hue, saturation, lightness — interpolates there, and converts back. Hue is an angle around a colour wheel, so blending it walks around the wheel through the vivid colours instead of cutting across the grey middle.

Two subtleties, both of which are bugs if you leave them out:

Grey has no hue. White, black and every grey convert to HSL with saturation 0 — and a hue of nothing in particular (the conversion returns 0, i.e. red, arbitrarily). Blend white to yellow naively and you'd travel from "red with no saturation" to "yellow with full saturation", swinging through pink on the way. The two lines that swap in the other end's hue fix it: a colourless colour borrows the hue it's heading for, so white→yellow just fades saturation up and lightness down. It stays in the yellow family the whole way.

Hue is circular. Going from hue 0.9 to hue 0.1 the short way is +0.2, not −0.8. The hue_step wrapping picks the shorter arc, and rem_euclid(1.0) at the end brings the result back into 0..1. Without it, some blends take the scenic route through every colour in the spectrum.

The ramp

partition_point is a binary search: it returns how many stops have a threshold at or below the value, which is exactly the index of the stop above it. From there, upper - 1 is the stop below, the two thresholds give a 0..1 position between them, and mix does the rest. Below the first stop and above the last, the ramp flattens out rather than extrapolating into nonsense.

Rust — const fn and 'static

pub const fn new means this constructor can run at compile time, and &'static [(f32, ColorRGBA)] means the stop list lives in the binary for the whole program. Together they let chapter 13 write const MASS_RAMP: ColorRamp = ColorRamp::new(&[…]); — a global with zero runtime construction cost and no lazy-initialisation machinery.

view/ — camera and mouse

Two files with no winit types in one and no wgpu types in either. camera.rs is pure math; controls.rs translates mouse events into calls on it.

The camera is three numbers

pan is where the world's origin sits on screen, in pixels from the window centre, +y up. zoom is pixels per world unit. The last three are limits copied out of the config once at construction. And the entire world→screen mapping — the one formula this whole codebase revolves around — is:

screen_px = world × zoom + pan

With the shipped config ("initial": 10.0), a particle of mass 200 has radius √200 / 2 ≈ 7.1 world units, so it draws about 141 pixels across. Mass 1 draws 10 pixels across. That's the pulse you see in fig. 0.

why though? — the no-scaling trick

"Resizing must not scale or move the scene." Look at the formula: the window's size appears nowhere in it. World units become pixels using only zoom and pan. So when the window changes, nothing about the scene's pixel size or its position relative to the window centre can change — the resize only changes how many pixels exist around the centre for the world to show through. The invariant isn't enforced by careful code; it's baked into the choice of coordinate system.

Panning: embarrassingly simple

The mouse moved 30 px right → add 30 to pan[0] → every world point lands 30 px further right. The scene sticks to your cursor 1:1 at any zoom, because pan is applied after the zoom multiply.

Zooming: exponential, and anchored under your cursor

deep dive: why multiply, and where that pan formula comes from

Why zoom_step.powf(lines) instead of adding? One wheel notch multiplies zoom by 1.1. Multiplying feels identical at every scale: +10% is a visible step whether you're at zoom 4 or zoom 4000. If we added, say, 50 per notch, zooming would crawl when far out and explode when close in. The clamp to min/max just stops you scrolling into oblivion.

The anchor formula, with actual numbers. The rule we want: the world point currently under your cursor stays under your cursor while everything grows around it. Say zoom = 10, pan = [0,0], and your cursor sits 100 px right of centre. The world point under it is w = (100 − 0) / 10 = 10. Scroll one notch in: new_zoom = 11, so k = 1.1.

If we changed only zoom, that world point would land at 10 × 11 = 110 px — it slid 10 px away from your cursor. To pin it, pan must absorb the slide: we need 10 × 11 + pan = 100, so pan = −10. The formula produces exactly that: pan' = 100 − (100 − 0) × 1.1 = −10. ✓

In general pan' = a − (a − pan) · k is just "solve w·zoom' + pan' = a for pan'". Zoom out and k < 1 — the same formula pulls the scene back toward your cursor.

The coordinate flip

src/view/controls.rs owns two jobs: remember what the mouse is doing, and translate raw window events into camera operations. It also handles a subtle, bug-breeding detail: the two halves of this program disagree about which way is up.

deep dive: the controller, line by line

Read it as a story: convert to centred coordinates; if we know where the cursor was, the left button is held, and panning is enabled in the config, pan by the difference; either way remember where it is now. Releasing the button needs no special handling — on_mouse_button flips left_down and this function stops calling pan_by.

Variants aren't just names, they're alternative shapes of data, and the compiler makes you handle each shape.

Everything chapter 12 built is plumbing; these two files finally draw. scene.rs turns particles into something the GPU understands; renderer.rs bakes a pipeline once and replays it every frame. The interesting story is how Rust structs become GPU bytes — the one place the two computers from chapter 2 must agree perfectly.

The translation layer

The GPU never sees a Particle. It sees a Shape: a thing with a centre, a size, a kind and a colour. Physics on one side, presentation on the other, and one small function between them.

sync is the whole mapping: position becomes centre, radius×2 becomes size (the shader wants a diameter), and mass becomes colour via chapter 10's ramp. clear() then extend() rather than building a fresh Vec means the allocation is reused every time — this runs on every frame that got a new snapshot.

Rust — #[repr(C)]

By default Rust may reorder your struct fields in memory for efficiency — the source order is a suggestion. #[repr(C)] switches to C's rules: fields in declared order, predictable layout. Mandatory for any struct whose raw bytes another system will read.

Rust — bytemuck's Pod and Zeroable

Turning a struct into bytes is trivially easy to do wrong (padding bytes, pointers, types with invalid bit patterns). Deriving Pod ("plain old data") makes the compiler prove the struct is nothing but plain numbers with no gaps — the derive literally fails to compile if there's hidden padding. That proof is what makes bytemuck::cast_slice(shapes) a safe, zero-cost "give me these 32×N bytes" instead of an unsafe hack.

And why _pad in Globals? WGSL rounds a struct's size up to a multiple of its largest member's alignment. Globals contains vec2s (8-byte aligned), so WGSL insists it's 24 bytes, not 20. The explicit _pad: f32 makes both sides agree on 24 honestly, and doubles as a free slot for the next field. Shape needs no such trick: it contains a vec4 (16-byte aligned) and is already 32 bytes, a clean multiple of 16.

why though? — this used to own the whole frame

Until the overlay arrived, this function was called render and did four more things: it created the command encoder, made the texture view, submitted the finished encoder to the queue, and presented the frame. It took the SurfaceTexture by value, because presenting consumes it.

All four had to move out the moment a second pass existed, and the reason is present. A frame can only be presented once, so whoever calls it owns the frame — and if the scene renderer owns the frame, there is no way for anything else to draw into it first. Now the renderer records into an encoder handed to it and returns; app.rs owns the frame, the encoder and the submission, and can slot any number of passes between the two. This is the standard shape for a renderer that isn't the only one: record, don't submit.

rpass.draw(0..6, 0..self.shape_count) is the whole drawing command. The first range is vertices: six, because a quad is two triangles. The second is instances: one per shape. The GPU runs the vertex shader 6×N times, and each run knows both which corner it is and which instance it belongs to — so it looks up shape #N in the storage buffer and places its corner accordingly. One command, any number of particles, no per-particle CPU work at draw time. That's instancing.

GPU concept — record, then submit

GPU work isn't issued call-by-call — that would mean thousands of tiny CPU↔GPU round-trips. Instead you record everything into a command encoder (a shopping list), then submit the finished list to the queue in one go. Until submit, nothing has happened on the GPU at all.

The black background is one enum value: LoadOp::Clear(BLACK) means "when this pass begins, wipe the canvas". Not a draw call — a "how to start the pass" setting, and the reason this pass must be the frame's first: anything drawn before it is erased. Chapter 15's overlay pass uses the other option, LoadOp::Load, which means "keep what's already there". Presenting — the moment pixels actually reach glass, and in Fifo mode the moment we wait for vsync — now happens back in app.rs, once, after every pass has been recorded.

Uploading new shapes

Called only on frames that received a snapshot (chapter 7), not on every frame. A GPU buffer has a fixed size, so if the shape count ever exceeds capacity the buffer is replaced — and then the bind group must be rebuilt too, because the old one still points at the buffer that just went away. Nothing grows the particle count today; this is here so that when something does, it doesn't silently draw the first N and drop the rest.

GPU concept — uniform vs storage buffer

Both are just blocks of GPU memory; the difference is how the shader is allowed to use them. A uniform is small (guaranteed only 64 KB), read-only, and the same value for every invocation — ideal for the 24-byte camera. A storage buffer can be enormous, can be declared as a runtime-sized array<Shape>, and can be indexed per-invocation — which is exactly what "shape number instance_index" needs. It can also be written by a compute shader, which is how the physics will eventually get on the GPU (chapter 16).

deep dive: sockets and plugs, and why they're separate objects
GPU concept — why two objects for one buffer?

The layout (socket shape) is part of the pipeline's compiled interface — the shader is compiled against "binding 0 is a uniform, binding 1 is a read-only storage array". The group (the plug) is swappable without recompiling anything, which is exactly what update_shapes does when it swaps in a bigger buffer. The socket numbers here are the same ones the shader declares with @group(0) @binding(0) and @binding(1). That pair of numbers is the entire connection between the two languages.

deep dive: the fragment shader, and how a square becomes a circle

Four lines, and one of them is the entire reason particles look round. Remember that local is the corner position, −1..+1 — but by the time the fragment shader sees it, the rasterizer has interpolated it across the triangle. So each fragment gets its own position within the quad: (0,0) dead centre, (1,1) at a corner, length > 1 anywhere outside the inscribed circle. discard means "produce no pixel at all" — the background shows through.

That's the difference between the two @location attributes doing their jobs: local is interpolated (every fragment differs), while color and kind are @interpolate(flat) (every fragment of a shape gets the same value). Interpolating the colour would be harmless here since all six corners carry the same one, but kind is a u32 — integers cannot be interpolated, and WGSL requires the flat qualifier on them.

kind is also the extension point: today KIND_CIRCLE is the only value, and the if looks pointless. Add KIND_SQUARE = 1 and shapes with that value simply skip the discard and stay square — one storage-buffer field, no second pipeline, no second draw call.

check yourself
How many times does the vertex shader run with 50,000 particles on screen?

300,000 — six corners × 50,000 instances. Which sounds enormous and takes the GPU no meaningful time at all; the fragment stage, running once per covered pixel, is the one that scales with how big the particles look rather than how many there are.

How would you make particles glow softly at the edges instead of having a hard rim?

Entirely in the fragment shader, using the same length(in.local): instead of discarding at >1, compute an alpha that falls off toward the rim and return vec4(in.color.rgb, in.color.a * falloff). You'd also need to turn on alpha blending in the pipeline's colour target. No CPU change whatsoever.

@group(0) @binding(1) — where do those numbers appear on the Rust side?

Twice: the bind group layout entry declares binding: 1 as a read-only storage buffer, and the bind group plugs the real buffer into binding: 1. Then set_bind_group(0, …) at draw time supplies group 0. Numbers matching across the language boundary is the entire wiring mechanism.

Step zero: a font file is not a picture

Open C:\Windows\Fonts\consola.ttf in a hex editor and you will not find any letters in it. A TrueType font is a small database of outlines. Each glyph is stored as a set of closed loops made of straight segments and quadratic Bézier curves, with coordinates in an abstract grid called the em square — typically 1000 or 2048 units on a side, deliberately nothing to do with pixels. Alongside the outlines are tables of metrics (how wide is each character, where does the baseline sit), a character map (which Unicode code point is which glyph), kerning pairs, and hinting bytecode.

To get from that to something you can put on screen, somebody has to rasterise it — per character, per size:

  1. Scale the outline from em units down to your pixel size.
  2. Flatten every Bézier curve into enough short line segments that the curve reads as smooth — and no more, because each one costs.
  3. Fill it: decide, for every pixel in the glyph's bounding box, what fraction of that pixel's area falls inside the outline. Not "is the centre inside" — the actual covered area, as a number from 0 to 1. That fraction is what makes text look smooth instead of jagged, and computing it properly means handling self-intersecting contours, a winding rule that says which side is "inside", and holes (the middle of an o is a second loop wound the other way).
  4. Hand back that little grid of coverage values, plus where to put it relative to the pen.

That is a genuinely hard piece of computational geometry, it is completely uninteresting once you've read the algorithm, and getting it 95% right produces text that looks subtly wrong in a way you can't name. So it is the one job we hand off, to a crate called fontdue, and the seam is drawn exactly there:

The atlas: rasterise once, draw forever

Doing that rasterisation per character per frame would be lunacy — it's the expensive part, and the answer is the same every time. So it happens once, at startup: rasterise every character we can ever display, pack the results side by side into one image, upload that image to the GPU as a texture, and never think about outlines again. From then on, drawing a letter is drawing a rectangle that reads from a known corner of that image. This is called a glyph atlas, and it is how essentially all real-time text works.

Which characters? Code points 0x20 to 0x7E — space through tilde, 95 printable ASCII characters. That is a deliberate ceiling: it's a debug readout that displays numbers and English labels we wrote ourselves, so there is nothing else to show. It also buys a data structure so simple it's barely one:

Because the range is contiguous, "which glyph is 'k'" is a subtraction: 'k' is 0x6B, minus 0x20, is index 75 into a fixed-size array. No hash map, no allocation, no branch except the range check. Anything outside — an accented letter, an emoji, a tab — silently becomes ? rather than crashing or vanishing, which is what you want from a debug overlay: a visible, obviously-wrong character beats a mystery.

Rust — returning Glyph by value

glyph returns Glyph, not &Glyph, and that is not a copy you should feel bad about. Glyph is nine f32s — 36 bytes, Copy, no heap, no pointer — so returning it by value is a register-sized move that the optimiser usually erases entirely. Returning a reference would tie the caller's lifetime to the atlas for no benefit and make the borrow checker part of the conversation. Rule of thumb: small plain-data structs travel by value.

Shelf packing

Now, where does each bitmap go in the image? This is the rectangle packing problem, which in its general form is NP-hard and has a small literature of clever heuristics (skyline, MaxRects, guillotine cuts). We are packing 94 rectangles that are all roughly 7×11 pixels, once, at startup. So we use the dumbest algorithm that exists:

Walk left to right laying glyphs in a row; when the next one won't fit, drop down by the tallest glyph in the row you just finished and start again at the left. That's it. It wastes space whenever glyph heights vary a lot within a shelf — which is exactly the case it isn't asked to handle, because every glyph here is one font at one size. GPU concept — why the atlas is exactly 512 wide

Uploading pixels to a texture goes through queue.write_texture, and wgpu requires the bytes per row of your source data to be a multiple of 256. That's not wgpu being fussy; it's a hardware alignment requirement that shows up in Vulkan, D3D12 and Metal alike.

The atlas is R8Unorm — one byte per pixel — so 512 pixels is exactly 512 bytes, which is 2 × 256. The upload is one straight memcpy of the whole buffer. Choose 500 instead and every row needs padding to 512 bytes, which means allocating a second staging buffer and copying row by row into it. Same picture, twenty more lines, for nothing. Pick a power of two and the problem never exists.

GPU concept — the one-pixel gutter

GUTTER = 1 leaves an empty pixel between neighbours, and it is there because of bilinear filtering. When the shader samples the atlas at some coordinate, the sampler doesn't return one pixel — it blends the four nearest, weighted by how close the coordinate is to each. At the very edge of a glyph, two of those four are outside it. With glyphs packed flush, "outside it" means "inside the next letter", and you get a faint smear of the neighbouring character along every edge. It's called texture bleeding, it is unmistakable once you know it, and one transparent pixel fixes it forever.

Walking a string into rectangles

That is the entire text engine. Find the baseline once, then walk the string pushing a rectangle per character and sliding the pen right by that character's advance. Three things worth calling out:

The if skips the space. A space rasterises to a 0×0 bitmap — it has an advance and no ink. Pushing a zero-sized quad wouldn't draw anything, but it would still cost a struct in the buffer and six vertex shader invocations on the GPU. In this overlay roughly one character in six is a space, so the check removes about 16% of the work for the price of two comparisons on the CPU.

The pen advances even for skipped characters. Obvious once said, easy to get wrong by putting pen += glyph.advance inside the if, at which point every space collapses and "tick 331" renders as "tick331".

The colour comes from the caller, not the atlas. The atlas stores coverage — how much of each pixel the letter covered — and nothing else. Colour is per-quad, so the same 16 KB of texture draws dim grey labels and bright white values and amber PAUSED without a second copy of anything. That is why the atlas is a one-channel image and not an RGBA one, and it is 4× the memory saved for free.

Rust — .chars(), not indexing

You cannot write text[3] on a Rust &str, and the reason is that a String is UTF-8: a character can occupy one to four bytes, so byte 3 might be the middle of one. .chars() is an iterator that decodes the UTF-8 as it walks, yielding real char values (each a full Unicode scalar). It's slightly slower than indexing an ASCII array, and it's the reason a stray é in a label produces a ? rather than two mangled bytes.

what it looked like

The panels appeared, correctly sized, correctly positioned, with correct translucent backgrounds. The text was almost absent: seven lines of stats rendered as an L and an N on the first line, an i and a 1 on the second, a lone 3 on the third. Every character that did appear was the right character in the right place in the right colour. The rest simply weren't there.

That pattern is the whole clue, and it's worth learning to read: layout code that was broken would have put letters in wrong places. Atlas code that was broken would have drawn wrong letters. Getting a correct subset means the data was perfect and something was reading it at the wrong stride.

Counting the survivors by their position in the buffer gives 5, 10, 15, 20, 25 — every fifth quad, exactly. Four out of five glyphs were being read from bytes that straddled two neighbouring quads, producing garbage rectangles with garbage uv coordinates that mostly landed on empty atlas space and drew nothing.

why nothing caught it

Worth dwelling on, because "add a check" is the obvious lesson and it's the wrong one. The Rust const assertion passed — it verified Quad was 64 bytes, and it was. bytemuck::Pod derived fine — the struct genuinely has no hidden padding in Rust. The WGSL compiled without a warning — it was valid WGSL describing a valid 80-byte struct. wgpu's validator saw a storage buffer of N × 64 bytes bound to an array of 80-byte elements and said nothing, because a runtime-sized array just takes however many whole elements fit.

Every individual piece was correct and self-consistent. The mistake lived in the gap between two languages, which is precisely the gap no tool in either language is looking at. The only two defences that actually work are knowing the alignment table by heart, and this — a comment on both sides of every shared struct saying "these must match", which chapter 13's Globals already carried and which this struct now carries too.

Panels: turning numbers into a laid-out block

Three small types stack up, each one a list of the one below: a panel is a list of lines, a line is a list of spans, and a span is a run of characters sharing one colour. That last level exists for exactly one reason — so a dim grey label and a bright white value can share a row:

Rust — the builder pattern, and impl Into<String>

span takes self by value and returns Self, which is what lets you chain: Line::default().span("speed", LABEL).span("+1.00x", VALUE). Each call consumes the line, pushes to it, and hands it back. No intermediate variable, no mut, and the type system guarantees you can't use a half-built line by accident because the old binding was moved out of.

impl Into<String> in the argument means "anything that can become a String". That accepts a &str literal and the String that format! produces, so callers never write .to_string() at the call site. It's the polite way to take text in Rust.

Then one function turns a panel into quads. It is the only place in the module that knows the window exists:

It measures before it draws, and it has to. A panel's width is the width of its longest line, and you cannot know that without walking every line — and you need it before placing anything, because a right-anchored panel's left edge is window width − margin − padding − that width. So the first pass measures, then the plate is emitted, then a second pass measures each line again to right-align it.

Three passes over the same text per frame, then, and measure is itself a walk over every character. For 137 quads that is a few thousand array lookups and float adds — genuinely nothing, next to a frame that also uploads a buffer and rasterises tens of thousands of pixels. It is worth naming as a decision rather than leaving it as an accident: if this overlay ever grew to a wall of text, caching each line's measured width alongside it would be the first and only optimisation needed.

The plate is pushed first, and that ordering is the layering. There's no depth buffer in this pass and no sorting; quads are drawn in the order they sit in the buffer, so anything pushed later paints over anything pushed earlier. Push the background last and you'd get a neat translucent rectangle with the text hidden behind it.

Everything is multiplied by scale — the margin, the padding, and (back at atlas-build time) the font size. That's the display's DPI scale factor, and it's what stops the overlay from shrinking to unreadable on a 4K laptop screen. More on that below.

Rust — fold(0.0, f32::max), and why not .max()

.max() on an iterator needs Ord, and floats don't implement it — because NaN is not less than, greater than, or equal to anything, so floats have no total order. fold(0.0, f32::max) sidesteps it by using f32's own two-argument max, which has defined NaN behaviour (it returns the other operand). Starting the fold at 0.0 rather than f32::NEG_INFINITY is deliberate too: an empty panel gets width zero, not a negative infinity that would place the plate somewhere in the next county.

The content: numbers in, lines out

overlay.rs is the only file in the module that knows what this program is about. Everything else deals in glyphs and rectangles; this one knows there's a simulation with a tick count. It's also the file to edit when you want the overlay to say something else, and it's deliberately boring:

Now the GPU side. This file exists separately from shader.wgsl because it disagrees with it about the most basic thing there is: what a coordinate means.

The uniform block is the tell. The scene's Globals carries resolution, pan and zoom. The overlay's carries resolution and nothing else — because no amount of dragging or scrolling may move it by one pixel:

Four bindings where the scene had two. Bindings 0 and 1 are the same idea as chapter 13 — a small uniform and a big storage array. Bindings 2 and 3 are new, and note they are declared with a bare var: no <uniform>, no <storage>. Textures and samplers are handles, not memory you address, so they get no address space qualifier.

Structurally this is chapter 14's vertex shader with different arithmetic in the middle. Same six-vertex quad, same instance_index lookup into a storage array, same no-vertex-buffer trick. Four differences, all of them consequences of fig. 15:

Unit corners, not ±1. A particle is described by its centre and a size, so its corners run −1 to +1 and get scaled by half the size. A UI rectangle is described by its top-left and a size, so its corners run 0 to 1 and rect.xy + corner * rect.zw walks from the anchor across the full extent. Same two triangles, different parameterisation of the same square.

The y flip. Clip space has +y pointing up; our pixels have +y pointing down. Compare the two halves of the expression and the flip is visible as the difference between x/w*2 - 1 and 1 - y/h*2: one maps 0→−1 and w→+1, the other maps 0→+1 and h→−1. It is the same conversion view/controls.rs does for the mouse in chapter 11, for the same reason — window systems count down from the top, graphics maths counts up from the middle — and here it's done on the GPU instead.

No camera. There is nowhere in this shader for pan or zoom to enter, and that's a guarantee rather than an omission. A UI that drifts when you drag the world is a UI with a bug; making the data unavailable is a stronger promise than remembering not to use it.

mix picks the uv corner. mix(a, b, t) is linear interpolation: a + (b - a) * t, componentwise. With t being a corner of 0s and 1s it isn't really interpolating — it's selecting. Corner (0,0) gives uv.xy, the atlas rect's top-left; corner (1,1) gives uv.zw, its bottom-right; corner (1,0) mixes to give the top-right. One instruction instead of a four-way branch, and the rasteriser then interpolates between those corners across the triangle, which is what stretches the glyph's little patch of atlas across its rectangle.

Two lines of real work, and both are worth a paragraph.

GPU concept — why the sample can't live inside an if

The GPU does not shade one fragment at a time. It shades them in 2×2 blocks, in lockstep, and that is not an implementation detail you can ignore — it's how textureSample works. Choosing a mip level means knowing how fast the texture coordinate is changing across the screen, and the hardware computes that by subtracting your neighbours' uv from yours. It gets the neighbours' values for free because they're running the same instruction at the same moment.

Put the sample inside a branch and that falls apart: if your neighbour took the other path, it never computed a uv, and the derivative is undefined. WGSL therefore requires textureSample to be called in uniform control flow — code every invocation in the block reaches. The fix is the one above: sample unconditionally, then use select(a, b, cond) — the branchless "pick one of two values" — to decide what to do with the result. A solid rectangle wastes one texture fetch; two of the 137 quads are solid rectangles. If you ever need a genuinely conditional sample, the escape hatch is textureSampleLevel, which takes an explicit mip level and therefore needs no derivatives at all.

The atlas holds coverage, not colour, and the last line is where that pays off. What comes back from the sample is a single number: how much of this pixel the letter covered, 0 to 1. It is used as an alpha multiplier on a colour that came from the quad. That is why one 16 KB greyscale image draws every colour of text in the program, why a partially-covered pixel at the edge of a letter comes out as a partial blend of the text colour with whatever is behind it (which is antialiasing), and why a solid background plate can go through the identical shader by simply skipping the multiply.

Because they answer different questions and change at different rates. The texture is what pixels exist; the sampler is the policy for reading between and beyond them. The pipeline, and the one setting that makes text possible

The overlay's pipeline is chapter 13's with one difference that matters enormously:

The scene pass passes blend: None (via format.into()), meaning every fragment replaces whatever was in the target. That's right for opaque discs on a cleared background. It is completely wrong for text, where the interesting pixels are the half-covered ones at the edge of every stroke.

GPU concept — what alpha blending actually computes

BlendState::ALPHA_BLENDING is shorthand for one formula, applied by fixed hardware after your fragment shader returns — alpha blending:

result.rgb = src.rgb × src.a + dst.rgb × (1 − src.a)

src is what the shader just returned; dst is what was already in the target. So an alpha of 1 keeps only the new colour, 0 keeps only the old, and 0.4 is a 40/60 mix. Feed it a glyph edge with 40% coverage and you get 40% of the text colour over 60% of the background — which is exactly what antialiasing means, done for free by hardware that was going to run anyway.

It's also what makes the background plates work: BACKGROUND is [0.02, 0.02, 0.04, 0.62], so 62% near-black over 38% of whatever particles are behind it. Blending is order-dependent (mixing A then B is not mixing B then A), which is the deeper reason the plate must be pushed into the buffer before the glyphs that sit on it.

prepare and draw: why the frame is split in two

Two methods, and the split is not arbitrary. prepare takes &mut self and does everything that touches memory: rebuild the quad list, grow the GPU buffer if it needs to, upload. draw takes &self and only records — set pipeline, set bind group, one draw call. This is the standard prepare/render split every serious renderer converges on, and the reason is ordering: uploads must be queued before the pass that reads them, and the pass can only be recorded once you hold the frame. Chapter 7's redraw does exactly that — prepares before acquire_frame, draws after.

self.quads.clear() keeps the Vec's allocation and throws away only its contents, so after the first frame the overlay never allocates again. Same trick as Scene::sync in chapter 13, same reason.

The buffer starts at 1024 quads — comfortably more than the 137 a full overlay uses — and grows by the same power-of-two doubling as the scene's shape buffer, rebuilding the bind group when it does. It will realistically never fire. It's four lines, and the alternative is text that silently truncates the day somebody adds a panel.

Finding a font on three operating systems

The program ships no font. It has to find one on your machine, and "where do fonts live" has three different answers, none of which is guaranteed:

Rust — #[cfg], compiled-out code

#[cfg(target_os = "windows")] is a conditional compilation attribute: the item below it only exists in the build if the condition holds. This isn't an if that runs and picks — on a Linux build the Windows array is not in the binary, was never type-checked past parsing, and the name FALLBACKS refers unambiguously to the one list that survived. Note the third arm has to be written as "not windows and not macos" rather than "linux", so the program still builds on BSD, and its Linux paths are a decent guess there too.

r"C:\Windows\..." is a raw string: the r prefix turns off escape processing, so a backslash is just a backslash. Without it every one would need doubling. Handy for Windows paths and regexes, which are the two places anyone ever meets it.

The list is per-platform, ordered by preference, and every entry is monospaced for the column alignment reason above — except the Windows and macOS proportional stragglers at the end, which are there purely as a last resort before giving up. The load order is: your configured path, then each fallback, then nothing:

Note what each failure costs you. A bad configured path prints a complaint naming the path and the OS error, then continues — you get an overlay in a different font and a line in the terminal telling you why. No font at all anywhere prints what it tried and returns None, and the program runs with no overlay. At no point does a missing font stop you from watching particles, which is the same "one bad key shouldn't cost you the file" philosophy as the config loader in chapter 6.

Rust — find_map, or "the first one that works"

.find_map(|c| Self::read(c).ok()) reads as: try each candidate, convert its Result to an Option with .ok() (throwing the error away), and stop at the first Some. Iterators in Rust are lazy, so this genuinely stops — once Consolas loads, the other paths are never even touched by the filesystem. The whole "try these in order until one works" pattern, in one line, with no index variable and no break.

Pixels, points, and the monitor you drag the window onto

fontSize: 14.0 in the config is not 14 physical pixels. It's 14 logical pixels, and the atlas is rasterised at font_size × scale, where scale is the OS display scale factor — 1.0 on a plain monitor, 1.5 at 150%, 2.0 on a Retina panel.

Which means the atlas is only correct for one scale factor, and dragging the window to a different monitor invalidates it. Hence:

Every glyph is rasterised again at the new size, a new texture is created and uploaded, and the bind group is rebuilt to point at it (the old one still refers to a texture that's about to be dropped — the same rule as chapter 13's buffer growth). It costs perhaps a millisecond and happens when you drag a window between monitors, so nobody will ever see it.

This is also why FontFace keeps the parsed fontdue::Font around rather than discarding it after the first rasterise: re-rasterising needs the outlines again, and holding the parsed font avoids re-reading and re-parsing the file. The font is size-agnostic; only the atlas is size-specific.

why though? — rasterise per size rather than scale one bitmap

You could rasterise once at a large size and let the GPU shrink it. It would look bad, and predictably so: a glyph is a few pixels across, and shrinking a bitmap of a letter blurs exactly the thin strokes and sharp corners your eye uses to tell letters apart. Real font rendering re-rasterises per size because the rasteriser can then place each stem on a whole-pixel boundary and keep it crisp. The industrial-strength alternative is a signed distance field — store distance-to-the-glyph-edge instead of coverage, which does survive scaling — and that's what engines do when text has to zoom smoothly. For an overlay at one fixed size, rasterising per size is both simpler and sharper.

check yourself
The atlas is one byte per pixel. How does the overlay draw green, white, amber and grey text out of it?

The atlas doesn't store colour at all — it stores coverage, meaning "how much of this pixel did the letter cover". Colour lives in the Quad, per rectangle, and the fragment shader multiplies the quad's alpha by the sampled coverage. Same 16 KB of texture, unlimited colours, and the amount of GPU memory would be identical if every line were a different shade.

You change fontSize from 14 to 28. Which parts of the program have to change, and which don't?

The atlas is re-rasterised at the new size, so it becomes a taller image with different uv rects, and ascent/line_height/advance all roughly double. Panels get bigger because their size is derived from measurement rather than hard-coded. Nothing else moves at all: the shader never learns the font size, the quad struct doesn't change, the pipeline doesn't change, and no constant needs editing. That's the payoff for storing uvs normalised to 0..1 and for measuring rather than assuming.

Why does a space character get an advance but no quad?

Because it has an advance and no ink. fontdue rasterises it to a 0×0 bitmap with a full advance_width, so push_line's size check skips pushing a quad while the pen still moves right. Move that pen += inside the if and every space in the overlay disappears.

You add a vec3<f32> field to the middle of the Quad struct on both sides. What happens, and how would you notice?

The two structs stop being the same size again — WGSL pads the vec3 to a 16-byte boundary and rounds the struct up, Rust doesn't — so the shader reads every quad from a drifting offset and you get a scattering of correct characters among garbage. You'd notice it exactly the way it was noticed the first time: by seeing which quads survived and realising they were evenly spaced. The fix is always the same — use a vec4 and ignore one component, or three scalars.

Why is the overlay a second render pass rather than a second draw call inside the first one?

Because a draw call inherits the pass's settings, and these two disagree about nearly all of them: different shaders and pipelines, different bind group layouts, and crucially different blending — the scene overwrites, the overlay blends. You'd have to switch pipelines mid-pass, which buys nothing over two passes and costs you per-pass load/store control. Two passes in one encoder is still one submission.

Where would you add a frame-time graph — a little sparkline of the last 100 frames?

Almost entirely in overlay.rs and panel.rs. You already have Quad::rect, which draws a solid rectangle of any size and colour with no atlas involvement, so a sparkline is 100 thin rectangles pushed straight into the quad list — no new shader, no new pipeline, no new buffer, no new bind group. The KIND_RECT path exists for the background plates, and it turns out to be a general-purpose 2D drawing primitive you got for free.

One frame, end to end

The grand finale. Two things are happening at once now, so here is one second of wall-clock time with both threads in it — the simulation ticking away on the left, one vsync frame doing its work on the right.

Read the right-hand lane as five phases: collect (is there new state?), convert (particles to shapes, numbers to quads), upload, record, submit and wait. Every frame runs all five; most frames find nothing new in the first one and skip straight past the middle three for the scene, while the overlay rebuilds itself unconditionally because it costs a few microseconds and cannot then be stale.

Trace it yourself: you drag left by 100 px. Which functions run, in order, and what number changes where?

The overlay says fps 144. What was true 144 frames ago, and what is true now?

That number was computed at most one second ago and is not recomputed until the next second boundary — RateMeter::sample returns early on all the frames in between. So the overlay is showing a one-second-old average, deliberately, because an instantaneous per-frame rate is unreadable noise. Everything else in the panel (tick, zoom, pan, speed) is current to this exact frame.

Where — in file and line terms — does "the scene must not scale on resize" actually live?

Nowhere, and that's the answer: it's the absence of window size from the camera formula (view/camera.rs) plus a resize() (gpu/context.rs) that touches only the surface. The shader's final divide by resolution maps pixels to clip space 1:1 for any window. The guarantee is structural, not coded.

Most of the chassis is now built and the hole left in it is a specific, small one. Here's the state of play:

Actual forcesthe hole

Step one: naive gravity on the CPU

Replace the mass oscillation in World::tick with the textbook loop: for every pair, compute F = G·m₁m₂/r² along the line between them, accumulate accelerations, then integrate — velocity += acceleration × delta; position += velocity × delta. Two things to get right on day one:

  • Softening. As r approaches zero the force approaches infinity and two particles slingshot to the edge of the universe. The standard fix is to compute r² + ε² instead of r², for some small ε — a "minimum distance" that costs nothing and removes the singularity.
  • Integrate symmetrically. Plain Euler (v += a·dt then x += v·dt) leaks energy and orbits spiral outward. Swapping to velocity Verlet or leapfrog is a few extra lines and is what makes orbits actually close.

This gets you real gravity for a few thousand particles at 60 tps, and it is entirely a change to one function. The tick rate, the thread, the hand-off, the renderer: untouched.

Step two: stop doing O(n²)

Every pair is 2.5 billion comparisons at 50,000 particles — per tick. The standard answer is a Barnes–Hut tree: group distant particles and treat each group as one particle at its centre of mass, which drops the cost to O(n log n). A quadtree is the 2D version.

Worth noticing: generation/grid.rs already solves the neighbourhood-query problem for the overlap pass, and a uniform grid is a perfectly good short-range accelerator too. The structures are different (grids are for "who is near me", trees are for "who can I approximate"), but the shape of the code — build an index, query it per particle — is one you've already read.

Step three: move it to the GPU

The endgame. A compute shader is a third kind of shader — no vertices, no pixels, just "run this function N times over this buffer". Particles would live in a storage buffer the GPU owns; a compute pass would read positions and write new ones; the render pass would draw straight from that same buffer with no CPU round-trip at all. Concretely:

  • @compute @workgroup_size(64) next to the two existing entry points in shader.wgsl.
  • A second pipeline (a ComputePipeline) in renderer.rs, and a begin_compute_pass recorded into the same encoder before the render pass.
  • Two particle buffers, ping-ponged — read from A, write to B, swap. The same double-buffer idea as chapter 8, one level down.
  • required_features in context.rs may need a line, and the storage buffer's read_only: true becomes false.

At that point World::tick stops holding particles at all and the simulation thread's job becomes "submit a compute pass at 60 Hz" — which, notably, still wants exactly the fixed-timestep clock chapter 8 built.

The one visual thing that's missing

At 60 tps on a 144 Hz screen, roughly three frames in five show a state that's up to 16 ms stale, and once particles actually move that reads as micro-stutter. The fix is interpolation: keep the previous snapshot as well as the current one, work out how far between the two ticks this frame falls, and blend the positions — ideally in the vertex shader, which makes it free. That means the snapshot carries two states and a blend factor instead of one state, so it's a real change to try_recv's signature. Worth doing the day something moves; pointless before then, which is why it isn't there.

why though? — the shape of what's left

Notice that every remaining step is local. Real forces: one function. Barnes–Hut: one new file next to it. GPU compute: renderer.rs and shader.wgsl. Interpolation: runner.rs and the shader. Nothing on that list requires touching the config loader, the camera, the input handling, the colour ramp, the generator or the overlay. That's what the module boundaries in chapter 4 were for.

the one thing physics will break

Reverse. Chapter 8 spells this out and it belongs on this list too: today's tick recomputes the world from elapsed, so a negative delta lands on exactly the state you came from. An accumulating integrator doesn't — it's approximately reversible at best, and not at all once anything dissipative shows up. When forces land, the arrow keys will still make the world run backwards and it will still look right, but it will no longer be the same run played in reverse. The eventual fix is a ring buffer of past snapshots on the simulation thread, which is also exactly what you'd want for the interpolation above — two features, one data structure.

Glossary

Plain-language definitions. Dotted terms all over this page jump here; use your browser's Back button (or Alt+←) to return.

adapter
wgpu's word for one physical GPU in your machine (or a software fallback). You don't draw with it — you inspect it and request a device from it. Created in gpu/context.rs.
atomic
A variable that can be read and written from several threads at once without tearing or a lock. AtomicBool is what simulation/runner.rs uses for its "keep running" flag: the main thread writes false from Drop, the simulation thread reads it every loop, and no Mutex is involved.
alpha blending
Combining a fragment's colour with what is already in the target instead of replacing it, using the fragment's alpha as the mix: result = src × src.a + dst × (1 − src.a). Done by fixed hardware after the fragment shader, and switched on per pipeline. It's what turns a glyph's partial edge coverage into smooth antialiased text, and what makes the overlay's panel backgrounds see-through. The scene pass doesn't use it; chapter 15.
atlas (texture atlas)
One image holding many small images packed side by side, so everything can be drawn from a single texture binding in a single draw call. Ours is a glyph atlas: every printable ASCII character rasterised once at startup into a 512×32 one-byte-per-pixel image. Drawing a letter is then just drawing a rectangle with the right uv corners. Chapter 15.
Barnes–Hut
The standard trick for making n-body gravity affordable: build a tree over space, and when a whole distant group of particles is far enough away, treat it as a single particle at its centre of mass. Turns O(n²) into O(n log n). Not implemented here; chapter 17.
baseline
The invisible line letters sit on — not the bottom of the text, since descenders like p and g hang below it. Every position a font rasteriser reports is measured from here: ascent is how far the font reaches above it, descent below, and a glyph's ymin says where its bitmap's bottom edge sits relative to it. Chapter 15, fig. 13.
bind group
The object that says which actual buffer is plugged into which numbered socket a shader declared. The socket numbering is @group(g) @binding(b) in WGSL; the Rust side matches it with set_bind_group(g, …). Its sibling, the bind group layout, describes only the socket's shape — the layout is part of the pipeline; the group carries the real data, and can be swapped when a buffer is replaced.
bleeding (texture)
When a filtered texture read at the edge of one packed image picks up pixels from its neighbour, because linear filtering blends the four nearest texels and two of them are outside the image you meant. Prevented by leaving a gap between packed items — the one-pixel gutter in the glyph atlas. Chapter 15.
buffer
A plain block of GPU memory with a size in bytes and a list of allowed uses (UNIFORM, STORAGE, COPY_DST…). No structure, no types — bytes. Both sides just have to agree on the layout (see chapter 13's byte table).
coverage
What fraction of a pixel's area falls inside a shape, as a number from 0 to 1 — not "is the centre inside", but the actual area. Computing it is what a font rasteriser does, and using it as an alpha is what makes text look smooth rather than jagged. The glyph atlas stores coverage and nothing else, which is why one greyscale image can draw text in any colour.
clip space / NDC
The coordinate system a vertex shader must output: x and y from −1 to +1 across the viewport (left→right, bottom→top), regardless of window size. Anything outside is clipped off. Also called normalized device coordinates.
command encoder
A recorder for GPU work. You "record" passes and copies into it; nothing executes until the finished recording is submitted to the queue. Like writing a full shopping list instead of driving to the store per item.
const evaluation
Rust running your code at compile time and baking the answer into the binary. Loops, conditionals and (since 1.82) floating-point arithmetic all work. simulation/speed.rs uses it to derive the length of the speed ladder from its factor and its clamp, so those two constants stay the only knobs. Zero runtime cost by construction — the runtime never sees the loop.
device
Your open, validated connection to a GPU. Creates every resource (buffers, pipelines, shader modules, bind groups) and checks your work. If you break the rules, it reports errors through the logger — that's why env_logger exists in this project.
discard
A WGSL statement that ends a fragment shader invocation without producing a pixel. What turns our square quads into round particles: any fragment more than one unit from the quad's centre simply doesn't exist, so the cleared background shows through.
drop-oldest
A hand-off policy: when the producer is faster than the consumer, keep only the newest item and throw the rest away. The opposite of a queue, and the right choice for live state — nobody wants to watch a backlog of stale physics. Implemented here by a single fresh flag; chapter 8.
fixed timestep
Advancing a simulation by the same delta every tick, regardless of how long the tick actually took in wall-clock time. Makes runs reproducible and integration stable. Its opposite — feeding in the measured frame time — makes your physics depend on your frame rate. Chapter 3.
font metrics
The numbers a rasteriser hands back alongside a glyph's pixels. Per font: ascent, descent, line gap, and their sum new_line_size (how far down the next line goes). Per glyph: advance (how far the pen moves afterwards — not the same as its width), xmin (the gap from the pen to the ink) and ymin (where the ink's bottom sits relative to the baseline). Chapter 15 draws all of them.
fragment
A candidate pixel produced by the rasterizer. The fragment shader runs once per fragment and returns its color, or discards it.
frame
One complete image of the window. Programs like this one produce a fresh frame continuously (here: at the monitor's refresh rate). Also used for the surface texture you draw the image into. Distinct from a tick.
HSL
A way of describing a colour as hue (an angle around a colour wheel), saturation (how vivid) and lightness. Blending two colours by interpolating these three, rather than by averaging red/green/blue, keeps the intermediate colours vivid instead of passing through grey. color/blend.rs converts to HSL, blends, and converts back.
interior mutability
Changing a value through a shared (&) reference, which Rust normally forbids. Types built for it — atomics, Mutex, RefCell — are exactly the ones whose job is to be modified from several places at once, and they enforce their own safety internally. It's why toggle_pause can take &self while obviously mutating something.
instance (wgpu)
The initialized wgpu library — the root object everything else comes from. Not to be confused with instancing.
instancing
Drawing the same geometry many times in a single command, with each copy told which number it is. draw(0..6, 0..N) means "6 vertices, N copies"; the shader reads @builtin(instance_index) and looks up that copy's data. One draw call for every particle on screen.
mutex
A lock that lets exactly one thread touch the data inside it at a time. In Rust the data lives inside the Mutex, so there is no way to reach it without locking. If a thread panics while holding one it becomes poisoned and later locks return an error — see chapter 8 for when ignoring that is legitimate.
packing (rectangle packing)
Fitting many small rectangles into one big one without overlap, wasting as little space as possible. NP-hard in general, with a literature of heuristics. The glyph atlas uses the simplest of them, shelf packing: fill a row left to right, drop to a new row when the next item won't fit. Near-optimal when everything is roughly the same height, which one font at one size guarantees.
physical vs logical pixels
Physical: actual screen dots. Logical: physical divided by the OS scale factor (125% scaling → 1 logical = 1.25 physical). We request the window in logical (1280×720) so it looks right on any monitor, but do all rendering math in physical.
pipeline (render pipeline)
The compiled, immutable bundle of "how to draw": vertex shader + fragment shader + output format + primitive type + blend/depth settings. Expensive to create, so it's built once at startup and reused every frame. Different look = different pipeline.
queue
Where command buffers are submitted for the GPU to execute, in order. Also provides write_buffer (uploads) and, in wgpu 30, present.
rasterise (a glyph)
Turning a character's stored outline — closed loops of lines and Bézier curves in an abstract em grid — into a small grid of coverage values at a specific pixel size. Involves scaling, flattening curves to segments, and area-filling with a winding rule. The one job this project hands to a crate (fontdue). Distinct from the GPU's rasterizer, which does the analogous job for triangles.
rasterizer
Fixed hardware between the two shader stages: takes each triangle's three clip-space corners, works out exactly which pixels it covers, and interpolates the vertex shader's other outputs across them. Not programmable, extremely fast — and its interpolation is what gives each fragment its own local coordinate, which is how the circles get cut out.
relaxation
Solving a set of constraints by repeatedly nudging everything a little way toward satisfying them, rather than solving exactly in one shot. Used here to separate overlapping particles: measure every intersection, move everyone a fraction of the way apart, repeat until nothing intersects. Chapter 9.
sampler
The rules for reading a texture, kept as an object separate from the texture itself: how to blend between neighbouring texels (Nearest picks one, Linear blends the four nearest), and what a coordinate outside 0..1 returns (ClampToEdge, Repeat…). Separate because one policy can serve many images, and the same image can be read two ways in two passes.
SDF (signed distance field)
Storing, per pixel, the distance to the nearest edge of a shape rather than whether it's inside. Unlike coverage, that survives being scaled up, so one texture renders crisp text at any size — the standard trick for text that has to zoom. Overkill for an overlay at one fixed size, which is why chapter 15 re-rasterises per size instead.
shader
A small program that runs on the GPU, thousands of instances in parallel. Kinds used here: vertex (per corner: "where does this go on screen?") and fragment (per pixel: "what colour, or none?"). The future physics will add compute (per anything: "just calculate").
spatial grid
A flat array of buckets covering a region, each holding the indices of the things inside it. Turns "which particles are near this one?" from a scan of everything into a look at nine buckets. Cell size is the whole design: too small and you miss pairs, too large and each bucket holds everything. generation/grid.rs.
span (of text)
A run of characters sharing one colour. The overlay models a line as a list of spans so a dim label and a bright value can share a row while still being measured, positioned and right-aligned as one unit. Chapter 15.
storage buffer
A GPU buffer a shader can index freely and, optionally, write to — and which can be declared as a runtime-sized array<T>. Bigger and more flexible than a uniform, which is limited and read-only. Ours holds the Shape list, 32 bytes each.
surface
The bridge object between the window and the GPU: the drawable area, owning a small rotating set of images (swapchain). Must be configured (size, format, present mode) before use, and re-configured on every resize.
surface texture
"This frame's canvas": the texture the surface hands you to draw into, which is then handed back with present. Acquiring it can fail in recoverable ways (window resized, GPU reset…) — gpu/context.rs handles all of them.
swapchain
The rotating set of 2–3 images behind a surface: while the monitor shows image A, you draw into image B, then swap. The word comes from Vulkan; wgpu hides it inside the surface.
texture
GPU memory organized as an image (width × height × pixel format) rather than raw bytes. What render passes draw into; also what images/sprites are stored as.
tick
One step of the simulation, always the same size in simulated seconds. Ticks are produced by simulation/runner.rs at the configured tickRate and have nothing to do with frames: the title bar shows both numbers so you can watch them disagree.
triple buffer
Three buffers rotating between three roles — one being written, one waiting in a shared slot, one being read — so a producer and a consumer can run at different speeds without either waiting or copying under a lock. Chapter 8, fig. 6.
uniform control flow
Code that every invocation in a GPU's lockstep group actually reaches. textureSample requires it, because it picks a mip level by comparing texture coordinates with the neighbouring fragments in the same 2×2 block — and a neighbour that took the other branch never computed one. The fix is to sample unconditionally and use select on the result, which is what ui/ui.wgsl does. Not to be confused with a uniform buffer.
uniform
Small, read-only data that is the same ("uniform") for every shader invocation in a draw — settings, not per-item data. Ours: window resolution + camera pan + zoom, 24 bytes, updated every frame. Per-particle data goes in a storage buffer instead.
uv coordinates
Where in a texture to read from, expressed as fractions of its size: (0,0) is the top-left corner, (1,1) the bottom-right, regardless of how many pixels it actually has. Each glyph in the atlas stores four of them — its rectangle's two corners — computed once at build time, which is why changing the font size needs no shader change. The letters u and v are used simply because x, y and z were taken.
vertex
One corner of a shape. GPUs draw everything as triangles between vertices. Our particle quad = 2 triangles = 6 vertex-shader runs per particle (two corners are visited twice).
vsync / Fifo
Synchronizing presentation to the monitor's refresh. In wgpu it's the Fifo present mode (the default, and the only one guaranteed everywhere): finished frames queue up and are shown one per refresh; when the queue is full, your program waits. Gives smooth, tear-free output and free CPU throttling — for the drawing thread only.
Vulkan
One of the low-level "languages" GPU drivers speak (others: DirectX 12, Metal). wgpu translates our calls into whichever one your platform has — on a Windows + NVIDIA box it picks Vulkan. You never write Vulkan yourself here.
WGSL
WebGPU Shading Language — the language shaders are written in for wgpu. Rust-ish syntax, but a separate, much smaller language compiled by the GPU driver. Chapter 14 is a full tour.
winit
The Rust crate for windows and input: creates the window, delivers every OS event (mouse, keyboard, resize) to our App. Cross-platform; knows nothing about drawing.
world space / screen space
World space: the simulation's own coordinate system, in "world units" — where particles actually live, forever, regardless of any window. Screen space (in this codebase): physical pixels measured from the window's center, +y up. The camera converts world → screen; the shader converts screen → clip.
