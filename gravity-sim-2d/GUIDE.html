gravity-sim-2d · rust + wgpu

Gravity Sim, Explained

A walk through every file of this codebase: a 2D n-body gravity simulator written in Rust on winit and wgpu. It assumes you can read Rust at an entry level (ownership, enums, traits, closures) and know nothing in particular about GPUs, real-time simulation, or font rendering. By the end you will know exactly what happens between "two particles attract" and "pixels change".

fig. 0: the kind of thing the default config produces. orbits, mergers, and a heavy centre.

How to read this: the numbered chapters tell one story in order. Inside each chapter, ▸ deep dive panels unfold the actual code line by line. Open them when you want the detail, skip them when you don't. Gold boxes cover the Rust that goes beyond the entry level. Blue boxes cover GPU concepts. Teal boxes answer "ok, but why is it built this way".

01

What you're looking at

When you run cargo run, this program does six things:

  1. Reads a config file, ~/.config/gravity-sim-2d/app-config.json, written for you the first time the program runs, together with a JSON Schema that teaches your editor every valid key. Window size, zoom limits, the gravitational constant, how many particles to make and where. Anything missing or broken falls back to a default on its own, so one bad value never costs you the rest of the file. (Outright broken JSON syntax is the one mistake that still loses the whole file to defaults; chapter 6 draws the line precisely.) The terminal prints the file's full path, Using config: …/.config/gravity-sim-2d/app-config.json, so there is never a mystery about which file is in effect.
  2. Builds a cloud of particles: sampled into a shape chosen in the config (disc, ring, clusters, sunflower spiral), given masses, pushed apart until no two of them overlap, and then given velocities. Alternatively the config can list exact particles by hand and skip the randomness entirely.
  3. Starts the simulation on its own thread, ticking at a configured rate (60 per second by default), completely independent of the monitor. Each tick computes real Newtonian gravity between every pair of particles and integrates the motion. Particles that touch merge into one, conserving mass and momentum.
  4. Finds a graphics card and prints which one it got, something like Using GPU: NVIDIA GeForce RTX 3080 (Vulkan). It asks for the high-performance adapter, so on a laptop with two GPUs the discrete one wins.
  5. Draws, forever: it repaints the window from scratch in lockstep with the monitor's refresh, showing whatever the simulation last published. Resizing shows more or less of the world; it never scales the scene.
  6. Draws an overlay on top: two panels of text in the top corners, telling you what the simulation is doing and which keys do what. Rendered from a font bundled into the binary, by code this project wrote itself (chapter 17).

The default config that gets written on first run produces a gaussian cluster of 100 light particles with orbital starting velocities and a modest gravitational constant. Left alone, it swirls, clumps, and slowly merges itself into fewer, heavier, redder bodies. The particles line in the overlay counts down as it happens.

one sharp edge

The config's simulation.method accepts three values: "Naive", "BarnesHut" and "Multipole". Only the first is implemented. The other two are todo!() stubs in src/simulation/world.rs, which means selecting them doesn't fail at load time; the simulation thread panics on its first tick. The window keeps running, frozen on the initial state, with the panic message on stderr. Chapter 9 shows the stubs and chapter 19 talks about what would fill them.

Chapter 6 walks through the trick.

why though?

Why two separate big libraries for one window? Because the OS and the GPU are genuinely separate machines with separate rules. winit's job ends where the inside of the window begins; wgpu's job is only the inside. The single point where they meet is called a surface, wgpu's name for "the drawable part of a window".

02

Two computers in your computer

Everything in this codebase makes sense once you accept one fact: a PC contains two very different computers, and this program runs on both at once.

The CPU is a few extremely capable cores. It runs the operating system, the Rust code, everything. It's great at complicated, branching, one-thing-after-another logic. This program uses two of its cores at once: one thread ticks the simulation, one runs the window (chapter 3).

The GPU is thousands of simple cores. Each one is slow on its own, but they all run the same small program at the same time on different data. Drawing is exactly that shape of problem ("for each of the default window's 640,000 pixels, decide a color"), so give each core a pixel and let them all go at once.

That small program is called a shader. The one that draws particles lives in src/gpu/shader.wgsl, written in a language called WGSL. Chapter 16 dissects it line by line. There is a second one, src/ui/ui.wgsl, for the text overlay, and chapter 17 explains why it is a separate file rather than two more functions in the first.

Worth being precise about where the physics happens today: on the CPU. Every tick, the simulation thread computes accelerations for every pair of particles in plain Rust (src/simulation/world.rs). The GPU only ever receives finished positions, sizes and colours. Chapter 19 sketches what it would take to move the force calculation onto the GPU, which is the reason this project is GPU-first in its architecture even while the math is CPU-side.

GPU concept

Why can't the CPU just draw? It can, and old software did. But "set 640,000 pixels, 144 times a second, while also integrating gravity" is a lot of repetitive work, and the CPU does it one pixel at a time. The GPU does thousands at a time. The n-body force calculation ("compute accelerations for 100,000 particles") has exactly the same shape, which is why it is the obvious next tenant.

check yourself
You bump amount from 100 to 50,000. Which of the two computers has to work harder?

Overwhelmingly the CPU. The naive gravity method is O(n²): 50,000 particles is 2.5 billion pair evaluations per tick, on one thread, and the tick rate will collapse (visibly: the tps number in the title drops while fps stays put). The GPU draws 50,000 instances instead of 100 and barely notices. The startup cost of packing them without overlap is CPU too (chapter 11).

Can the Rust code read a variable that lives in the shader?

No. Separate programs, separate processors, separate memory. The only communication is explicit: the CPU sends bytes (buffers, commands), the GPU produces an image. That's why chapter 15 makes such a fuss about copying structs into buffers.

03

Two clocks, not one

The window is not a painting; it's a flipbook. The program produces a complete new image, a frame, over and over, and the monitor shows each one until the next arrives. Nothing on screen "stays"; if it's visible, it's because it was redrawn this frame, from scratch, again.

The simulation is also a flipbook, but a different one. It advances in ticks of a fixed size, 1/60th of a second of simulated time by default, on a thread that has never heard of the monitor. These two rates have nothing to do with each other, and that is a design decision, not an accident.

Why not just tick once per frame?

Because then the physics would depend on the monitor. A 165 Hz screen would run the universe 2.75 times faster than a 60 Hz one; alt-tabbing would freeze time; a dropped frame would be a dropped moment of gravity. And integrating with a variable step is numerically worse: orbits that are stable at a constant 1/60 s drift and blow up when the step keeps changing size. Now that the tick does real integration (velocity += acceleration × dt), this stopped being a theoretical argument.

So src/simulation/runner.rs gives the world its own thread and its own fixed-timestep clock, and the window becomes a viewer: at each vsync it asks "anything new?", takes it if so, and draws.

why though? the alternative

There is a single-threaded version of this: keep an accumulator in the redraw handler, add the frame time to it, and run while accumulator >= TICK { tick(); accumulator -= TICK; }. It's simpler, and for many games it's the right answer. It also means a tick can never run while a frame is being drawn; the two share a core, so a slow tick is a dropped frame. This project chose the thread because n-body ticks get arbitrarily expensive as the particle count grows, and that coupling is exactly what you don't want.

A third dial: how fast that clock runs

The tick size is fixed; that is the whole point above, and nothing you press changes it. What the arrow keys change is how much wall-clock time passes between ticks. At speed +2x the thread aims for a deadline every 8.3 ms instead of every 16.7 ms; each tick still integrates exactly 1/60 s of simulated time. The physics resolution is untouched; only the pace is.

That distinction is the reason reverse is even possible. Running the world backwards means feeding the tick a negative dt, a step of −1/60 s, not running the loop backwards in time. Chapter 9 has the whole mechanism, and also the honest caveat: with merging collisions in play, reverse is no longer a perfect rewind.

why though? three numbers that all sound like "speed"

Keep these apart or nothing later makes sense:

fps is how often the window is redrawn. The monitor decides it. Pausing does not change it; a paused sim still redraws at full refresh rate, it just keeps drawing the same thing.

tickRate (config) is the size of one step of simulated time, and the base rate ticks are aimed at. Changing it changes the physics resolution.

speed (arrow keys) is a multiplier on that base rate, and a sign. It changes nothing about the physics; only how often, and in which direction, steps happen. tps, the second number in the title bar, is what you actually get: roughly tickRate × speed, and negative in reverse.

Who keeps the drawing loop spinning?

winit is event-driven: it sleeps until something happens. So how does the window redraw continuously? At the end of every draw, src/app.rs calls request_redraw(): "wake me up to draw again". That would spin at 100% CPU, except for one elegant brake: the surface is configured in Fifo mode (chapter 14), which means "presenting a finished image waits for the monitor's next refresh". That wait is vsync. Free, perfectly-paced throttling, for the drawing only.

One extra wrinkle: some platforms stop delivering redraw events entirely while the window is completely covered. The chain of "each redraw requests the next" would break and never restart. That is why app.rs also handles Occluded(false) ("the window just became visible again") with one more request_redraw(): it re-primes the loop.

check yourself
You minimise the window. What happens to the simulation?

Nothing. It keeps ticking at 60 tps on its thread, gravity and mergers included. Redraws stop, so snapshots pile up in the slot and get overwritten; each new one simply replaces the last. Restore the window and you see the present, not a backlog.

The monitor is 144 Hz and tickRate is 60. Roughly what fraction of frames get a fresh snapshot?

About 60/144 ≈ 42%. The other ~58% call try_recv(), get None, and redraw the shapes already sitting in the GPU buffer. That's not a waste; it's how the camera stays responsive at full refresh rate even when the world is slow.

You hit Space. What does the fps number do, and what does the tps number do?

fps doesn't move; the window is still redrawing at the refresh rate, still panning and zooming normally, just drawing an unchanging world. tps falls to 0, because ticks stop happening. If the two rates were coupled, pausing the world would freeze the camera too, and you could no longer look around a frozen scene, which is most of what pausing is for.

What stops the redraw loop from using 100% of a CPU core?

Vsync. Presenting in Fifo mode blocks until the monitor is ready, so the loop naturally runs at the refresh rate. (The simulation thread throttles itself differently: chapter 9.)

Rust: thin mod.rs files

check yourself
Which object would you ask: "make me a bigger buffer, the particle count grew"?

The Device: it creates all resources. renderer.rs does exactly that in update_shapes, and then has to rebuild the bind group too, because the old one still points at the buffer that just went away.

Why do Surface and Adapter both come straight from the Instance?

They're independent facts about the machine: the Surface is about the window, the Adapter is about the GPU. They only meet later, when the code asks "which adapters can draw to this surface" and then configures the surface using the chosen device.

06

config/ + build.rs: starting up

The program starts in a 25-line file:

Four moves. Install the logger (wgpu reports most mistakes through Rust's log system, and with no logger installed those reports go nowhere). Load the config, which also returns the path of the file it used so the overlay can display it later. Build the event loop. Hand control to App, which never returns until quit. Note that App::new runs before run_app: by the time winit takes over, the particle cloud exists and the simulation thread is already ticking. There is no window yet; physics does not need one.

Rust: the lifetime in App<'a>

App holds config: &'a AppConfig and config_file: Option<&'a str>: borrows, not copies. The 'a writes down "this App may not outlive the values it points at". Both are locals in main created before app and dropped after it, so the rule holds and the compiler proves it. No reference counting, no cloning a config that only ever needs one owner.

Where the config lives, and who puts it there

config/store.rs owns the filesystem side. The settings live at ~/.config/gravity-sim-2d/app-config.json: the same layout on every OS, including Windows, where ~ is the user profile folder. Not %APPDATA%, not the XDG dance; one predictable place to look when an edit isn't taking effect.

Two files, two very different write policies, and the asymmetry is the design:

  • The config is written once and never again. include_str! bakes the repo's app-config.json into the binary as a template; a machine without a config gets a copy, and from then on the file belongs to the user.
  • The schema is regenerated every launch it drifts. super::schema() produces the schema text fresh from the Rust types, compares it byte-for-byte with what's on disk, and rewrites only on difference. A schema from an older build, a deleted schema, a hand-edited schema: all silently repaired, because the schema describes what this binary understands, not what the user wants.

If any of this fails (no home directory, disk error), open() returns None and load() parses the embedded template instead, labelled the built-in defaults. The program always starts.

The config file itself

Three naming conventions coexist here, and each is deliberate. Section keys are camelCase (tickRate) to read like JSON. Enum tags are PascalCase ("Circle", "Merge") because they are serde's default encoding of Rust enum variants: a bare string for a variant with no data, a one-key object for a variant that carries some. Enum fields stay snake_case (angular_speed) because no rename attribute touches them.

One subtlety worth knowing: this template is not the same thing as the code's Default impls. AppConfig::default() describes a 1280×720 window over a radius-1000 uniform cloud with masses up to 2000; the template is a curated demo scene, a small gaussian cluster on orbital velocities in an 800×800 window. Delete a section from your config file and you get the code default for that section, which may not be what the template shipped.

Parsing: one bad key shouldn't cost you the file

The obvious way to read the file is serde_json::from_str::<AppConfig>(&text)?, one call, done. But then a single typo anywhere means nothing loads, and you get one error message about one line. config/partial.rs takes the tedious road instead: parse the file into a generic JSON tree, then walk it key by key, and when a key is missing or unparseable, substitute that field's own default and print exactly which dotted path was bad. deep dive: how a section wires itself up

Every section struct implements the trait the same way: warn about unrecognised keys, take your own defaults, then read each key with leaf.

A few sections add a second validation layer on top, for values that would break arithmetic downstream. config/simulation.rs guards the number the runner divides by:

tick_period() computes 1.0 / tick_rate and hands it to Duration::from_secs_f32, which panics on a negative or NaN input. Catching it here means the simulation thread can treat its period as always sane. The same pattern guards maxCatchUpTicks (silently clamped to at least 1), fontSize (at least 4, below which glyphs stop being glyphs), and all three colors thresholds (finite and positive, via a little positive() helper local to colors.rs). Notably unguarded: gravitationalConstant. A negative G is repulsive gravity, and the config lets you have it on purpose.

Rust: the Default supertrait

The trait is declared pub trait FromJsonObject: Default. The : Default bound means anything implementing it must also implement Default, which is what lets the generic section helper fall back to T::default() for a missing or mistyped section without knowing anything else about T.

The particles section: an enum where the others are structs

"particles" is the one section that is a choice rather than a bag of knobs: either Generation (describe a cloud, let the app sample one, chapter 11) or Set (write the exact particles out by hand). Its parser hand-implements serde's externally-tagged enum encoding, and handles the case serde would just reject:

deep dive: how a hand-written particle stays valid

A particle in the config is {"position": {"x": ..., "y": ...}, "mass": ..., "velocity": ...}, every field optional. The type that makes that work is worth reading, because it solves three problems in four attributes:

Particle's fields are private, and its constructor clamps mass to non-negative. But serde normally constructs structs field-by-field, bypassing constructors. #[serde(from = "Fields")] reroutes: JSON deserializes into the private shadow struct Fields, then goes through From<Fields> for Particle, which calls Particle::new, which clamps. A config-supplied negative mass arrives already fixed; the invariant survives even hand-written input.

#[serde(default)] on Fields is what makes every field optional ({"mass": 5.0} is a valid particle at rest at the origin), and #[schemars(rename = "Particle")] hides the shadow struct from the generated schema, where the definition appears under the name users expect. Note deny_unknown_fields here does hard-error on a typo'd key, unlike the lenient section parsers; the error is caught one level up by ParticlesConfig::set and degrades to defaults, so the strictness costs the list, not the launch.

The schema pipeline: doc comments that ship

Every config type in this project carries /// doc comments, and they are not commentary: schemars turns them into the description fields of app-config.schema.json, which is what an editor shows on hover and during autocompletion inside the settings file. Delete one and the schema silently loses its documentation. They are product copy that happens to live in source code.

The editor is the linter; the program never refuses to start. Both halves describe the same types, so they can't disagree about what the keys are, only about how rudely to react.

deep dive: schema(), and the two pieces of surgery

Draft-07 is chosen for maximum editor compatibility. Then three fixes to what schemars produced:

Drop the root required list. schemars marks every non-Option field required, but the loader treats every section as optional; removing the array makes the schema agree. Only the root is touched: nested required lists survive, correctly, because inside a leaf enum serde genuinely does require the variant's fields.

The injected property whitelists it. Its runtime mirror is AppConfig's known-keys list, which also includes "$schema"; the two allowances must be kept in sync by hand.

It re-wraps every description: doc comments arrive with hard line breaks from 80-column source, so single newlines inside a paragraph become spaces while blank-line paragraph breaks survive. And it gives each oneOf branch (schemars' encoding of an enum) a "title" named after its variant, detected by a neat slice pattern: a branch whose required array is exactly one string is an externally-tagged variant, and that string is its name. The schema is generated at compile time too, so the copy checked into the repo always matches the Rust types. build.rs is ordinary Rust that cargo compiles and runs before the crate itself, and its problem is that at that moment the crate doesn't exist yet: it can't use gravity_sim_2d::config. So it rebuilds a miniature of the module tree by textually including the same source files:

The included files contain paths like use crate::config::partial::leaf and use crate::math::Vec2; inside the build script, crate means the build script, so those paths must resolve against its module tree. Hence the mirror, and hence the two extra passengers: particles.rs mentions Particle, which mentions Vec2, so both files ride along. This is also why bytemuck is a build dependency: Vec2 implements bytemuck's Pod for the GPU's benefit (a hand-written impl, since the struct is generic; chapter 8), and those impls have to compile even in a context that will never touch a GPU.

Two config files stay out of the mirror entirely: store.rs and mod.rs, the filesystem loader, which schema generation never needs. The partial module is different: the included files reference it, so it can't just be omitted, and instead it gets a stub with identical signatures whose bodies do nothing. The build script only needs the config type definitions (for the JsonSchema derives) and their Default impls; no JSON is ever parsed at build time. But the FromJsonObject impls live in the same source files as the types and have to compile, so the trait and helpers must exist. The stub satisfies the type-checker, and its inertness documents that the build script exercises none of the loader.

Two subtleties in ten lines. The schema file is both a rerun trigger and a build output; writing it unconditionally would dirty the trigger on every build and rebuild forever. The compare-before-write converges in one pass. And a write failure is a cargo::warning, not an error, so a read-only checkout still compiles; the schema is a convenience artefact, not a build input.

Put the two halves together and the same schema() function runs at two sync points: compile time keeps the repo copy honest, and store::seed at launch keeps the user's copy honest. One generator, no drift, anywhere.

Construction: the world starts before the window does

Read the order carefully, because it's the one place the whole architecture is visible in a few lines. Generation makes a Vec<Particle>. Scene::init borrows it to build the initial shape list (the renderer will need to know how big a buffer to allocate) and to build the mass-to-colour ramp out of the colors config. Then the Vec is moved into a World, which is moved onto the simulation thread, and from that moment the main thread cannot touch a particle again except through try_recv. The thread is already integrating gravity before a window exists.

config.simulation gets passed twice by value, once to the runner (which keeps the tick period, the catch-up cap and the method, feeding the method back into every tick call) and once to the World (which keeps the gravitational constant and the collision strategy). That works because SimulationConfig derives Copy, and it is quietly the app's entire cross-thread configuration strategy: the config crosses the boundary once, by value, at spawn. No locks, no atomics, no shared settings object. Immutability is the synchronisation.

Rust: move, and why that's the whole safety story here

World::new(particles, ...) takes the Vec by value, so ownership moves into it; then spawn moves the World into a closure that runs on another thread. After those lines the name particles is unusable; the compiler rejects any attempt to read it. That's not a style rule, it's the data race being made impossible to write. Two threads can't accidentally share the particle list, because after the move only one of them has it.

The font field is the odd one out. FontFace::load resolves the configured font path, or falls back to the JetBrains Mono bytes embedded in the binary, so it always succeeds; a bad path just prints a complaint and uses the bundled face. It runs here, at startup, because parsing a font needs neither a window nor a GPU. But it's stored as Option<FontFace>, and the reason is a Rust mechanic worth knowing: Ui::new wants the FontFace by value, and resumed only has &mut self. .take() is how you move a value out of a struct you're only borrowing: it swaps a None in and hands you what was there.

deep dive: resumed, booting the window

Five things worth pausing on:

1. The size is in logical pixels. On a monitor with 125% scaling, winit multiplies by 1.25 and makes a bigger physical window. Everything after this line works in physical pixels.

2. The guard at the top. resumed can fire more than once on some platforms; the early return makes a second call harmless. It also makes the unwrap_or_else on the font unreachable in practice (the only path that could find the Option empty is a second resumed, and the guard returns first); the reload is belt-and-braces, not a live code path.

Rust: Arc, or shared ownership

Rust's core rule: every value has exactly one owner, so the compiler always knows when to free it. But the window genuinely needs two owners: the App (to ask for redraws) and the GPU surface (which draws into it and must never outlive it). Arc, atomically reference counted, is the escape hatch: a counter travels with the value, .clone() makes a new handle and bumps it, and the value is freed when the count hits zero. Rust: async, in one paragraph

An async fn doesn't run when called; it returns a plan (a future) that must be driven by an executor. wgpu makes GPU setup async because on some platforms (the web) you're not allowed to block. On desktop, blocking is fine, and that is the entire job of pollster::block_on.

deep dive: window_event, the actual switchboard

The handler is split into three functions (window_event, redraw, on_window_event) because of a Rust borrowing rule worth understanding, since you will hit it in your own code.

Rust: why the handler is split up

The borrow checker tracks borrows per field inside a single function body: &mut self.gpu, &self.simulation and &self.scene in one arm are three independent borrows, no conflict. The moment you call a method on self, that stops working: a method takes &self or &mut self, which borrows the whole struct, and the compiler can no longer see that it only touches fields you aren't already holding. So the redraw path lives in fn redraw(&mut self), which re-borrows self.gpu on its own terms, and the mouse/resize arms live in on_window_event for the same reason. Same behaviour either way; the split exists purely so each borrow of self.gpu lives and dies inside one function. It's also why on_window_event opens with its own let Some(gpu) = &mut self.gpu even though window_event already checked: the first check was a boolean, this one needs the binding.

Two details in the keyboard pattern do real work:

state: ElementState::Pressed filters out key releases. Without it every key would fire twice, once down, once up, and Space would pause and instantly unpause.

physical_key: PhysicalKey::Code(code) asks for the key's position on the keyboard, not the character it would type. winit offers both: logical_key is what the layout says (on a French AZERTY layout the key where QWERTY has Q produces "a"), while physical_key is derived from the hardware scancode and always calls that key KeyA. For controls you want physical, so Space and the arrows work identically on every layout.

on_key: four keys, and two of them are modal

Every branch is one call into SimulationHandle. This file decides which question to ask and knows nothing about how it's answered: no speed value, no tick counter, no atomics live here. Chapter 9 has all of that.

if !repeat is the whole design of the space bar. Hold a key down and the OS sends a stream of Pressed events, the first genuine and the rest auto-repeats; KeyEvent flags which is which. For the arrows that stream is a feature: hold → and the speed winds up smoothly, one rung per repeat, or the paused world scrubs continuously, ten ticks per repeat. For a toggle it's a disaster: holding Space for a second would flip pause roughly thirty times and land wherever the timing left it. So the space arm carries a match guard: the pattern must match and the condition must hold, otherwise matching continues downward and a repeated space falls through to _ => {}, silently discarded.

The arrows are modal, and that is deliberate interface design. Running, "left and right" is a natural way to say slower and faster. Paused, speed is meaningless (there's nothing to be fast about), and the obvious thing to want is to nudge the frozen world back and forth. Same keys, and the overlay's controls panel rewrites its own description of them every frame, so you always know which mode you're in (chapter 17). Stepping backwards genuinely runs the physics with a negative dt, which since the arrival of merging collisions comes with an honest asterisk that chapter 9 spells out.

redraw: the whole frame in one function

Five steps, and every one of them is conditional except the last:

  • The snapshot is optional. When the simulation hasn't published since the last frame, the sync and the upload are skipped entirely. The GPU still holds the previous shapes, so drawing them again costs nothing extra. While paused, this is every frame.
  • The rate sample is optional. sample returns true only once a second, which is when the title bar gets rewritten. Setting a window title is a call into the OS; you don't want it 144 times a second.
  • The overlay rebuild is unconditional, and cheap on purpose: a handful of formatted strings turned into rectangles. Rebuilding it from scratch every frame is what keeps it incapable of being stale (chapter 17).
  • The frame is optional. If acquire_frame returned None, the surface was mid-repair (chapter 14) and this frame is skipped; at full refresh rate nobody notices one missing frame.
  • The redraw request is unconditional. It's the last line no matter what happened above, and it sits outside the if let: a frame that failed to acquire must still schedule the next attempt, or one hiccup would freeze the window forever.

Both passes record into one command encoder and go to the GPU in one submit. The scene pass clears the target and draws the world; the ui pass loads that result back and draws text over the top. The only thing making the overlay appear on top is that its pass was recorded second (chapters 15 and 17). Presentation is gpu.ctx.queue.present(frame): in wgpu 30, presenting is a Queue method that consumes the frame, not a method on the frame itself. The pre_present_notify() call just before it is a winit hint that helps compositors time the frame; winit's docs say to call it exactly there.

Rust: the Status struct, and why it's a copy

ui.prepare could have taken &self.simulation and &self.camera and read what it needed. Instead it takes a flat Status built on the spot: plain numbers, no references, no lifetimes. That costs a copy of a few dozen bytes per frame and buys two things. First, the ui/ module never has to use crate::view::Camera, so it stays a module about text rather than a module about this particular program. Second, it dodges the split-borrow problem from the box above: gpu.ui is mutably borrowed while self.camera and self.simulation are read, and disjoint field borrows only work when the compiler can see the individual fields, which it can here and could not through a method call.

The title bar is a measurement instrument

Frames are counted here; ticks are read from the simulation handle. Once a second the difference becomes two numbers. It's twenty lines of instrumentation, and it's the fastest way to confirm the two clocks really are independent: set tickRate to 15, or to 240, and watch the second number move while the first one doesn't. Or crank amount until the naive O(n²) tick can't hold its rate, and watch tps sag on its own.

Two details are load-bearing. The meter keeps its last values as fields (fps, tps) instead of only returning them, because the overlay redraws every frame and needs a number on all of them; sample returning true just means "these are new". The numbers on screen are therefore up to one second old, which is the point: an instantaneous frame rate is an unreadable flicker.

And ticks is i64, not u64. Run the world backwards and the tick counter decreases, so ticks - self.ticks goes negative. As u64 that subtraction underflows: in a release build it wraps silently to a number around 18 quintillion, and the title bar would report a tick rate with twenty digits. Signed arithmetic simply reports -80 tps, which is both correct and genuinely useful information.

Rust: the two faces of integer overflow

5u64 - 10u64 is not "-5" and it is not undefined behaviour. In a debug build Rust checks every arithmetic operation and panics with "attempt to subtract with overflow". In a release build those checks are compiled out for speed and the value wraps around to u64::MAX - 4. So this exact bug would crash loudly under cargo run and produce silent nonsense under cargo run --release, which is the worst possible way to find out. Choosing the signed type is how you stop having the conversation.

That's what makes rendering continuous: each frame schedules the next one. Vsync keeps this from spinning wildly, because presenting blocks until the monitor wants a new image. It keeps running and keeps drawing the last snapshot forever. math/vec2.rs: the vector everything speaks

Ninety lines that every other module imports. Vec2 replaced the bare [f32; 2] pairs that used to circulate through the codebase, and the interesting question is not "what is a 2D vector" but why this project hand-rolls one instead of pulling in glam or nalgebra.

The answer is in the attribute stack: this one type wears three hats at once, and no off-the-shelf vector type wears all three cleanly.

  • GPU plain-old-data. #[repr(C)] pins the layout to exactly eight bytes, x at offset 0, y at offset 4, no padding, which is precisely the memory layout of a WGSL vec2<f32>. Combined with the Pod/Zeroable impls at the bottom of the file, Vec2 can sit directly inside the structs that get byte-cast into GPU buffers: Shape.center, both renderers' Globals.resolution, the camera's pan.
  • Config and schema type. Serialize, Deserialize and JsonSchema mean a Vec2 can appear in app-config.json as {"x": 1.0, "y": 2.0} (it does, in hand-written particles and in the CommonVector velocity strategy), and the doc comments on the fields become schema descriptions. deny_unknown_fields, declared for serde and schemars separately, makes {"x": 1, "y": 2, "z": 3} a hard error in both the parser and the editor: there is no z in this universe.
  • Simulation math type. Operator overloads so the physics reads like physics: *particle.position() + new_velocity * delta.

The whole API

It is deliberately minimal. Besides the constructor there are exactly three inherent items, all on the f32 instantiation:

And seven operator impls, all component-wise, all generic over T: Add, Sub, Neg, AddAssign, SubAssign, plus Mul<T> and Div<T> for scaling by a scalar. Note the asymmetry: vec * 2.0 compiles, 2.0 * vec does not, because the scalar-on-the-left version would need an impl on f32, which is more ceremony than this project wants. There is no dot product, no normalize, no component-wise multiply, no indexing; nothing needed one yet, and the type grows only when a call site forces it. Where code needs a per-component min or max (the collision grid does), it writes Vec2::new(a.x.min(b.x), a.y.min(b.y)) at the call site.

Everything except the two assignment operators takes self by value (an AddAssign necessarily mutates through &mut self). Vec2 is Copy and eight bytes; passing it in a register is cheaper than passing a pointer to it, and no borrow-checker conversation ever starts.

Rust: default type parameters

pub struct Vec2<T = f32> declares a generic struct whose parameter defaults to f32 when unwritten, so every use site in the codebase just says Vec2. Nothing currently instantiates any other T; the genericity costs nothing (generics are compile-time) and leaves the door open for, say, an integer pixel coordinate later. The operator impls put their bounds on T (T: Add<Output = T> and so on) rather than on the struct, which is the idiomatic shape: the type exists for any T, the arithmetic exists only where it makes sense.

The two unsafe lines

Everywhere else in the project, Pod and Zeroable come from #[derive(...)], where the bytemuck crate proves the claim mechanically and refuses to compile if the struct has hidden padding. The derive cannot handle a generic struct (it would have to prove the claim for every possible T), so these two impls are written by hand, and unsafe is Rust making the author sign for it: "I assert that any bit pattern is a valid Vec2<T> whenever it's a valid pair of Ts". The assertion holds because the struct is repr(C) with two identical fields and no padding for any T whose alignment divides its size, which is true of every Pod primitive. The bounds do the real work: you can only claim Vec2<T>: Pod when T: Pod already holds.

This is the one place in the entire codebase the word unsafe appears. Worth appreciating: a windowed, multithreaded GPU program, and the sum total of its unsafe surface is two empty impl blocks that say a pair of floats is a pair of floats. Everything else that is traditionally dangerous (sharing state across threads, handing memory to another processor) is done through safe abstractions.

check yourself
Why is there a #[serde(deny_unknown_fields)] here when the config loader is famously lenient?

Leniency lives at the section level, where each key falls back independently. A Vec2 is a leaf: it gets deserialized atomically by serde inside a leaf() call, and there is no meaningful "partial vector" to fall back to. Strict rejection turns a typo'd {"x": 1, "why": 2} into one clear error, which the caller then converts into "that whole setting reverts to default" with a warning. Strict leaf, lenient tree.

The camera's pan is a Vec2 in pixels; a particle's position is a Vec2 in world units. Should those be different types?

A stricter design would wrap them (struct Pixels(Vec2), struct World(Vec2)) so the compiler rejects mixing them. This project keeps one type and relies on the shader's single conversion formula (chapter 16) as the only meeting point, which is a reasonable trade at this size: the newtype ceremony would touch every file for one class of bug that currently has exactly one place to happen.

09

simulation/: gravity on a clock

Five files of substance, plus a thin mod.rs of re-exports. particle.rs is the atom, world.rs is the state and the physics that changes it, collision.rs merges bodies that touch (big enough to get chapter 10 to itself), runner.rs is the thread plus the hand-off, and speed.rs is the ladder the arrow keys walk. None of them import winit or wgpu; the simulation could run headless tomorrow.

The atom

Twenty bytes: two floats of position, one of mass, two of velocity. The fields are private, and that privacy is doing a job: every path that sets a mass (the constructor, the setter, and the serde route from chapter 6 that funnels config-written particles through Particle::new) clamps it non-negative. Nothing in the codebase can construct a particle with negative mass, so nothing downstream has to check.

Worth knowing what this struct is not: it is not #[repr(C)] and not bytemuck::Pod. Particles never travel to the GPU directly; the renderer's Shape (chapter 15) is the GPU-facing type, and Scene::sync is the translation. The Pod machinery lives one level down, on Vec2 itself.

why though? radius = √mass / 2

Mass is treated as area, not diameter. Four times the mass draws twice as wide, which is what the eye expects from a 2D disc of uniform density. The important part is that this rule lives in one function, and now four different subsystems lean on it: the renderer sizes discs with it (chapter 15), the generation overlap pass decides how much room each particle needs with it (chapter 11), the collision pass uses it as the contact distance (chapter 10), and the merge math relies on it for a satisfying property: because area is proportional to mass, a merged particle is drawn exactly as large as the discs it swallowed put together. Put the formula in two places and one day they disagree.

The world, and its tick

The bookkeeping at the top encodes the time model. delta is allowed to be negative; that is how reverse works, and the tick counter moves by ±1 accordingly, a signed position in the world's history rather than a count of work done. A delta of exactly zero returns early, because otherwise the sign test would have to invent an answer for "which way did we just go". The collider lives on the struct, rather than being built per tick, so its internal scratch buffers are reused forever with no steady-state allocation. And elapsed is currently written and never read: a leftover ledger, kept presumably for debugging or future use.

barnes_hut and multipole are single-line todo!() stubs. The enum variants exist, the config accepts them, the schema documents them, and selecting one panics the simulation thread on its first tick. Chapter 7's quiz covers what that looks like from the window's side (a frozen but responsive app); chapter 19 covers what would fill the stubs.

The gravity

Newton, in two functions. g_accel_vector computes the acceleration one particle feels from one other. The textbook says a = G · m / d² pointing along the line between them; the code says offset × G · m / d³, which is the same thing with the direction folded in: dividing the un-normalised offset by one extra power of distance is the normalisation, so there's no separate "unit vector" step. Only the target's mass appears, exactly as in physics: the force is proportional to both masses, but acceleration divides your own mass back out. A massless particle falls like anything else and pulls on nothing.

G comes from the config (gravitationalConstant, default 4.0) and is deliberately not the real 6.674×10−11; the world runs in arbitrary units, and 4.0 makes the demo scene move on a human timescale. The config doesn't even insist it be positive: set it negative and gravity pushes.

naive runs the pair formula in two strict phases, and the separation is a correctness decision, not a style one. Phase one computes every acceleration against the pre-step positions and collects them into a scratch list. Phase two applies them. Interleave the phases (move particle 0, then compute particle 1's force from the already-moved particle 0) and the result depends on array order, and momentum quietly stops being conserved. Compute-all-then-move-all is the simultaneity of "all forces act at the same instant" translated into code.

why though? semi-implicit Euler

Phase two updates velocity first, then position using the new velocity. That ordering has a name, semi-implicit (or symplectic) Euler, and it is a genuinely different integrator from the version with the lines swapped. Plain explicit Euler (x += v_old · dt then v += a · dt) systematically injects energy: orbits spiral outward, slowly and unstoppably. The semi-implicit variant makes an error of the same size but with a bounded, oscillating energy drift, so orbits stay orbits for a very long time. Same cost, one line reordered, categorically better behaviour. It is the standard first choice for orbital mechanics.

no softening, and what stands in for it

The classic n-body hazard: as two particles approach, 1/d² heads to infinity, one tick applies a colossal acceleration, and both bodies slingshot across the universe. The classic fix is softening: compute d² + ε² instead of d² so the force has a ceiling. This code does not do that. Its only guard is the exact test distance == 0.0, which exists to skip self-interaction (a particle paired with itself has distance zero) and exactly coincident particles, where there is no direction to pull along.

What stands in for softening is the collision system: with collisions: "Merge", two particles whose discs overlap fuse before their centres can get pathologically close, so the divergent regime is mostly unreachable. That is a real cross-feature dependency worth stating plainly: switch the config to "Ignore" and close passes become numerically violent slingshots, not because anything broke but because the guard rail was the merging.

Cost: the nested iterators make this O(n²) per tick, every pair evaluated twice (once from each side). At the default 100 particles that is 10,000 cheap evaluations, 60 times a second, nothing. At 10,000 particles it is 100 million per tick, and the tps counter will tell you exactly how much the machine minds. The accelerations vector is also allocated fresh every tick, an easy future win the collider already demonstrates the pattern for.

why though? is reverse still honest?

Mostly, and the caveats are worth understanding because they're fundamental, not bugs. A symplectic integrator is time-reversible in exact arithmetic: step forward with +dt, then backward with −dt, and you land where you started. In floating point the rounding isn't symmetric, so the return trip drifts by a tiny amount that compounds per step; ten ticks back and forth is visually perfect, ten thousand is not. And merging is strictly one-way: the collider fires regardless of dt's sign, and nothing stores what the ingredients were. Run time backwards after a merger and you replay the motion in reverse, but the merged body stays merged. The config's own schema documentation says it in one line: "reversing the speed dial replays the motion, not the merges."

The thread

runner.rs has two jobs that pull in opposite directions, hit the tick rate accurately and hand results to another thread without ever making either side wait, plus one supporting craft the first depends on: sleeping precisely.

Job one: hitting the rate

base_period is what tickRate asked for: 16.67 ms at 60 tps. period is that divided by the magnitude of the speed; at 2x the thread aims for a deadline every 8.3 ms. signed_delta is the untouched delta carrying the speed's sign. Between them they state the thing worth memorising: speed changes how often ticks happen and which way they point, never how big they are. Wind the speed to 10x and you have not changed the physics by one bit; you have asked for the same steps, sooner.

The line that matters most is next_tick += period. The naive version, next_tick = Instant::now() + period, would let every microsecond of lateness accumulate, and after a minute the sim would run measurably slow. Adding a fixed period to the previous deadline means a tick that runs 3 ms long simply leaves 3 ms less sleep before the next one; the average stays exact.

max_catch_up (default 5) is the escape hatch for when exactness isn't possible. If the machine genuinely can't tick fast enough, running the whole backlog would make each pass longer, which grows the backlog: the classic death spiral. After at most five back-to-back ticks the loop abandons the debt and re-bases the clock. The simulation runs slower than real time, deliberately and visibly (the tps number drops), instead of locking up. With n-body cost scaling as O(n²), this stopped being a theoretical safeguard the day gravity landed. Note also that a catch-up burst publishes once, at the end: the renderer only ever sees whole, settled states, never a mid-burst frame.

The two branches at the top are the two ways of not ticking, kept separate on purpose. Paused is a mode entered with Space, and it enables manual stepping. Speed zero is just a rung of the ladder you happened to land on while walking toward reverse. They look identical on screen for a moment (nothing moves), but only the first one lets the arrows step, and the overlay labels them differently (PAUSED versus a speed reading of halted). Both branches re-base next_tick on every idle pass, and that line is easy to leave out: without it, a ten-second pause leaves the deadline six hundred ticks in the past, and the instant you resume, the catch-up loop sprints to repay a debt that shouldn't exist. Re-basing states the policy: time spent paused is not time the simulation owes.

Job two: sleeping accurately

the thing that bites everyone on Windows

thread::sleep(16.6ms) does not wake you up in 16.6 ms. It wakes you up in at least that, rounded up to the OS timer granularity, which has historically been as coarse as 15.6 ms on Windows. Modern runtimes use high-resolution timers and get much closer, but "close to" isn't "exactly". Sleeping to 500 µs short of the deadline and burning the rest in a spin_loop costs a sliver of one core and makes the pacing boringly reliable.

The MAX_SLEEP cap is unrelated: it keeps each individual sleep under 50 ms so that a slow tick rate (say tickRate: 0.5) doesn't make quitting take two seconds. The loop re-checks the running flag after every chunk, and the paused flag too: at a slow tick rate the thread may be asleep for seconds at a stretch, and a Space that only takes effect when the nap happens to end feels broken. One extra atomic read per 50 ms chunk is free, and it makes pausing feel instantaneous at any tick rate.

Job three: the hand-off

The main thread needs to read particles; the simulation thread needs to write them. The obvious answer, wrap the Vec in a Mutex and let the renderer lock it while uploading, is wrong: the renderer would hold that lock for the duration of a GPU upload, and the simulation would stall behind it, or vice versa. What you want is for neither side to ever wait for the other. There is no channel here, despite what the shape suggests; it is a hand-rolled single-slot mailbox:

Rust: mem::swap, and why it's free

A Vec is three machine words on the stack (a pointer to the heap, a length, a capacity) and the actual elements live somewhere else. mem::swap(&mut a, &mut b) exchanges those three words. A hundred thousand particles behind the pointer don't move an inch; they just belong to a different variable now. This is why "swap instead of copy" is such a common Rust pattern for hand-offs, and why holding a lock across one is harmless.

The fresh flag is what makes it drop-oldest rather than a queue. The writer sets it on every publish; the reader clears it on every receive. Publish twice between two frames and the first snapshot is simply overwritten; it was never wanted. Read twice between two ticks and the second read returns None. And one nice touch in spawn: the slot starts pre-filled with the initial particles and fresh: true, so the very first frame has something to draw even if the thread hasn't ticked yet.

Rust: a poisoned Mutex

slot.lock() returns a Result, not the guard directly. If a thread panicked while holding this lock, Rust marks it "poisoned" and every later lock() returns Err, on the theory that the protected data might be half-updated. unwrap_or_else(PoisonError::into_inner) says "give me the data anyway". That's the right call here, and only because of what's inside: a Vec, a counter and a bool, all fully written before the guard drops, so there is no observable half-state. One nuance worth getting right: the todo!() panic from chapter 7's quiz doesn't actually poison this lock, because it fires mid-tick, when no guard is held; the window survives simply because a child thread's panic doesn't propagate, and try_recv keeps serving the last published snapshot. The recovery here is insurance against the rarer case of a panic landing inside the critical section itself.

The control knobs: four atomics

This struct is the complete list of what the two threads can see of each other. The snapshot data goes through the mutex; everything else is a single machine word that either side can read or write with no lock, no waiting, and no way to observe a half-written value.

Rust: there is no AtomicF32

The standard library provides atomic integers and AtomicBool, and that's it; hardware atomics are defined over integer words. The standard workaround is what speed does: store the float's bit pattern in an AtomicU32 with f32::to_bits() and reconstitute it with f32::from_bits(). That is not a conversion and loses nothing: an f32 is exactly 32 bits, and those two functions reinterpret the same bits under a different type. It's the same trick as bytemuck in chapter 15, at the scale of one number.

Rust: Ordering::Relaxed, and why it's enough

Every atomic operation makes you name an Ordering, and the honest short answer is "this is the hardest topic in concurrent programming, and you almost always want Relaxed or SeqCst". Relaxed guarantees the one variable is never torn (you always read a value somebody actually wrote), and guarantees nothing about the order of other memory around it.

That is exactly the right level here, because none of these four atomics is used to publish other data. They are self-contained facts: a bool that means paused, a bit pattern that means speed. The worst consequence of a stale read is the sim thread reacting one loop iteration late, which is invisible. The one place ordering genuinely matters ("the particle buffer I just swapped in is fully written before you read it") is handled by the Mutex, whose lock and unlock provide that guarantee as part of the deal. Reach for a stronger ordering the moment an atomic starts meaning "the thing over there is ready now".

Stepping while paused: draining, not reading

Two functions, and a compact lesson in atomics. fetch_add, not store: the window thread doesn't say "the pending step count is now 10", it says "add 10 to whatever is there". Press → three times inside one 2 ms nap and the counter holds 30 and the world moves 30 ticks; with store, two of those presses would be silently overwritten. And because the value is signed, a left press and a right press in the same window cancel to zero, which is exactly the right answer.

swap(0), not load then store(0): the same bug in a different hat. swap reads the old value and writes the new one as a single indivisible operation. Split it into a load and a store and there is a gap, nanoseconds wide but real, in which a key press can land after the read and be wiped by the write. Every arrow press that ever went missing in a program like this went missing exactly there.

Rust: unsigned_abs and the i32::MIN trap

steps.unsigned_abs() looks like pedantry over .abs(), and isn't. i32 spans one more negative value than positive, so i32::MIN.abs() has no representable answer: it panics in debug, wraps in release. unsigned_abs returns u32, which has room, and cannot fail for any input. Reaching the trap would take holding an arrow key for years, but the version with no edge case costs exactly the same to write.

Shutting down

Nothing calls this explicitly. When run_app returns, App is dropped, which drops its SimulationHandle, which flips the flag and waits for the thread. The Option<JoinHandle> dance exists because join consumes the handle by value and drop only has &mut self; .take() is, once again, how you move a value out of a struct you're only borrowing. let _ = thread.join() deliberately ignores the result, so even a thread that died panicking gets collected without taking the shutdown with it.

The speed ladder, and the reason it has a zero in the middle

The requirement sounds simple: each press changes the speed by a factor of 1.1, it must be able to run backwards, and it clamps at ±10. Try to build that with a plain multiplier and you hit a wall: press "slower" from 1.0 and you get 0.909, then 0.826, then 0.751, and the sequence approaches zero forever without arriving, because a positive number divided by 1.1 is still positive. Multiplication cannot change a sign. There is no number of presses that gets from +1.0 to −1.0, and none that reaches a full stop either.

So the rungs are numbered with an integer, and the number zero is given a meaning of its own:

Read value carefully; it's four lines doing three things. signum() collapses the index to −1, 0 or +1: which side of the bridge are we on. Zero gets its own arm and a literal 0.0. abs() - 1 is the off-by-one that makes index 1 mean normal speed: rung 1 is FACTOR to the power zero, which is 1.0. And .min(LIMIT) clamps the magnitude before the sign is applied, so one expression serves both ends of the ladder and the reverse half is guaranteed to mirror the forward half.

Rust: a const block that runs a loop

MAX_INDEX is not a number someone worked out on a calculator; it's a while loop the compiler runs at compile time and bakes into the binary as a literal. Rust's const evaluator handles loops, conditionals and (since 1.82) floating-point arithmetic, so this is ordinary code that simply never executes at runtime.

Why bother? It keeps FACTOR and LIMIT the only two knobs. Change FACTOR to 1.5 and the ladder re-derives its own length; hard-code 26 and you've planted a bug that appears the day someone edits a constant fifteen lines up. With today's numbers: 1.124 ≈ 9.85, still under the limit, so the loop continues; 1.125 ≈ 10.83 trips it, giving MAX_INDEX = 26. That last rung's raw magnitude overshoots and is clamped down to exactly 10.0, so ±10 is genuinely reachable rather than merely approached. 53 rungs in total: 26 each way, plus the stop.

why though? where the ladder doesn't go

There is no slow motion. The slowest non-zero speed on this ladder is 1.0x in either direction, because every rung away from the stop multiplies the magnitude; walking down from +1.00x goes straight to halted, then out into −1.00x. Fractional speeds would mean letting the exponent go below zero and giving LIMIT a companion minimum. It isn't there because "slower than real time" is what tickRate is for, and stepping while paused covers "I want to look at one moment" more precisely than any slow-motion dial would.

One more design split worth noticing: the Speed value lives on the handle, a main-thread object, not in Shared. The simulation thread never sees an index and has never heard of a ladder; it reads one f32 and multiplies. The rung you're standing on is interface state, in the same category as which panel the overlay draws; the number is the only part that is physics. That is also why faster and slower take &mut self (they move an ordinary field) while toggle_pause and step take plain &self: atomics provide interior mutability, mutation through a shared reference, because being poked from several places is their entire purpose.

the read-modify-write in toggle_pause

toggle_pause loads the flag, inverts it, stores it back: three steps, not one, so two threads calling it simultaneously could both read false and both write true, losing a toggle. The airtight version is fetch_xor(true, Ordering::Relaxed). It's safe as written because exactly one thread ever calls it: the window thread, from inside a keyboard event, and winit delivers those one at a time. Worth knowing anyway; the day this gets called from a second place (a config hot-reload, a network command), the bug appears, and it's the kind that happens once an hour and never in a debugger.

check yourself
Why does the copy in publish happen before the lock is taken, not after?

Because that copy is the only expensive thing in the whole hand-off, O(number of particles). Doing it inside the lock would make the main thread wait for it at exactly the wrong moment. Outside the lock, the main thread's worst case is "wait for three word-sized writes".

Two particles pass within a hair of each other with collisions: "Ignore". What happens, and why doesn't it happen with "Merge"?

With Ignore, 1/d² gets enormous for one tick and both particles are flung outward at high speed: the classic unsoftened-gravity slingshot. With Merge, their discs overlap before the centres get close enough for that, and the collider fuses them into one body at the centre of mass. The merge system is quietly doing softening's job.

You set maxCatchUpTicks to 1000. What have you built?

A death spiral, if the machine ever falls behind, which O(n²) gravity makes easy. A slow patch produces a backlog, running the backlog takes longer than real time, which produces a bigger backlog. The cap converts "hang forever" into "run slower than real time and show it in the title bar".

Why can't the speed just be a float you multiply and divide by 1.1?

Because it could never reach reverse, or a stop. Dividing a positive number by 1.1 gives a smaller positive number, forever, and multiplication can't flip a sign. Numbering the rungs with an integer and defining index 0 as "stopped" gives you a value that is the crossing point, so the ladder walks continuously from +10x to −10x.

You replace steps.swap(0) with steps.load() followed by steps.store(0). What breaks, and how often?

Arrow presses go missing, rarely and unreproducibly. Between the load and the store there's a gap of a few nanoseconds; a press landing in it gets added to a value that is about to be overwritten with zero. You'd hit it perhaps once in a long session, conclude the keyboard is flaky, and never find it. swap has no gap because it is one instruction.

You step 10 ticks back, then 10 forward, while paused. Is the world bit-identical to where it started?

Close, but not guaranteed. Semi-implicit Euler is reversible in exact arithmetic, but floating-point rounding isn't symmetric between the two directions, so tiny differences can survive the round trip. And if a merge fired anywhere in those ten backward ticks (the collider runs regardless of dt's sign), the trip is definitively one-way. For eyeballing a moment, it's plenty; for forensics, it isn't a time machine.

collision.rs: when bodies meet

Every tick, after the integrator has moved everything, World::on_tick asks one question: did any discs end up overlapping? If so, each connected group of overlapping particles collapses into a single body carrying the group's total mass and momentum, sitting at its centre of mass. This file is the answer to that question, and it is the most algorithmic 250 lines in the project: a spatial grid, a union-find, and a weighted reduction, all rebuilt every tick without allocating.

The driver

Every field of Collider is a scratch buffer that persists between ticks purely so it never reallocates; Default gives empty everything and the first tick warms them up. The let Self { grid, parents, ... } = self; destructuring at the top is a borrow-splitting move: it turns one &mut self into five independent mutable borrows, so grid can be iterated while parents is written. (Chapter 7's aside on per-field borrows is the same rule from the other side.)

The pair test itself: two discs overlap when the distance between centres is less than the sum of their radii, tested as length_squared() < contact² to skip the square root. The comparison is strict, so exact tangency does not merge. j <= i makes each unordered pair tested once (and skips the particle finding itself in its own neighbourhood). And the merging flag, fed by whether union actually joined anything new, lets the overwhelmingly common nothing-touched tick exit before any cluster work happens.

Phase 1: the grid

Checking every pair is O(n²), which would double the cost of the tick for nothing: almost all pairs are nowhere near each other. So candidates come from a uniform grid, rebuilt from scratch every resolve. This is the second spatial grid in the project (generation/grid.rs is the first, chapter 11), and the duplication is intentional: that one only ever runs during startup and optimises for simplicity (a Vec of Vecs); this one runs every tick and optimises for allocation behaviour.

The layout this produces is worth naming, because it shows up all over high-performance code: it's a CSR (compressed sparse row) structure, built by counting sort. Instead of one little list per cell, there is one flat items array holding every particle index, grouped by cell, plus a starts array saying where each cell's group begins: cell c's members are items[starts[c]..starts[c+1]]. Three passes build it: count how many land in each cell (into starts, offset by one), turn the counts into running totals (a prefix sum, after which starts is the boundary table), then scatter each particle into its cell's range using cursors as write heads. Two flat arrays, zero per-cell allocations, and iterating a cell is a contiguous slice: the cache-friendliest shape this data can take.

deep dive: choosing the cell size, five constraints in one expression

The cell size is the maximum of five lower bounds, each solving a different failure:

  • 2.0 * widest is the correctness bound. The neighbour search only looks at the 3×3 block of cells around a particle. Two discs can touch at a centre distance of at most r_i + r_j ≤ 2 × widest, so if cells are at least that wide, any touching partner is guaranteed to be within one cell in each axis. Shrink cells below this and the search silently misses pairs; there is no error, just particles passing through each other occasionally.
  • sqrt(width × height / count) is the efficiency bound: cells sized so a roughly uniform cloud averages about one particle per cell.
  • The two extent / count bounds guard degenerate shapes. A nearly collinear cloud has height close to zero, which would make the area-based bound tiny and the column count astronomical; these cap the cell count at roughly the particle count per axis.
  • MIN_CELL_SIZE = 1e-6 handles a cloud of massless particles collapsed to one point: width, height and every radius are zero (the radius bound depends on mass, not position), all four other bounds evaluate to zero, and the division in column_row would otherwise divide by zero.

span adds its own two guards: non-finite or non-positive extents produce one cell, and the cell count per axis is clamped to the particle count (memory stays proportional to n even if geometry says otherwise), plus one spare cell so a particle exactly on the far edge has a home. column_row then clamps the computed cell into range from both ends, making it total even for positions outside the fitted box.

One honest performance note: the correctness bound means a single giant particle among thousands of tiny ones inflates every cell to the giant's diameter, packing many small particles per cell and degrading the pair scan back toward quadratic locally. That is the standard weakness of uniform grids under mixed sizes, and with merging steadily producing giants, it is this code's most likely future bottleneck.

Phase 2: chaining pairs into groups

Overlap is pairwise, but merging has to be transitive: if a touches b and b touches c, all three are one pile, even though a and c never touch. The structure for "maintain disjoint groups under repeated joins" is a union-find (also called disjoint-set), and this is a compact, idiomatic one:

The idea: parents is a forest stored in an array. Every particle starts as its own root (parents[i] == i). Joining two groups means pointing one root at the other; asking "which group is this particle in" means following parent links to the root. Two refinements make it fast:

Path halving. On the way up, find re-points every visited node to its grandparent, so chains flatten as a side effect of being walked. Amortised over a run, lookups become effectively constant time. It's the cheaper cousin of full path compression (which would need a second pass) and gives nearly the same behaviour in three lines.

Rooting at the minimum index. Textbook union-find merges by rank or size to keep trees shallow. This one always does parents[max] = min, deliberately trading a little tree depth for a property the next phase exploits: the root of every group is its lowest-numbered member. Combined with path halving, the depth cost is negligible, and the determinism is worth real money: the output order of merged particles doesn't depend on the order pairs happened to be discovered in.

Phase 3: the merge math

The clustering walk visits particles in index order. The first member of each group to be visited (which, thanks to min-index rooting, shares a root with the group's lowest index) claims a slot in clusters via the slots map (UNCLAIMED = u32::MAX is the sentinel) and becomes the cluster's seed. Then every member, seed included, gets absorbed: count it, add its mass, add its mass-weighted position relative to the seed, add its momentum.

why though? positions relative to the seed

The centre of mass is Σ(m·p)/Σm, so why not accumulate position × mass directly? Precision. An f32 has about 7 significant digits; for a cluster orbiting at coordinates around 10⁵, the products are around 10⁶ and the differences between members (what actually determines the centre) live in the last digit or two: classic catastrophic cancellation. Accumulating (p − p_seed) × m keeps the sums small, because members of a touching cluster are by definition near the seed. The final position adds the small correction back onto the seed's full-precision coordinates. Same math, arranged so the big numbers never meet the small ones.

Cluster::particle has two guards, both earning their keep. A singleton returns the seed unchanged: not "a cluster of one recomputed through the formulas", which would put every untouched particle through a multiply-divide round trip per tick and perturb it in the last bit, but the literal original particle. Particles that don't collide are bit-identical after resolve, which is why running the collider every tick is safe. A zero-total-mass group returns the seed too, because massless particles are legal (chapter 9's clamp allows mass 0) and dividing by their total would produce NaN.

Finally mem::swap(particles, merged) replaces the world's list wholesale, the same three-word swap as the runner's mailbox, and the old list becomes next tick's scratch.

Why is the pair test >= and not >?

The continue fires on distance² >= contact², so merging requires strictly less: genuine overlap, not mere tangency. Two discs at exact contact distance, which is what the generation module's separation pass drives pairs toward, stay separate. Flip it to > and freshly generated clouds could merge on tick one.

What does merging |= union(...) actually accumulate, and why does the early return check it instead of "did any pair overlap"?

union returns true only when two previously separate groups joined. A pair that overlaps but is already in the same group (via some third particle) adds no information. The simulation runs at −1.00x and two bodies drift into each other. Do they merge?

Yes. The collider runs after every tick and never sees dt's sign; overlap is overlap. This is the concrete mechanism behind "reverse is not a rewind": going backwards can create mergers that never happened on the way forward, and nothing can ever undo one.

generation/: building the cloud

This module runs exactly once, before the window exists, and produces the Vec<Particle> the simulation will own forever. It's the only place in the codebase with randomness in it. The entry point is a two-way dispatch on the config's particles section:

A hand-written Set list passes through untouched: no separation, no repositioning, exactly what was typed (modulo the mass clamp that serde already applied in chapter 6). A Generation config runs the three-phase pipeline, and the phase order is load-bearing. Positions and masses first, because the overlap pass needs to know how much room each particle takes, and room comes from mass. Separation second. Velocities last, because two of the velocity strategies are functions of position: Orbital gives each particle a velocity perpendicular to its radius, Radial one pointing along it. Sample those before separation and every particle that got nudged would be orbiting a point it no longer sits on; the demo scene's tidy rotating cluster would shear apart on tick one.

One property worth stating plainly: there is no seed. rand::rng() is the OS-seeded thread-local generator, so two runs of the same config produce different clouds (except Sunflower positions, which use no randomness at all). Threading the single &mut impl Rng through every sampler is exactly what would make the module seedable in one line, if reproducible runs ever became a requirement.

Phase 1: sampling

Every position strategy produces points on the unit disc (radius 1, centred on the origin), and Area::from_unit_disc then stretches that disc into whatever shape the config asked for by multiplying each axis by the area's semi-axes. One set of samplers, written once in disc space, and ellipse support falls out for free: a linear map preserves uniformity, so "uniform on the disc" becomes "uniform per area on the ellipse".

Curious detail: the Area type lives in config/generation.rs (it's a config value, it needs the serde and schema derives), but this impl Area block lives here, with the geometry. Rust allows inherent impls anywhere in the same crate, and the split puts the data definition with the other config types and the behaviour with its only users.

deep dive: the sqrt that stops the clump, and the spiral that needs no rng

The obvious version picks a random angle and a random radius. It looks right and is wrong: it puts far too many points near the centre. The area of a thin ring at radius r grows with r (the ring at r = 0.9 has nine times the area of the ring at r = 0.1, so it deserves nine times the points), but a uniform radius gives every ring the same count. Taking the square root of a uniform value biases it outward by exactly the right amount: the fraction of points inside radius r becomes r², which is precisely the fraction of area inside radius r.

The same square-root logic shows up twice more. Ring inverse-CDF samples r = sqrt(inner² + u × (1 − inner²)), uniform-per-area over the annulus. And Sunflower uses r = sqrt((i + 0.5) / amount) with theta = i × golden_angle, where the golden angle is PI * (3.0 - 5.0_f32.sqrt()), about 137.5°: Vogel's spiral. Equal area per point from the sqrt, no spokes or rings ever forming because the golden angle is as far from any rational fraction of a turn as an angle can be. The + 0.5 keeps point zero off the exact centre.

The gaussian sampler is the module's one true rejection loop: draw a 2D normal (via a hand-rolled Box-Muller transform, whose u1.max(f32::MIN_POSITIVE) guard exists because ln(0) is negative infinity), accept if inside the disc, retry up to 64 times, then give up and return a uniform point. The cap guarantees termination for absurd spreads, where acceptance becomes vanishingly rare and the strategy gracefully degrades toward Uniform. Contrast Clusters, which handles the boundary the other way: it clamps escapees radially onto the rim, so a tight cluster near the edge piles up along the boundary arc.

Rust: &mut impl Rng

Every sampler takes rng: &mut impl Rng rather than reaching for a global. impl Rng in argument position means "some concrete type implementing Rng, decided at compile time": no vtable, fully inlined. The &mut is because generating a number advances the generator's state, and one exclusive borrow threaded everywhere means one stream of randomness with no accidental correlation.

Phase 2: making them not overlap

Sample a few hundred particles into a disc and plenty will land on top of each other. Two families of fix exist. Rejection sampling (draw, check against everything placed so far, redraw on collision) distorts the distributions it guards: rejections concentrate wherever there's space, a Ring stops being a ring, and the deterministic Sunflower can't be resampled at all. Relaxation samples everything wherever the strategy wants and then repeatedly pushes intersecting pairs apart until nobody intersects. It works with every strategy and preserves the sampled shape, because it only ever nudges. This project does relaxation, and the config's own doc comment states the promise: positions are nudged, not resampled, so the shape survives.

The solver, and the three decisions in it

Decision one: measure everything, then move everything. The alternative (move each particle the moment an overlap is found) converges faster but makes the result depend on array order, which means the same input produces subtly different clouds for no meaningful reason.

Decision two: divide by the contact count, then overshoot. A particle wedged inside a clump might be intersecting eight neighbours, each contributing a "get away from me" vector. Applying the raw sum would fire it across the map; the clump would collapse back and repeat next pass. Dividing by the count averages the demands, and RELAXATION = 1.4 then pushes slightly past the average, because pure averaging undershoots and takes forever to settle. (Numerics people will recognise successive over-relaxation.)

Decision three: the area is a hard wall. Every moved particle goes through Area::clamp_inside, which leaves inside points alone and radially projects escapees back onto the boundary (p / sqrt((x/a)² + (y/b)²) lands exactly on the ellipse). Overcrowd the area badly enough and the solver will trade "outside the area" for "still overlapping at the rim", which is the correct reading of the config's contract: the spawn region is a constraint, not a suggestion.

Three details worth naming:

  • distance_sq >= wanted * wanted compares squared distances, avoiding a square root for every pair that isn't touching, which is most of them.
  • Two particles at exactly the same point have no direction to separate along; dividing by zero would spray NaN through the whole cloud. Coincident pairs get a deterministic direction synthesised from the particle's index times the golden angle, so a stack of coincident particles opens into a rosette instead of all shooting the same way. (The constant here is the literal 2.399_963_2; the sunflower sampler computes the same number as PI * (3.0 - 5.0_f32.sqrt()). Same angle, two spellings.)
  • The correction is split by mass, each particle moving in proportion to the other's share of their combined mass, so a heavy particle barely budges while a light one does the travelling. Physically arbitrary, visually right: big things hold their ground. The total_mass > 0.0 guard catches the two-massless-particles case with an even split instead of 0/0.

Not comparing everything to everything

Checking every pair is O(n²) per pass, with as many passes as the config's iterations allows (32 by default). So neighbours come from a uniform grid, the simpler sibling of chapter 10's: one Vec<u32> of indices per cell, rebuilt each pass because the pass moves particles.

Two constraints, and the larger wins. Cells must be at least contact wide, the largest distance at which any two particles could interact (two widest radii plus the padding), because that is exactly what guarantees an overlapping pair lands within the 3×3 block of cells around either of them. Make cells smaller and the search silently misses pairs. Beyond that floor, cells are sized for roughly one particle each, so a thin cloud in a huge area doesn't allocate a million empty buckets. The same two-bound logic reappears in collision.rs with two extra degenerate-shape guards; the two grids stay separate code because one only ever runs during startup and one is rebuilt sixty times a second, and they've diverged in storage strategy accordingly.

Knowing when to stop, and when to admit defeat

accumulate_pushes returns the depth of the worst intersection it found, and the loop breaks as soon as that is at or below tolerance = 1e-3 × widest_radius: a convergence threshold relative to particle scale, so microscopic and gigantic clouds behave identically. Because the measurement happens before anything moves, the early exit is a real guarantee about the final state, not a hope.

And when the task is impossible, it says so up front. Random arrangements of discs can't be packed much past about 65% coverage (well below the hexagonal-packing ceiling of about 91%, which needs arrangement, not relaxation), so before the first pass:

The occupied area counts each particle as its disc grown by half the padding, since each of the two neighbours sharing a gap owns half of it. Not a panic, not a clamp: generation proceeds, leaves the residual overlap behind, and tells you which three knobs would fix it. (And under collisions: "Merge", any overlap that survives generation gets fused on the very first tick, which is either a bug or a feature depending on what you were trying to build.)

check yourself
Why does Sunflower come out clean without any separation at all?

Because the golden-angle spiral is constructed to be evenly spread: consecutive points land about 137.5° apart around the centre, the least resonant angle there is, so no spokes and no clumps form and each point gets an equal share of area. At sane densities the natural spacing already exceeds the particle diameters. Crank amount up far enough and even it will overlap, and then the separation pass earns its keep.

You set padding to 5.0. What changes?

wanted grows by 5 for every pair, so the cloud settles with a five-unit gap between neighbours instead of touching. The grid's cell size grows too (padding is part of contact), and the crowding check counts half the padding into each particle's footprint, so it warns earlier, correctly.

The overlap pass moves particles. Why doesn't that ruin a Ring distribution?

Because it only ever nudges by the amount needed to stop touching, and the pushes are symmetric. A ring stays a ring, slightly thicker. Rejection sampling would distort it, because rejected candidates get redrawn into wherever happens to be empty.

Why must velocities be sampled after separation rather than in the same pass as positions?

Orbital computes v = ω × r from the particle's position, and Radial points along it. Separation moves particles. Velocities sampled first would describe orbits around points the particles no longer occupy; the rotating disc would visibly shear. Position-free strategies (Stationary, CommonVector, Random) wouldn't care, but ordering the pipeline for the strategies that do costs nothing.

color/: mass, in colour

Three small files that know nothing about particles, physics or GPUs. They answer one question, "given a number and a list of colour stops, what colour is it?", and the answer is more interesting than it sounds.

A colour is four floats from 0 to 1 (red, green, blue, alpha) because that is exactly what the shader wants and what WGSL's vec4<f32> is. Not 0 to 255, not a struct, and being a plain float array makes it Pod for free, so it embeds directly in the GPU-bound structs. The three constants are the fixed colours of the mass ramp; the thresholds where each kicks in come from the config's colors section (defaults: white at 10, yellow at 200, red at 1000).

Why blending in RGB looks wrong

The naive way to blend two colours is to average each channel. Try it with yellow [1, 1, 0] and red [1, 0, 0] and you get [1, 0.5, 0], which is orange; fine. Now try blue [0, 0, 1] and yellow [1, 1, 0]: you get [0.5, 0.5, 0.5], a dead grey. Halfway between two vivid colours should not be mud.

So mix converts both ends into HSL (hue, saturation, lightness), interpolates there, and converts back. Hue is an angle around a colour wheel, so blending it walks around the wheel through the vivid colours instead of cutting across the grey middle.

Two subtleties, both of which are bugs if you leave them out:

Grey has no hue. White, black and every grey convert to HSL with saturation 0 and a hue of nothing in particular (the conversion returns 0, which is red, arbitrarily). Blend white to yellow naively and you'd travel from "red with no saturation" to "yellow with full saturation", swinging through pink on the way. The two swap lines fix it: a colourless endpoint borrows the hue it's heading for, so white to yellow becomes a pure saturation-and-lightness fade at constant yellow hue. If both ends are achromatic, the first swap makes them agree and the step is zero; harmless.

Hue is circular. Going from hue 0.9 to hue 0.1 the short way is +0.2, not −0.8. The hue_step adjustment picks the shorter arc, and rem_euclid(1.0) at the end brings the result back into 0..1. Without it, some blends take the scenic route through every colour in the spectrum. (The private to_hsla/to_rgba pair below mix are the textbook conversions, chroma and sector match included; the one idiom worth stealing is [r, g, b].into_iter().reduce(f32::max) for a three-way max without nesting.)

The ramp

partition_point is a binary search: it returns how many stops sit at or below the value, which is exactly the index of the stop above it. From there, upper - 1 is the stop below, the two thresholds give a 0..1 position between them, and mix does the rest. Below the first stop and above the last, the ramp flattens out rather than extrapolating into nonsense.

The constructor sorts, and that one line is what backs a promise made all the way over in the config schema: "the three are sorted by mass, so the order you write them in doesn't matter". It also means the colour names in the config are really just labels on (threshold, colour) pairs; write "red": 5, "white": 500 and light particles come out red. Note the deliberately paranoid float handling: sorting with total_cmp (which, unlike partial_cmp, is a total order that can't panic and puts NaN somewhere consistent), an explicit NaN check in sample, and a zero-span guard so duplicate thresholds can't divide by zero. sample is total: any f32 in, valid colour out.

view/: camera and mouse

Two working files, plus a re-export mod.rs: camera.rs is pure math with no winit types anywhere, controls.rs translates mouse events into calls on it. No wgpu types in either.

The camera is three numbers

pan is where the world's origin sits on screen, in physical pixels from the window centre, +y up. zoom is pixels per world unit. The private fields are limits copied out of the config once at construction; the camera never holds a config reference. And the entire world-to-screen mapping, the one formula this whole codebase revolves around, is:

screen_px = world × zoom + pan

The formula itself doesn't live in this file. It lives in the vertex shader (chapter 16), and these fields only mean anything because the shader applies them exactly that way; camera and shader are two ends of one contract. With the shipped "initial": 10.0, one world unit is ten pixels, so a mass-100 particle (radius 5 world units) draws about 100 pixels across.

why though? the no-scaling trick

"Resizing must not scale or move the scene." Look at the formula: the window's size appears nowhere in it. World units become pixels using only zoom and pan, so when the window changes, nothing about the scene's pixel size or its position relative to the window centre can change; the resize only changes how many pixels exist around the centre for the world to show through. The invariant isn't enforced by careful code; it's baked into the choice of coordinate system.

Panning: embarrassingly simple

The mouse moved 30 px right, so add 30 to pan.x, and every world point lands 30 px further right. The scene sticks to the cursor 1:1 at any zoom, because pan is applied after the zoom multiply; that's the entire reason pan is stored in pixels rather than world units.

Zooming: exponential, and anchored under the cursor

deep dive: why multiply, and where that pan formula comes from

Why zoom_step.powf(lines) instead of adding? One wheel notch multiplies zoom by 1.1. Multiplying feels identical at every scale: +10% is a visible step whether you're at zoom 4 or zoom 4000. Adding a fixed amount would crawl when far out and explode when close in. powf also accepts fractional line counts, which is what trackpads produce, so zooming is smooth there for free. The clamp stops you scrolling into oblivion; and because the clamped value feeds k, hitting a limit makes k = 1 and the pan correction becomes a no-op, so scrolling at the stops doesn't drift the view.

The anchor formula, with actual numbers. The rule wanted: the world point currently under the cursor stays under the cursor while everything grows around it. Say zoom = 10, pan = (0,0), cursor 100 px right of centre. The world point under it is (100 − 0) / 10 = 10. Scroll one notch in: new_zoom = 11, so k = 1.1. Changing only zoom would land that point at 10 × 11 = 110 px; it slid 10 px away. To pin it, solve 10 × 11 + pan' = 100, giving pan' = −10. The formula produces exactly that: 100 − (100 − 0) × 1.1 = −10. In general pan' = a − (a − pan) · k is just "solve w · zoom' + pan' = a for pan'", computed without ever converting to world space. Zoom out and k < 1; the same line pulls the scene back toward the cursor.

Two configuration edge cases the code chooses not to guard: initial isn't clamped against min/max, so a config starting outside the range snaps into it on the first scroll; and step at or below 1 inverts or freezes zooming, which the config's own schema documentation warns about instead of preventing. Config leniency, chapter 6 flavour.

The coordinate flip

src/view/controls.rs owns two jobs: remember what the mouse is doing, and translate raw window events into camera operations. It also handles a subtle, bug-breeding detail: the two halves of this program disagree about which way is up.

deep dive: the controller, line by line

Read it as a story: convert to centred coordinates; if the cursor's previous position is known, the left button is held, and panning is enabled in the config, pan by the difference; either way remember where the cursor is now. Releasing the button needs no special handling: on_mouse_button flips left_down and this function stops calling pan_by.

cursor is an Option<Vec2> because "where was the cursor last event" genuinely has no answer before the cursor has ever entered the window, and panning needs a previous position to subtract from. Encoding "no answer yet" in the type means the first-ever mouse event can't produce a garbage jump.

A mouse wheel reports LineDelta in whole notches; a trackpad reports PixelDelta in pixels. The match normalises both into notch units, dividing pixels by SCROLL_PIXELS_PER_LINE = 60.0, a conventional notch height, so the same zoom_step exponent serves both input styles. Horizontal scroll is discarded in both arms. And self.cursor.unwrap_or(Vec2::ZERO) reads as "the cursor position, or the window centre if it's never been seen": a graceful default for the scroll-before-first-mouse-move edge, instead of a crash.

Two honest gaps a future version might close: left_down is only cleared by a release event, so a release that the window never hears about (possible around focus loss on some platforms) leaves the next hover panning with no button held; and cursor keeps its last inside position after the pointer leaves, so a scroll from outside anchors at a stale point. Both are the kind of papercut you fix when a platform actually exhibits it.

gpu/: the drawing machine

Everything chapter 14 built is plumbing; these two files finally draw. scene.rs turns particles into something the GPU understands; renderer.rs bakes a pipeline once and replays it every frame. The interesting story is how Rust structs become GPU bytes: the one place the two computers from chapter 2 must agree perfectly.

The translation layer

The GPU never sees a Particle. It sees a Shape: a thing with a centre, a size, a kind and a colour. Physics on one side, presentation on the other, and one small function between them.

sync is the whole mapping: position becomes centre, radius times two becomes size (the shader wants a diameter), and mass becomes colour via chapter 12's ramp, which Scene::init built from the config's thresholds. clear() then extend() rather than building a fresh Vec means the allocation is reused; and since merging only ever shrinks the particle count, the steady state allocates nothing. This runs only on frames that received a new snapshot, not on every frame.

Rust: a const assertion

const _: () = assert!(size_of::<Shape>() == 32); is a compile-time check with no runtime presence at all. If someone adds a field or reorders one such that the struct stops being exactly 32 bytes, the build fails here, with this line highlighted, instead of the shader silently reading garbage. Cheap insurance at the one place the two languages have to agree.

Two structs, two languages, one memory layout

There are two buffers. Globals is the camera: the same for every particle, so it's a uniform. The shape list is per-particle and much larger, so it's a storage buffer.

Two declarations, two languages, two compilers, describing the same bytes. Nothing checks they match; if they drift apart the shader just reads garbage from the wrong offsets. Here is Shape, byte by byte:

deep dive: the three magic attributes, and the mystery _pad
Rust: #[repr(C)]

By default Rust may reorder struct fields in memory for efficiency; the source order is a suggestion. #[repr(C)] switches to C's rules: fields in declared order, predictable layout. Mandatory for any struct whose raw bytes another system will read.

Rust: bytemuck's Pod and Zeroable

Turning a struct into bytes is trivially easy to do wrong (padding bytes, pointers, types with invalid bit patterns). Deriving Pod ("plain old data") makes the compiler prove the struct is nothing but plain numbers with no gaps; the derive fails to compile if there's hidden padding. That proof is what makes bytemuck::cast_slice(shapes) a safe, zero-cost "give me these 32×N bytes" instead of an unsafe hack.

And why _pad in Globals? WGSL rounds a struct's size up to a multiple of its alignment, which for this struct is 8 (from the vec2s). Without the pad, the WGSL side would be 24 bytes while the Rust side is 20, the uniform buffer would come up 4 bytes short of the shader's minimum binding size, and wgpu would reject the bind group at draw time. The explicit _pad: f32 makes both sides agree on 24 honestly, and doubles as a free slot for the next field. Shape needs no such trick: its vec4 already lands the size on a clean multiple.

One draw call for every particle

rpass.draw(0..6, 0..self.shape_count) is the whole drawing command. The first range is vertices: six, because a quad is two triangles. The second is instances: one per shape. The GPU runs the vertex shader 6×N times, and each run knows both which corner it is and which instance it belongs to, so it looks up shape #N in the storage buffer and places its corner accordingly. One command, any number of particles, no per-particle CPU work at draw time. That's instancing, done "vertex-pulling" style: the pipeline declares buffers: &[], no vertex buffers at all, because both the geometry and the per-instance data are fetched by index inside the shader.

The black background is one enum value: LoadOp::Clear(BLACK) means "when this pass begins, wipe the canvas". Not a draw call; a "how to start the pass" setting, and the reason this pass must be the frame's first: anything drawn before it is erased. It runs even when there are zero shapes, which is what keeps the window black rather than undefined. The overlay's pass uses the other option, LoadOp::Load, "keep what's already there", which is the entire mechanism of layering (chapter 17).

GPU concept: record, then submit

GPU work isn't issued call-by-call; that would mean thousands of tiny CPU-to-GPU round-trips. Instead everything is recorded into a command encoder (a shopping list), and the finished list goes to the queue in one submit. Until then, nothing has happened on the GPU at all. Notice this function takes an encoder and records: it does not create the encoder, submit, or present. app.rs owns the frame and the submission, which is exactly what lets it slot the overlay's pass in after this one. The standard shape for a renderer that isn't the only one: record, don't submit.

Uploading new shapes

Called only on frames that received a snapshot (chapter 7), not on every frame. A GPU buffer has a fixed size, so if the shape count ever exceeded capacity, the buffer is replaced with the next power of two, and then the bind group must be rebuilt too, because the old one still points at the buffer that just went away. In this app the count only ever falls (merging), so the growth path will likely never fire after startup; it's four lines of insurance against the day something spawns particles at runtime. Shrinking never happens either: stale bytes past shape_count just sit in the buffer, never drawn, because the draw call's instance range, not the buffer's length, decides what exists.

GPU concept: uniform vs storage buffer

Both are just blocks of GPU memory; the difference is how the shader may use them. A uniform is small (only 64 KB guaranteed), read-only, and the same value for every invocation: ideal for the 24-byte camera. A storage buffer can be enormous, can be declared as a runtime-sized array<Shape>, and can be indexed per-invocation, which is exactly what "shape number instance_index" needs. It can also be written by a compute shader, which is how the physics would eventually move to the GPU (chapter 19).

deep dive: sockets and plugs, and why they're separate objects
GPU concept: why two objects for one buffer?

The layout (socket shape) is part of the pipeline's compiled interface; the shader is compiled against "binding 0 is a uniform, binding 1 is a read-only storage array". The group (the plug) is swappable without recompiling anything, which is exactly what update_shapes does when it swaps in a bigger buffer. The socket numbers here are the same ones the shader declares with @group(0) @binding(0) and @binding(1). That pair of numbers is the entire connection between the two languages.

visibility: ShaderStages::VERTEX is worth noting: the fragment stage never touches either buffer. Colour reaches it as a flat, per-instance output of the vertex stage instead (chapter 16).

check yourself
Which single line paints the background black?

You add a time: f32 field after zoom in Globals but forget the WGSL side. What happens?

Both sides compile fine, and nothing complains: wgpu only requires the bound buffer to be at least as large as the shader's struct, so the Rust side's 28 bytes sail past the shader's 24-byte minimum, and time quietly lands in the bytes the shader calls _pad. It's the opposite drift, a Rust struct smaller than the WGSL one, that gets rejected at draw time; and swapping two same-sized fields produces no error at all and just renders nonsense. Edit those two structs as a pair, always.

Why is write_buffer for Globals unconditional but update_shapes conditional?

Because the camera can change on any frame (a drag is in progress right now) and it's 24 bytes; checking would cost more than writing. The shapes can only change when the simulation ticks, and at scale that upload is megabytes, well worth skipping when nothing is new.

WGSL: var vs let

In WGSL, let is an immutable value; var is actual addressable storage. The corner array is a var because indexing with a runtime value (vertex_index) requires the array to exist in real memory on every backend, not as a compile-time value. Write let there and some compilers reject it.

deep dive: the fragment shader, and how a square becomes a circle

Four lines, and one of them is the entire reason particles look round. Remember that local is the corner position, −1..+1, but by the time the fragment shader sees it, the rasterizer has interpolated it across the triangle. So each fragment gets its own position within the quad: (0,0) dead centre, (1,1) at a corner, length > 1 anywhere outside the inscribed circle. discard means "produce no pixel at all", and the background shows through.

Because the scene pipeline does no blending, this discard is the only thing shaping the circle, which means the edge is hard: a pixel is either inside or it isn't, and at small sizes you can see the staircase. A soft edge would mean returning an alpha that fades near length(in.local) == 1.0 and turning on blending in the pipeline; the machinery for exactly that is in the overlay's pipeline one chapter over.

kind is also the extension point: today KIND_CIRCLE is the only value (a constant maintained by hand on both sides of the language boundary), and the if looks pointless. Add a second kind and shapes with it simply skip the discard and stay square: one storage-buffer field, no second pipeline, no second draw call.

check yourself
How many times does the vertex shader run with 50,000 particles on screen?

300,000: six corners times 50,000 instances. Which sounds enormous and takes the GPU no meaningful time; the fragment stage, running once per covered pixel, is the one that scales with how big the particles look rather than how many there are. (Meanwhile the CPU integrating 2.5 billion gravity pairs per tick is the actual bottleneck at that count; chapter 19.)

Where does the vertical flip between "screen" and "clip" happen for particles?

Nowhere, and that's the trick. winit's y-down cursor coordinates get flipped once, in centered() (chapter 13), so the camera's pixel frame is already y-up, and this shader's pixels * 2.0 / resolution carries y-up straight into y-up clip space. The overlay, which genuinely lives in a y-down frame, does its own flip in its own shader instead.

@group(0) @binding(1): where do those numbers appear on the Rust side?

Twice: the bind group layout entry declares binding: 1 as a read-only storage buffer, and the bind group plugs the real buffer into binding: 1. Then set_bind_group(0, …) at draw time supplies group 0. Numbers matching across the language boundary is the entire wiring mechanism.

ui/: text from scratch

Two panels of text sit in the top corners of the window. The left one says what the world is doing; the right one says what you are doing to it, which keys do what, and which settings file is in effect. They look like the most ordinary thing on screen and they are by some distance the most machinery per pixel in this codebase.

Because there is no such thing as "draw text" on a GPU. There is no text. There are triangles, and there is reading colours out of an image, and that is the entire vocabulary. Every character you can see is a small rectangle, two triangles exactly like a particle, with a picture of a letter stretched over it. The whole overlay is one draw call of instanced quads: a couple of translucent background plates plus one quad per visible character.

why though? there are crates for this

There are, and they're good: wgpu_text, glyphon, egui all render text onto a wgpu surface. This module exists because the point of the project is to know what the machine is doing, and "text appears" is exactly the kind of thing that stays magic forever unless you build it once. One crate survives the cut, and the seam is worth stating precisely: fontdue turns one character at one size into a greyscale bitmap plus its measurements, and everything else (the atlas, the layout, the buffers, the shader, the blending) is this project's code.

Step zero: getting a font at all

The program ships its own font: include_bytes! compiles the JetBrains Mono variable-weight TTF (from the JetBrains_Mono/ directory at the repo root, OFL licence alongside) straight into the executable. The loading policy is therefore two steps and infallible: if the config names a fontPath, try it, and on any failure print why and fall through; then use the bundled face. There is no OS font hunting, no per-platform fallback list, and no "overlay disabled" state; a machine with no fonts installed at all still gets text. The expect inside bundled() ("the bundled font is compiled in, and parses") is the honest kind of panic: the bytes are a compile-time constant, so if they don't parse, the binary was broken at build time. The startup log prints Using font: … so there's never a mystery about which face is live.

One trade to know about: FontSettings::default() loads the variable font at its default weight, with no axis selection. Fine for an overlay; worth knowing if the text ever looks lighter or heavier than the JetBrains Mono you're used to.

The atlas: rasterise once, draw forever

Rasterising a character (turning its stored outline into pixels) is the expensive part, and the answer never changes for a given size. So it happens once, at startup: rasterise every character the overlay can ever display, pack the bitmaps side by side into one image, upload that image to the GPU as a texture, and never think about outlines again. From then on, drawing a letter is drawing a rectangle that reads from a known corner of that image. This is a glyph atlas, and it is how essentially all real-time text works.

Which characters? Code points 0x20 to 0x7E: space through tilde, the 95 printable ASCII characters. A deliberate ceiling: this is a debug readout displaying numbers and labels the project wrote itself. It also buys a data structure so simple it's barely one:

Because the range is contiguous, "which glyph is 'k'" is a subtraction: 0x6B minus 0x20 is index 75 into a fixed-size array. No hash map, no allocation. Anything outside the range (an accented letter, an emoji) silently becomes ?, which is what you want from a debug overlay: a visible, obviously-wrong character beats a mystery. Since the overlay now displays the config file's path, this is no longer hypothetical; a path with non-ASCII characters in it renders its exotic parts as question marks and everything still works.

Shelf packing

Where does each bitmap go in the image? Rectangle packing in general is NP-hard with a literature of clever heuristics. This is 90-odd rectangles of nearly identical height, once, at startup, so the dumbest algorithm wins:

Walk left to right laying glyphs in a row; when the next one won't fit inside the fixed ATLAS_WIDTH = 512, drop down by the tallest glyph in the row just finished and start again at the left. The width is fixed and the height is whatever the packing needed, which is why the build is two passes: placements first, then blitting and uv computation, because the normalised v coordinates can't be computed until the total height is known. Only inked glyphs are packed; the space character rasterises to a 0×0 bitmap and exists purely as an advance.

GPU concept: the one-pixel gutter

GUTTER = 1 leaves an empty pixel between neighbours, and it is there because of bilinear filtering. When the shader samples the atlas, the sampler doesn't return one pixel; it blends the four nearest, weighted by how close the coordinate is to each. At the very edge of a glyph, two of those four are outside it. With glyphs packed flush, "outside it" means "inside the next letter", and you get a faint smear of the neighbouring character along every edge: texture bleeding, unmistakable once you know it. One transparent pixel (the atlas buffer starts zeroed) fixes it forever. The sampler's ClampToEdge mode is the same insurance at the atlas's outer border.

The vocabulary of a line of text

Typography has five hundred years of terminology and a rasteriser hands you all of it at once. Here is the complete set of numbers this project actually uses, drawn for a monospaced face at a 14-pixel size (representative values; every font reports its own):

The one line of arithmetic that ties it together

Everything above is measured from a baseline, in a y-up world. The overlay places rectangles by their top-left corner, in a y-down world, because that's what a corner-anchored panel is naturally described in. Converting between the two is one expression, done once at atlas-build time, and it is the single most error-prone line in the module:

Read it as: the bitmap's bottom is ymin above the baseline, so its top is ymin + height above the baseline, so in a y-down world its top is -(ymin + height) relative to the baseline. Walking a string into rectangles

That is the entire text engine. Find the baseline once (callers pass the top of the line box and the ascent converts), then walk the string pushing a rectangle per character and sliding the pen right by that character's advance. Three things worth calling out:

The if skips the space. A space has an advance and no ink; pushing a zero-sized quad would still cost a struct in the buffer and six vertex-shader runs. Roughly one character in six in this overlay is a space, so the check trims real work for the price of two comparisons.

The pen advances even for skipped characters. Obvious once said, easy to get wrong by putting pen += glyph.advance inside the if, at which point every space collapses and tick    331 renders as tick331.

The colour comes from the caller, not the atlas. The atlas stores coverage (how much of each pixel the letter covered) and nothing else. Colour is per quad, so the same atlas draws dim grey labels, bright white values, green RUNNING and amber PAUSED without a second copy of anything. That is why the atlas is a one-channel image and not RGBA: four times the memory saved, for free.

The quad, and the 16 bytes that once ate four glyphs in five

Same idea as Shape in chapter 15, one level richer: a rectangle in pixels, a rectangle in the atlas, a colour, and a tag saying which of two kinds this is. KIND_RECT ignores the uv fields and paints flat colour (the translucent plate behind each panel); KIND_GLYPH multiplies the colour's alpha by the coverage it reads from the atlas. Two kinds, one pipeline, one draw call.

Now, about that _pad: [u32; 3]. Three separate scalars where vec3<u32> would look tidier, mirrored in the WGSL as _pad0, _pad1, _pad2. The reason is the most instructive bug this codebase has produced, and an earlier revision shipped it.

what the bug looked like

Panels correctly sized and positioned, translucent backgrounds fine, and the text almost absent: a scattering of individually perfect characters, each the right glyph in the right place in the right colour, with everything between them missing. Counting the survivors by buffer position gave every fifth quad, exactly.

That pattern is worth learning to read. Broken layout puts letters in wrong places. A broken atlas draws wrong letters. A correct subset means the data was perfect and something was reading it at the wrong stride.

The cause was one word: the padding written as _pad: vec3<u32> on the WGSL side. Same twelve bytes, surely. But WGSL's alignment rules are not Rust's:

Panels: turning numbers into a laid-out block

Three small types stack up, each a list of the one below: a panel is a list of lines, a line is a list of spans, and a span is a run of characters sharing one colour. That last level exists for exactly one reason: so a dim grey label and a bright white value can share a row.

Rust: the builder pattern, and impl Into<String>

span takes self by value and returns Self, which is what lets callers chain: Line::default().span("speed", LABEL).span("+1.00x", VALUE). Each call consumes the line, pushes to it, and hands it back; the old binding is moved out of, so a half-built line can't be used by accident. impl Into<String> in the argument accepts both a &str literal and the String that format! produces, so call sites never write .to_string().

Then one function turns a panel into quads. It is the only place in the module that knows the window exists:

It measures before it draws, and it has to. A panel's width is the width of its longest line, and you can't know that without walking every line; and you need it before placing anything, because a right-anchored panel's left edge is derived from it. So one pass measures, the plate is emitted, then each line measures again to right-align (the top-right panel's rows are flush-right, ragged-left, which keeps its column pinned to the corner as the numbers inside change width). Several passes over the same short strings per frame is genuinely nothing next to a frame that uploads buffers and rasterises pixels; if the overlay ever grew into a wall of text, caching measured widths would be the first and only optimisation needed.

The plate is pushed first, and that ordering is the layering. There's no depth buffer in this pass and no sorting; quads draw in buffer order, later over earlier. Push the background last and you'd get a neat translucent rectangle with the text hidden behind it.

Everything is multiplied by scale: the margin, the padding, and (back at atlas-build time) the font size. That's the display's DPI factor, and it's what keeps the overlay the same physical size on a 4K laptop panel and a 1080p desktop monitor.

Rust: fold(0.0, f32::max), and why not .max()

.max() on an iterator needs Ord, and floats don't implement it, because NaN is not less than, greater than, or equal to anything, so floats have no total order. fold(0.0, f32::max) sidesteps it with f32's own two-argument max, which has defined NaN behaviour. Starting at 0.0 rather than negative infinity also means an empty panel measures zero wide instead of placing its plate somewhere in the next county.

The content: numbers in, lines out

overlay.rs is the only file in the module that knows what this program is about. Everything else deals in glyphs and rectangles; this one knows there's a simulation with a tick count. It's the file to edit to make the overlay say something else, and it's deliberately boring:

format!("{label:<LABEL_WIDTH$}") means "left-align this string, padded with spaces to LABEL_WIDTH characters" (the $ pulls the width from the constant, which is 12). That's the whole column alignment, and it only lines up exactly in a monospaced font, which the bundled JetBrains Mono is; point fontPath at a proportional face and the value column goes gently ragged. The left panel, stats(), is six entry lines under a SIMULATION heading: particles, tick, fps, tps, zoom, pan.

Three details worth noticing. The manual is context-sensitive: the space and arrow entries rewrite themselves depending on status.paused, so the panel always describes what the keys do right now, quoting the same STEP_TICKS constant the keys actually use. The SETTINGS section shows the config path that chapter 6's loader reported, closing the loop for anyone wondering which file to edit (and it's absent entirely when the app is running on built-in defaults). And because the whole overlay is rebuilt from scratch every frame, keeping any of this in sync needs no mechanism at all: no dirty flags, no events. The panel is a pure function of the Status, so it cannot be stale. That's the payoff for the apparent waste of re-formatting a dozen strings at refresh rate: microseconds of formatting buy the complete absence of a category of bug.

Rust: Display, and why Speed formats itself

status.speed.to_string() works because Speed implements std::fmt::Display: the trait for "how does this look to a human". Its implementation is the halted / +1.10x logic from chapter 9, living next to the ladder it describes rather than in the overlay. Note this is deliberately not Debug: Debug is for programmers and prints Speed { index: 2 }; Display is for users. Rust keeps the two apart on purpose.

Two passes, one frame

GPU concept: why two passes and not one

The two draws cannot share one pass configuration, because they disagree about almost everything: different shaders, different bind group layouts, different coordinate conventions, and crucially different blending (the scene overwrites, the overlay blends). Switching pipelines mid-pass is legal, but you'd still issue two draws with two set_pipeline calls, so you gain nothing over two passes and lose per-pass load/store control. Two passes in one encoder is also nearly free on desktop GPUs: a pass boundary costs a state flush, not a round-trip, and the whole encoder is still one submission.

ui.wgsl: the second shader

The overlay's shader exists separately from shader.wgsl because it disagrees with it about the most basic thing there is: what a coordinate means.

Structurally this is chapter 16's shader with different arithmetic in the middle, plus two new bindings. The differences, one by one:

Unit corners, not ±1. A particle is described by its centre and a size, so its corners run −1 to +1 and get scaled by half the size. A UI rectangle is described by its top-left and a size, so its corners run 0 to 1 and rect.xy + corner * rect.zw walks from the anchor across the full extent. Same two triangles, different parameterisation of the same square.

The y flip. Clip space has +y up; these pixels have +y down. Compare the two halves of the clip expression: x/w × 2 − 1 maps 0 to −1 and width to +1, while 1 − y/h × 2 maps 0 to +1 and height to −1. It's the same conversion centered() does for the mouse in chapter 13, for the same reason, done on the GPU this time.

No camera. The uniform carries the resolution and nothing else. There is nowhere in this shader for pan or zoom to enter, which is a stronger promise than remembering not to use them: a UI that drifts when you drag the world is a UI with a bug, made unwritable.

mix picks the uv corner. mix(a, b, t) is linear interpolation componentwise, and with t being a corner made of 0s and 1s it isn't really interpolating; it's selecting. Corner (0,0) gives the atlas rect's top-left, (1,1) its bottom-right, (1,0) mixes to the top-right. One instruction instead of a four-way branch, and the rasteriser then interpolates between those corners across the triangle, stretching the glyph's little patch of atlas over its rectangle.

GPU concept: why the sample can't live inside an if

The GPU shades fragments in 2×2 blocks, in lockstep, and that's not an implementation detail you can ignore: it's how textureSample works. Choosing a mip level means knowing how fast the texture coordinate changes across the screen, and the hardware computes that by subtracting neighbouring fragments' uv from yours; it gets the neighbours' values for free because they're running the same instruction at the same moment. Put the sample inside a branch and a neighbour that took the other path never computed a uv, so the derivative is undefined. WGSL therefore requires textureSample in uniform control flow, code every invocation reaches. The fix is what this shader does: sample unconditionally, then use select(a, b, cond), the branchless pick, to decide what to do with the result. A solid rectangle wastes one texture fetch at uv (0,0); two quads per panel are solid rectangles. Cheap.

The atlas holds coverage, not colour, and the last line is where that pays off: the sampled value is used as an alpha multiplier on a colour that came from the quad. That's why one greyscale image draws every colour of text, why a half-covered pixel at a letter's edge blends smoothly with whatever is behind it (which is antialiasing), and why the panel plate goes through the identical shader by simply skipping the multiply.

The pipeline behind this shader differs from the scene's in exactly one setting that matters: blend: Some(wgpu::BlendState::ALPHA_BLENDING). The scene overwrites pixels; text is made of partial-coverage edges and deliberately translucent plates, so this pass alpha blends, computing result = src × alpha + dst × (1 − alpha) in fixed hardware after the fragment shader. It's also why plate-before-glyphs ordering matters: blending is order-dependent.

Uploads, growth, and DPI

The renderer side follows patterns you've already seen twice. prepare uploads the whole quad list and the 16-byte resolution uniform every frame; the quad buffer starts at a capacity of 1024 (64 KB) and grows by powers of two with a bind-group rebuild, exactly like the shape buffer. The atlas uploads as an R8Unorm texture ("R": one channel; "8": eight bits; "Unorm": the byte 0..255 arrives in the shader as 0.0..1.0, which is why coverage needs no division anywhere), read through a Linear-filtering, ClampToEdge sampler. Four bindings in one group: uniform, quads, texture, sampler; the last two are new kinds relative to the scene, and note their WGSL declarations use a bare var with no address space, because textures and samplers are opaque handles, not memory you point into.

One genuinely new mechanism: DPI changes at runtime. Drag the window to a monitor with a different scale factor and winit fires ScaleFactorChanged, which lands in Ui::set_scale: re-rasterise the atlas at font_size × scale, upload it as a fresh texture, rebuild the bind group (the old one points at a texture that's about to drop). This is why Ui keeps the parsed FontFace around rather than discarding it after the first rasterise: the font is size-agnostic, only the atlas is size-specific. Re-rasterising rather than scaling the old bitmap is what keeps text sharp; shrinking or stretching a bitmap of a letter blurs exactly the stems and corners your eye reads by.

check yourself
The atlas is one byte per pixel. How does the overlay draw green, white, amber and grey text out of it?

The atlas doesn't store colour at all; it stores coverage, "how much of this pixel did the letter cover". Colour lives in the Quad, per rectangle, and the fragment shader multiplies the quad's alpha by the sampled coverage. Same kilobytes of texture, unlimited colours.

You change fontSize from 14 to 28. Which parts of the program change, and which don't?

The two stubs: BarnesHut and Multipole

SimulationMethod has three variants, the config and schema document all three, and two of them are todo!(). They are stubs for the two classic answers to the same problem: at 50,000 particles, the naive method's 2.5 billion pair evaluations per tick are hopeless, and both fixes rest on one physical observation: from far away, a clump of particles is indistinguishable from one heavy particle at its centre of mass.

Barnes-Hut builds a quadtree over space each tick: recursively split the world into quarters until each leaf holds a few particles, and store each node's total mass and centre of mass. To compute the force on one particle, walk down from the root; whenever a node looks small from where you stand (its size divided by its distance is below a threshold, conventionally called θ), take the node's summary and don't descend. Each particle then interacts with O(log n) nodes instead of n particles. The structure of the code would be familiar from this very codebase: build an index, query it per particle, exactly like the two grids, with a tree instead of a grid because "who can I approximate" needs multiple scales, where "who is near me" needed only one.

Multipole (the fast multipole method) is the same tree taken further: instead of one point mass per node, store a short series expansion describing the node's gravity field, and translate expansions between nodes so groups interact with groups. Costliest to build, cheapest per particle, approaching O(n). The config's schema documentation describes exactly this split, which is why the variants exist in advance of their implementations: the settings file is documenting intent.

Both are contained changes: a new file next to collision.rs, a real body for the stub arm, nothing else. The runner, the hand-off, the renderer and the controls don't care how accelerations were computed. Until then, remember the sharp edge from chapter 1: selecting either unimplemented method panics the simulation thread on its first tick, and the window keeps running, frozen, with the panic on stderr.

Cheap wins before the big rewrite

  • Softening. If collisions: "Ignore" is ever meant to be a supported mode rather than a debugging switch, the force law needs the d² + ε² treatment from chapter 9's warning box, one line in g_accel_vector.
  • Stop allocating per tick. naive collects a fresh Vec<Vec2> of accelerations every tick; the Collider two functions away already demonstrates the persistent-scratch pattern. Small, real, and the kind of change that matters at 60 allocations a second.
  • Half the pair work. Newton's third law says the force on i from j is minus the force on j from i; the naive loop computes both anyway. An index-triangle loop (j > i, apply to both) halves the arithmetic at the cost of no longer being two nested pretty iterators.
  • Threads. The acceleration pass is embarrassingly parallel (every particle's sum is independent), which is the textbook shape for rayon's parallel iterators: change iter() to par_iter() and the O(n²) constant divides by the core count. The integration and collision passes want more care, but the expensive 95% doesn't.

The endgame: physics on the GPU

A compute shader is the third kind of shader: no vertices, no pixels, just "run this function N times over this buffer". Particles would live in a storage buffer the GPU owns; a compute pass would read positions and write new ones; the render pass would draw straight from that same buffer with no CPU round-trip at all. Concretely:

  • @compute @workgroup_size(64) as a third entry point next to the two in shader.wgsl.
  • A ComputePipeline in renderer.rs, and a begin_compute_pass recorded into the same encoder before the render pass.
  • Two particle buffers, ping-ponged: read from A, write to B, swap. The same double-buffer idea as the runner's mailbox, one level down.
  • The storage binding's read_only: true becomes writable, and required_features in context.rs may grow a line.

At that point World stops holding particles at all and the simulation thread's job becomes "submit a compute pass at 60 Hz", which, notably, still wants exactly the fixed-timestep clock chapter 9 built. The merging pass is the awkward passenger: union-find is a sequential algorithm at heart, and either stays on the CPU (requiring a readback) or gets rethought.

The one visual thing that's missing

At 60 tps on a 144 Hz screen, roughly three frames in five show a state up to 16 ms stale, and with particles genuinely moving, that reads as micro-stutter. The fix is interpolation: keep the previous snapshot as well as the current one, work out how far between ticks this frame falls, and blend positions, ideally in the vertex shader where it's free. That means the snapshot hand-off carries two states and a blend factor instead of one state, a real change to try_recv's contract. Worth doing now that things move; the related upgrade, a ring buffer of past snapshots, would also make reverse an honest replay instead of a re-integration, fixing chapter 9's caveat and chapter 10's one-way mergers in a single data structure.

why though? the shape of what's left

Notice that every remaining step is local. Barnes-Hut: one new file and one match arm. Parallelism: one function. GPU compute: renderer.rs and the shader. Interpolation: runner.rs and the shader. Nothing on the list touches the config loader, the camera, the input handling, the colour ramp, the generator or the overlay. That's what the module boundaries in chapter 4 were for, and the fact that gravity itself arrived without moving any of those walls is the evidence they were in the right places.

Glossary

Plain-language definitions. Dotted terms all over this page jump here; use the browser's Back button (or Alt+←) to return.

adapter
wgpu's word for one physical GPU in the machine (or a software fallback). You don't draw with it; you inspect it and request a device from it. Created in gpu/context.rs, chapter 14.
alpha blending
Combining a fragment's colour with what is already in the target instead of replacing it, using the fragment's alpha as the mix: result = src × src.a + dst × (1 − src.a). Done by fixed hardware after the fragment shader, switched on per pipeline. It's what turns a glyph's partial edge coverage into smooth antialiased text, and what makes the overlay's panel backgrounds see-through. The scene pass doesn't use it. Chapter 17.
atomic
A variable that can be read and written from several threads at once without tearing or a lock. simulation/runner.rs uses four: the running flag, the pause flag, the speed (an f32 smuggled through AtomicU32 as its bit pattern), and the signed step counter. Chapter 9.
atlas (texture atlas)
One image holding many small images packed side by side, so everything can be drawn from a single texture binding in one draw call. This project's is a glyph atlas: every printable ASCII character rasterised once at startup into a 512-wide, one-byte-per-pixel image whose height the packer computes. Drawing a letter is then just drawing a rectangle with the right uv corners. Chapter 17.
Barnes-Hut
The standard trick for making n-body gravity affordable: build a quadtree over space, and when a whole distant clump is far enough away, treat it as one particle at its centre of mass. Turns O(n²) into O(n log n). The config accepts "method": "BarnesHut" today, but the implementation is a todo!() stub that panics the simulation thread. Chapters 9 and 19.
baseline
The invisible line letters sit on; not the bottom of the text, since descenders like p hang below it. Every position a font rasteriser reports is measured from here: ascent is how far the font reaches above it, descent below, and a glyph's ymin says where its bitmap's bottom edge sits relative to it. Chapter 17, fig. 13.
bind group
The object that says which actual buffer (or texture, or sampler) is plugged into which numbered socket a shader declared. The socket numbering is @group(g) @binding(b) in WGSL; the Rust side matches it with set_bind_group(g, …). Its sibling, the bind group layout, describes only the socket's shape; the layout is part of the pipeline, the group carries the real resources and can be swapped when a buffer is replaced.
bleeding (texture)
When a filtered texture read at the edge of one packed image picks up pixels from its neighbour, because linear filtering blends the four nearest texels and two of them are outside the image you meant. Prevented by leaving a gap between packed items: the one-pixel gutter in the glyph atlas. Chapter 17.
buffer
A plain block of GPU memory with a size in bytes and a list of allowed uses (UNIFORM, STORAGE, COPY_DST…). No structure, no types; bytes. Both sides just have to agree on the layout (see chapter 15's byte table).
build script
An ordinary Rust program named build.rs that cargo compiles and runs before the crate itself, usually to generate code or files. This project's regenerates app-config.schema.json from the config types by re-including their source files with a stubbed parser. Chapter 6.
centre of mass
The mass-weighted average position of a group, Σ(m·p)/Σm: the point a merged body must sit at for the system's balance to be unaffected by the merge. The collider computes it in a precision-friendly form, accumulating positions relative to a seed particle. Chapter 10.
clip space / NDC
The coordinate system a vertex shader must output: x and y from −1 to +1 across the viewport (left to right, bottom to top), regardless of window size. Anything outside is clipped off. Also called normalized device coordinates.
command encoder
A recorder for GPU work. Passes and copies are "recorded" into it; nothing executes until the finished recording is submitted to the queue. Like writing a full shopping list instead of driving to the store per item.
const evaluation
Rust running your code at compile time and baking the answer into the binary. Loops, conditionals and (since 1.82) floating-point arithmetic all work. simulation/speed.rs uses it to derive the speed ladder's length from its factor and clamp, so those two constants stay the only knobs. The compile-time size assertions on Shape and Quad are the same machinery used as a tripwire. Chapters 9, 15 and 17.
device
Your open, validated connection to a GPU. Creates every resource (buffers, pipelines, shader modules, bind groups, textures) and checks your work. Mistakes are reported through the logger, which is why env_logger exists in this project.
discard
A WGSL statement that ends a fragment shader invocation without producing a pixel. What turns the square quads into round particles: any fragment more than one unit from the quad's centre simply doesn't exist, so the background shows through. Chapter 16.
drop-oldest
A hand-off policy: when the producer is faster than the consumer, keep only the newest item and throw the rest away. The opposite of a queue, and the right choice for live state; nobody wants to watch a backlog of stale physics. Implemented here by a single fresh flag on the snapshot slot. Chapter 9.
fixed timestep
Advancing a simulation by the same dt every tick, regardless of how long the tick actually took in wall-clock time. Makes runs stable to integrate and independent of the display. Its opposite, feeding in the measured frame time, makes the physics depend on the frame rate. Chapter 3.
font metrics
The numbers a rasteriser hands back alongside a glyph's pixels. Per font: ascent, descent, line gap, and their sum new_line_size (how far down the next line goes). Per glyph: advance (how far the pen moves afterwards; not the same as its width), xmin (the gap from the pen to the ink) and ymin (where the ink's bottom sits relative to the baseline). Chapter 17 draws all of them.
fragment
A candidate pixel produced by the rasterizer. The fragment shader runs once per fragment and returns its colour, or discards it.
frame
One complete image of the window. Programs like this one produce a fresh frame continuously, at the monitor's refresh rate. Also used for the surface texture the image is drawn into. Distinct from a tick.
HSL
A way of describing a colour as hue (an angle around a colour wheel), saturation (how vivid) and lightness. Blending two colours by interpolating these three, rather than by averaging red/green/blue, keeps the intermediate colours vivid instead of passing through grey. color/blend.rs converts to HSL, blends, and converts back. Chapter 12.
interior mutability
Changing a value through a shared (&) reference, which Rust normally forbids. Types built for it (atomics, Mutex, RefCell) are exactly the ones whose job is to be modified from several places at once, and they enforce their own safety internally. It's why toggle_pause can take &self while obviously mutating something. Chapter 9.
instance (wgpu)
The initialized wgpu library: the root object everything else comes from. Kept around in this project because recovering a surface marked Lost means asking the instance for a new one. Not to be confused with instancing.
instancing
Drawing the same geometry many times in a single command, with each copy told which number it is. draw(0..6, 0..N) means "6 vertices, N copies"; the shader reads @builtin(instance_index) and looks up that copy's data in a storage buffer. One draw call for every particle on screen, and a second one for every rectangle of the overlay.
JSON Schema
A standard, machine-readable description of what a JSON document may contain: which keys, what types, what ranges, with documentation attached. Editors read it to autocomplete and lint the settings file. This project's is generated from the Rust config types by the schemars crate, with /// doc comments becoming the descriptions. Chapter 6.
mutex
A lock that lets exactly one thread touch the data inside it at a time. In Rust the data lives inside the Mutex, so there is no way to reach it without locking. If a thread panics while holding one it becomes poisoned and later locks return an error; see chapter 9 for when ignoring that is legitimate.
packing (rectangle packing)
Fitting many small rectangles into one big one without overlap, wasting as little space as possible. NP-hard in general, with a literature of heuristics. The glyph atlas uses the simplest, shelf packing: fill a row left to right, drop to a new row when the next item won't fit. Near-optimal when everything is roughly the same height, which one font at one size guarantees. Chapter 17.
physical vs logical pixels
Physical: actual screen dots. Logical: physical divided by the OS scale factor (125% scaling means 1 logical = 1.25 physical). The window is requested in logical pixels so it looks right on any monitor, and all rendering math happens in physical ones.
pipeline (render pipeline)
The compiled, immutable bundle of "how to draw": vertex shader + fragment shader + output format + primitive type + blend settings. Expensive to create, so it's built once at startup and reused every frame. Different look = different pipeline; this program has two.
queue
Where command buffers are submitted for the GPU to execute, in order. Also provides write_buffer and write_texture (uploads) and, in wgpu 30, present.
rasterise (a glyph)
Turning a character's stored outline (closed loops of lines and Bézier curves in an abstract grid) into a small array of coverage values at a specific pixel size. The one job this project hands to a crate (fontdue). Distinct from the GPU's rasterizer, which does the analogous job for triangles.
coverage
What fraction of a pixel's area falls inside a shape, as a number from 0 to 1; not "is the centre inside", the actual area. Computing it is what a font rasteriser does, and using it as an alpha is what makes text look smooth rather than jagged. The glyph atlas stores coverage and nothing else, which is why one greyscale image can draw text in any colour.
rasterizer
Fixed hardware between the two shader stages: takes each triangle's three clip-space corners, works out exactly which pixels it covers, and interpolates the vertex shader's other outputs across them. Not programmable, extremely fast; its interpolation is what gives each fragment its own local coordinate, which is how the circles get cut out.
relaxation
Solving a set of constraints by repeatedly nudging everything a little way toward satisfying them, rather than solving exactly in one shot. Used at generation time to separate overlapping particles: measure every intersection, move everyone a fraction of the way apart, repeat until nothing intersects. Chapter 11.
sampler
The rules for reading a texture, kept as an object separate from the texture itself: how to blend between neighbouring texels (Nearest picks one, Linear blends the four nearest), and what a coordinate outside 0..1 returns (ClampToEdge, Repeat…). Separate because one policy can serve many images, and the same image can be read two ways in two passes.
SDF (signed distance field)
Storing, per pixel, the distance to the nearest edge of a shape rather than whether it's inside. Unlike coverage, that survives being scaled up, so one texture renders crisp text at any size: the standard trick for text that has to zoom. Overkill for an overlay at one fixed size, which is why chapter 17 re-rasterises per size instead.
semi-implicit (symplectic) Euler
The integrator in World::naive: update velocity from acceleration first, then position from the new velocity. Costs the same as naive Euler with the lines swapped, but its energy error stays bounded instead of growing, so orbits stay orbits. The standard first choice for orbital mechanics. Chapter 9.
shader
A small program that runs on the GPU, thousands of instances in parallel. Kinds used here: vertex (per corner: "where does this go on screen?") and fragment (per pixel: "what colour, or none?"). A future physics port would add compute (per anything: "just calculate"). Chapters 16 and 17.
softening
Replacing d² with d² + ε² in a gravity law so the force stays finite as two bodies approach. This project doesn't have it; merging collisions remove overlapping pairs before the singular regime, and the only guard in the force code is a skip at exactly zero distance. Chapters 9 and 19.
spatial grid
An array of buckets covering a region, each holding the indices of the things inside it. Turns "which particles are near this one?" from a scan of everything into a look at nine buckets. Cell size is the whole design: too small and pairs are missed, too large and each bucket holds everything. This codebase has two: generation/grid.rs (startup only, re-bucketed each relaxation pass) and the CSR-layout one in simulation/collision.rs (rebuilt every tick). Chapters 10 and 11.
span (of text)
A run of characters sharing one colour. The overlay models a line as a list of spans so a dim label and a bright value can share a row while still being measured, positioned and right-aligned as one unit. Chapter 17.
storage buffer
A GPU buffer a shader can index freely and, optionally, write to, and which can be declared as a runtime-sized array<T>. Bigger and more flexible than a uniform, which is small and read-only. This project has two: the 32-byte-stride Shape list and the 64-byte-stride Quad list.
surface
The bridge object between the window and the GPU: the drawable area, owning a small rotating set of images (swapchain). Must be configured (size, format, present mode) before use, and re-configured on every resize.
surface texture
"This frame's canvas": the texture the surface hands over to draw into, then given back at present. Acquiring it can fail in recoverable ways (window resized, GPU reset…); gpu/context.rs handles all of them. Chapter 14.
swapchain
The rotating set of two or three images behind a surface: while the monitor shows image A, the program draws into image B, then they swap. The word comes from Vulkan; wgpu hides it inside the surface.
texture
GPU memory organized as an image (width × height × pixel format) rather than raw bytes. What render passes draw into; also what the glyph atlas is stored as.
tick
One step of the simulation, always the same size in simulated seconds. Ticks are produced by simulation/runner.rs at the configured tickRate (scaled and signed by the speed dial) and have nothing to do with frames: the title bar shows both numbers so you can watch them disagree.
triple buffer
Three buffers rotating between three roles (one being written, one waiting in a shared slot, one being read) so a producer and a consumer can run at different speeds without either waiting or copying under a lock. Chapter 9, fig. 5.
union-find
A data structure answering "are these two things in the same group?" under repeated merging of groups, in effectively constant time per operation. An array of parent links forming forests; joining points one root at another, and lookups flatten paths as they walk (this project uses path halving). How the collider turns pairwise overlaps into transitive piles. Chapter 10.
uniform control flow
Code that every invocation in a GPU's lockstep group actually reaches. textureSample requires it, because it picks a mip level by comparing texture coordinates with the neighbouring fragments in the same 2×2 block, and a neighbour that took the other branch never computed one. The fix is to sample unconditionally and use select on the result, which is what ui/ui.wgsl does. Not to be confused with a uniform buffer.
uniform
Small, read-only data that is the same ("uniform") for every shader invocation in a draw: settings, not per-item data. The scene's is window resolution + camera pan + zoom, 24 bytes, updated every frame. Per-particle data goes in a storage buffer instead.
uv coordinates
Where in a texture to read from, expressed as fractions of its size: (0,0) is the top-left corner, (1,1) the bottom-right, regardless of how many pixels it actually has. Each glyph in the atlas stores four of them (its rectangle's two corners), computed once at build time, which is why changing the font size needs no shader change. The letters u and v are used simply because x, y and z were taken.
vertex
One corner of a shape. GPUs draw everything as triangles between vertices. A particle quad = 2 triangles = 6 vertex-shader runs per particle (two corners are visited twice).
vsync / Fifo
Synchronizing presentation to the monitor's refresh. In wgpu it's the Fifo present mode (the default, and the only one guaranteed everywhere): finished frames queue up and are shown one per refresh; when the queue is full, the program waits. Smooth, tear-free output and free CPU throttling, for the drawing thread only.
Vulkan
One of the low-level "languages" GPU drivers speak (others: DirectX 12, Metal). wgpu translates the app's calls into whichever one the platform has; the terminal's Using GPU: line says which was picked. You never write Vulkan yourself here.
WGSL
WebGPU Shading Language: the language shaders are written in for wgpu. Rust-ish syntax, but a separate, much smaller language compiled by the GPU driver. Chapter 16 is a full tour; chapter 17 has the alignment rules that bite.
winit
The Rust crate for windows and input: creates the window, delivers every OS event (mouse, keyboard, resize) to the App. Cross-platform; knows nothing about drawing.
world space / screen space
World space: the simulation's own coordinate system, in world units, where particles actually live regardless of any window. Screen space (in this codebase): physical pixels measured from the window's centre, +y up. The camera converts world to screen; the shader converts screen to clip.
